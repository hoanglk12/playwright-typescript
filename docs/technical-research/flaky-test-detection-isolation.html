Automatic Flaky Test Detection and Isolation

Playwright already computes a per-test flaky outcome and monocart already stores it, but nothing in this framework reads either signal beyond a single Slack field on the UI side. This report traces exactly what Playwright 1.61.1 and monocart 2.11.2 give for free, verified against the installed source rather than assumed, and lays out a phased path from "surface what already exists" to "rerun a flagged test in isolation to tell true flakiness apart from shared-state pollution."

01

Summary

What already runs for free, and the four gaps sitting on top of it
EN

Playwright computes a per-test flaky outcome the moment a test fails at least once and then passes or gets skipped within its retry budget. This repo already retries in CI: UI via env.retries (default 2), API hardcoded to 2. monocart already stores a caseType: 'flaky' flag per test too. None of that is a proposal; it runs on every CI build today.

VI

Playwright tự tính ra outcome flaky cho một test ngay khi test đó fail ít nhất một lần rồi pass hoặc bị skip trong giới hạn retry. Repo này đã bật retry trên CI: phía UI qua env.retries (mặc định 2), phía API hardcode cứng là 2. monocart cũng đã lưu sẵn cờ caseType: 'flaky' cho từng test. Không có gì trong đó là đề xuất, nó đang chạy thật trên mọi lần build CI.

GapWhere it shows upWhy it matters
API flaky count is dropped at four separate points api.config.ts:77-88, playwright-with-slack.yml:571-620 & :907-960, api-restful-tests-with-slack.yml:102-120 UI Slack already shows a 🔁 Flaky field; API Slack does not, even though the underlying data exists
No cross-run flakiness memory monocart trend file is summary-level only (share.js:156-172) Can't answer "which tests flake 1 run in 20" without a new store
No mechanism to re-run a flagged test alone --last-failed excludes flaky tests by design (ok() returns true for flaky) Can't distinguish true flakiness from order-dependency without one
No quarantine convention no @flaky tag, grepInvert, or list anywhere in the repo Confirmed flaky tests have no documented place to live once identified
✓
EN

Top-line conclusion: the expensive part of flaky triage, capturing what went wrong on the failing attempt, is already solved. consoleHelper and attachVerboseLogFailureContext both gate on testInfo.status, which is per-attempt, so a flaky test's failing attempt already carries full console/network/redacted-payload diagnostics today, with zero changes needed. What's missing is aggregation and routing, not capture.

VI

Kết luận chính: phần tốn kém nhất trong việc triage flaky test, bắt lại chuyện gì đã xảy ra ở lần chạy fail, đã được giải quyết sẵn. Cả consoleHelper lẫn attachVerboseLogFailureContext đều gate theo testInfo.status, vốn tính theo từng attempt, nên lần chạy fail của một test flaky đã có sẵn đầy đủ console/network/payload đã redact, không cần sửa gì cả. Thứ còn thiếu là gom lại và định tuyến dữ liệu, không phải chuyện bắt dữ liệu.

What's proposed
EN

A three-increment path: (A) close the API flaky-reporting gap with config and workflow edits only, no new code; (B) add a small "flaky ledger" reporter that emits an ID-precise list in the exact shape Playwright's own --last-failed-file reader expects; (C) add a non-blocking CI job that reruns flagged tests in isolation to separate true flakiness from order-dependency. Auto-quarantine, auto-skip, gating flags, retry-count changes, and any third-party service are carved out for separate sign-off, covered in section 04.

VI

Một lộ trình ba bước: (A) vá lỗ hổng báo cáo flaky phía API chỉ bằng sửa config và workflow, không thêm code mới; (B) thêm một reporter "flaky ledger" nhỏ, xuất ra danh sách chính xác theo ID, đúng định dạng mà chính bộ đọc --last-failed-file của Playwright mong đợi; (C) thêm một job CI không chặn pipeline, chạy lại riêng lẻ các test bị gắn cờ để phân biệt flaky thật với lỗi phụ thuộc thứ tự. Auto-quarantine, auto-skip, các cờ gate, thay đổi số lần retry, và bất kỳ dịch vụ bên thứ ba nào đều được tách riêng, cần user duyệt độc lập, nói rõ ở mục 04.

02

Confirmed facts

Verified against installed source, not general Playwright knowledge
EN

Every row below was checked against node_modules/playwright/lib and node_modules/monocart-reporter/lib, not assumed from general familiarity with Playwright.

VI

Mọi dòng dưới đây đều được đối chiếu trực tiếp với node_modules/playwright/lib và node_modules/monocart-reporter/lib, không suy đoán từ hiểu biết Playwright nói chung.

ClaimVerdictEvidence
A test is flaky only when it has both an expected/skipped result and an unexpected one across its own attempts Confirmed computeTestCaseOutcome(), common/index.js:2524-2550: computed per TestCase, never across shards or across different tests
ok() treats flaky as a passing outcome Confirmed common/index.js:2766-2769: ok() returns true for expected | flaky | skipped. A flaky test never fails the run.
Failed-then-cascade-skipped also reads as flaky Confirmed, false-positive source The only route to unexpected requires zero expected and zero skipped results (:2547). Serial-mode cascade skips in misc-api specs can manufacture a false flaky reading.
--last-failed can rerun flagged flaky tests Rejected .last-run.json is written from !t.ok() (runner/index.js:6179); since ok() is true for flaky, they're structurally excluded.
--last-failed-file accepts a hand-written ID list Confirmed runner/index.js:6012-6014 does no validation beyond parsing {status, failedTests} and filtering by ID. This is the mechanism Option C is built on.
Test IDs are stable and project-scoped Confirmed, with a rot condition common/index.js:2071-2079: sha1(path) + sha1([project=id]path+titles). Stable across reruns of the same commit; invalidated by file moves, title renames, or project renames.
monocart's trend file carries per-test history Rejected platform/share.js:156-172 copies only date, duration, and scalar summary fields per entry. No per-test data survives into trends.
monocart already stores per-test flaky classification today Confirmed visitor.js:238-366: outcome: testCase.outcome() and caseType: 'flaky' are already in every monocart-report/index.json. Nothing currently reads it.
Existing failure-context gating needs no change for flaky tests Confirmed base-test.ts:124 / ApiTest.ts:203 gate on testInfo.status, which is per-attempt. A flaky test's failing attempt already gets its attachment; its passing attempt does not.
Single-test isolation is a valid discriminator for the API suite Rejected api.config.ts:41's own comment: shared cartId/addressId state across tests in a spec. Running one test alone will fail for reasons unrelated to flakiness.
⚠
EN

The --last-failed-file path is also a write target: LastRunReporter overwrites it at onEnd. A rerun invoked with a flaky-ID file as that override path will replace the file with its own failures. Any implementation must copy the ledger to a scratch path first.

VI

Đường dẫn --last-failed-file cũng là một đích ghi: LastRunReporter sẽ ghi đè nó ở bước onEnd. Một lần rerun dùng file ID flaky làm đường dẫn override đó sẽ bị thay bằng chính danh sách fail của lần rerun đó. Bất kỳ triển khai nào cũng phải copy ledger sang một đường dẫn tạm trước.

Options

Six approaches, from "surface what's already free" to a third-party service
Option A: surface what already runs for free
EN

Route the API suite's already-computed flaky count through the same onEnd → workflow → Slack path the UI suite already uses. No new dependency, no new code.

VI

Đưa số lượng flaky đã tính sẵn của bộ API suite đi qua cùng đường onEnd → workflow → Slack mà UI suite đã dùng. Không thêm dependency, không thêm code.

ProsCons
Corrects a real asymmetry between the two suites' Slack reportsGives a count, not a list of which tests
Lowest risk: markdown table rows and workflow echo/extract steps onlyStill invisible locally, since local runs have retries: 0
Merged UI summary already computes summary.flaky correctly, so the API single-job case needs no merge logicDoesn't distinguish true flakiness from order-dependency
Option B: flaky ledger reporter
EN

A Reporter that walks suite.allTests() at onEnd, selects outcome() === 'flaky', and emits an ID-precise flaky-ids.json in Playwright's own .last-run.json shape, plus a richer flaky-report.json for humans.

VI

Một Reporter duyệt qua suite.allTests() ở onEnd, chọn ra outcome() === 'flaky', xuất ra flaky-ids.json chính xác theo ID, đúng định dạng .last-run.json của Playwright, cùng một flaky-report.json đầy đủ hơn cho con người đọc.

ProsCons

Option C: rerun-in-isolation, the discriminator
EN

Consume the ledger's ID list in a follow-up CI job. This means different things per suite: the UI suite (fullyParallel: true) can rerun a single flagged test alone at --workers=1. The API suite (fullyParallel: false, shared cartId/addressId) cannot; the correct unit there is the whole spec file for that one project.

VI

Dùng danh sách ID từ ledger trong một job CI tiếp theo. Điều này khác nhau giữa hai suite: UI suite (fullyParallel: true) có thể chạy lại riêng một test bị gắn cờ ở --workers=1. API suite (fullyParallel: false, chia sẻ cartId/addressId) thì không thể, đơn vị đúng ở đó là cả spec file cho đúng một project.

05

Recommended approach

A + B + C, in that order, each independently reviewable
✓
EN

Adopt A, then B, then C as three separate, reviewable increments. Defer D until B's artifact exists to aggregate. Adopt E only as a manually-applied tag with a tracking ticket, never automatic. Do not adopt F now.

VI

Áp dụng A, rồi B, rồi C thành ba bước riêng biệt, mỗi bước đều xét duyệt độc lập. Hoãn D lại cho đến khi có artifact của B để gom dữ liệu. Chỉ áp dụng E dưới dạng tag gắn thủ công kèm ticket theo dõi, không bao giờ tự động. Chưa áp dụng F ở thời điểm này.

1. A is a genuine, cheap fix, worth landing on its own
EN

It closes a real asymmetry with echo/markdown-table edits only, and it establishes the baseline number that tells you whether B and C are worth building at all. If the API flaky count stays at zero, C has no work to do.

VI

Nó vá một sự bất đối xứng có thật chỉ bằng sửa echo/bảng markdown, đồng thời cho ra con số nền để biết B và C có đáng xây hay không. Nếu số flaky của API luôn bằng không, C không có gì để làm cả.

2. B converts a number into an actionable list, safely
EN

Its output format is chosen so Playwright's own --last-failed-file reader consumes it with no bespoke filtering. It changes no test behaviour, so it's safe to land and observe before building anything on top of it.

VI

Định dạng output của nó được chọn sao cho chính bộ đọc --last-failed-file của Playwright dùng được luôn, không cần lọc thêm gì. Nó không thay đổi hành vi test nào, nên an toàn để triển khai và quan sát trước khi xây thêm lên trên.

3. C answers the question that actually determines the fix
EN

The repo has both failure modes on record: UI's Firefox Juggler teardown workarounds, and the API's explicit shared-state warning. Because failure diagnostics are already captured for flaky attempts, C plus the existing attachments is a complete triage loop with no new capture machinery.

VI

Repo này đã ghi nhận cả hai kiểu lỗi: workaround teardown Firefox Juggler ở phía UI, và cảnh báo shared-state rõ ràng ở phía API. Vì thông tin chẩn đoán fail đã được bắt sẵn cho các lần chạy flaky, C cộng với các attachment đã có sẵn tạo thành một vòng triage hoàn chỉnh, không cần cơ chế bắt dữ liệu mới nào.

4. D is deferred, not rejected
EN

The obvious substrate, monocart trends, provably cannot carry per-test history, and the existing cache-key pattern already has a live bug. B's per-run artifact makes D a pure add-on later, with no rework cost from waiting.

VI

Nền tảng hiển nhiên, monocart trend, đã được chứng minh không thể mang lịch sử theo từng test, và pattern cache key hiện tại đã có bug thật. Artifact theo từng lần chạy của B khiến D chỉ là bước bổ sung sau này, chờ đợi không tốn công làm lại.

⚠
EN

Do not bundle --fail-on-flaky-tests, retry-count changes, auto-quarantine, or a third-party service into this work. Each is called out separately in the risk table below because each reverses or interacts with a decision this repo has already made deliberately.

VI

Không gộp --fail-on-flaky-tests, thay đổi số lần retry, auto-quarantine, hay dịch vụ bên thứ ba vào lần thay đổi này. Mỗi thứ được tách riêng trong bảng rủi ro bên dưới vì mỗi thứ đều đảo ngược hoặc tương tác với một quyết định mà repo này đã chủ đích đưa ra từ trước.

Single-test isolation is an inverse signal for the API suite: shared cartId/addressId means an isolated test fails for reasons unrelated to flakiness High Option C Never rerun API tests individually; rerun at spec-file granularity, scoped to the one failing project

Implementation steps

Ordered, per increment, for a future implementation agent
Increment A · API flaky parity
  1. Add a 🔁 Flaky row to the onEnd step-summary table in api.config.ts, mirroring the UI config's existing row
  2. Add a flaky-count line to the API and Misc extract steps in playwright-with-slack.yml, mirroring the existing pattern used for passed/failed/skipped
  3. Add api_flaky / misc_flaky job outputs, then a 🔁 Flaky field to the GRA and Misc Slack blocks
  4. Repeat the extract/output/Slack-field additions in api-restful-tests-with-slack.yml
Increment B · flaky ledger reporter
  1. Create src/reporters/flaky-ledger-reporter.ts implementing the Reporter interface, with named exported interfaces for the ledger's output shapes
  2. In onEnd, select tests with outcome() === 'flaky' and record test ID, title, file/line, project, attempt count and statuses, and the first error message
  3. Write flaky-ids.json in the exact {status, failedTests} shape --last-failed-file expects, plus a richer flaky-report.json for humans; mark any entry with a skipped attempt as suspect-cascade
  4. Wrap all file I/O in try/catch that logs and never rethrows
  5. Register the reporter in both playwright.config.ts and api.config.ts with distinct output directories so the two suites don't collide
  6. Confirm npm run lint passes and a full run produces byte-identical results.json/HTML report content versus a baseline run
Increment C · rerun-in-isolation, non-blocking
  1. Add a UI rerun script: single project, --workers=1, --last-failed --last-failed-file= pointed at a copy of the ledger
  2. Add an API rerun script that groups ledger entries by project and spec file, and reruns each group as a whole file against its own project, never a single test in isolation
  3. Add a non-blocking CI job, continue-on-error: true, with a hard timeout, gated to skip entirely when the ledger is empty
  4. Copy the ledger to a scratch path before invoking the rerun, since the file is a write target too
  5. Classify each rerun outcome as confirmed-flaky (failed again) or isolation-passed (suspected order-dependency), and surface the counts in the CI step summary
  6. Leave the report artifacts from this job separate from the deployed Cloudflare Pages report
Later, manual · quarantine convention
  1. Document the @flaky tag in CLAUDE.md's tag list
  2. Apply it manually to a test only after Increment C has confirmed it more than once, referencing a tracking ticket
  3. Add a non-blocking @flaky-only job so quarantined tests keep reporting instead of disappearing from the suite
