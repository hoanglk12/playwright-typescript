Schema Validation with Zod

The API suite currently checks a few fields per response and casts the rest. Zod validates the whole shape at runtime. This plan adds it as an opt-in assertion, piloted on the dummyjson suite only.

Why

Three assertion styles carry the API suite today: assertJsonPath('id', 1) checks one value, assertJson({...}) checks that a partial object is present, and response.json<ProductsListResponse>() checks nothing at all — it's a compile-time label stuck on whatever came back over the wire.

tests/api/dummyjson-products.spec.ts casts a response to ProductsListResponse and then only asserts that total > 0 and skip === 0. If dummyjson renamed products to items, or started returning total as a string, the test would keep passing. TypeScript is satisfied by the cast; nothing downstream ever checks it against the real payload.

Zod closes that gap. One call — await response.assertSchema(ProductsListSchema) — walks the full response: every field, every type, every array element, every nested object, and fails with the exact path that broke. It doesn't replace the value assertions above; it sits alongside them and catches the drift they were never designed to catch.

Where GRA is different

Why the pilot stops at dummyjson

tests/api/CLAUDE.md already documents staging behaviour that a strict schema would treat as a failure: PLA catalog queries with broken price_range data, a productSearch field missing from the staging schema entirely, __typename discriminators that return ConfigurableProduct or ConfigurableWishlistItem even for simple products, and per-brand stock levels low enough that some fields go missing outright.

None of that is a bug in the test framework — it's accepted, worked-around staging reality. A schema strict enough to be useful would turn each of those into a hard failure, multiplied across all 8 brand projects at once. dummyjson has a stable, documented public contract and no such quirks, which is why it's the pilot and GRA is a separate decision made after the pilot proves out.

Ground rules for every schema

01

z.looseObject, never z.object or z.strictObject. Unknown fields are API evolution, not a test failure.

02

safeParse, never parse. The parsed result is discarded — existing assertions keep reading the raw body untouched.

03

No z.coerce.*. Coercion hides the exact type drift a schema exists to catch.

04

No z.discriminatedUnion on GRA's __typename — the discriminator itself isn't reliable there.

Rules 1 and 2 matter beyond style: z.object().parse() strips unknown keys and returns a deep clone by default, which would silently change what a test reads back if anything downstream ever touched the parsed value instead of the original body.

Pilot steps — dummyjson only

  1. Install and confirm module resolution

    Why: the project uses NodeNext resolution against a CJS-style consumer; Zod's dual-published exports need to be proven to resolve here before any spec work starts.

    npm i -D zod@^4.4.3, then a throwaway file importing * as z from 'zod' and one z.looseObject. npm run lint must pass. If it doesn't, try the zod/v4 subpath before touching anything else.

  2. Add assertSchema() to ApiResponseWrapper

    Additive only — no existing method changes.

    Reads the already-fetched body, runs schema.safeParse(), and on failure asserts with z.prettifyError(result.error) as the message so the test report shows the exact path that broke.

  3. Add assertDataSchema() to GraphQLResponseWrapper

    Kept separate from assertNoErrors() — validating the data shape and checking for GraphQL errors stay two different checks.

    Same pattern, applied to getData() instead of the raw body.

  4. Write schemas for the four dummyjson domains

    These already have hand-written interfaces in src/api/services/dummyjson/models.ts — the schemas mirror them, they don't replace them.

    New file: src/data/api/schemas/dummyjson-schemas.ts. One schema per interface (products, carts, users, auth), all z.looseObject.

  5. Add assertSchema calls alongside existing assertions

    Nothing existing is removed — this is purely additive to each test.

    Run each affected spec individually against the misc-api project and confirm green.

  6. Prove the assertion has teeth

    A schema that never fails is providing no signal — this has to be checked once, deliberately, per domain.

    Break one field's type on purpose, re-run, confirm the failure names the exact path. Revert immediately after confirming.

  7. Run the full misc-api project and stop

    GRA is a separate decision, made after this pilot is reviewed — not an automatic next phase.

    npm run test:api:misc covers dummyjson, restful-booker, and objects-crud. Document the outcome and reassess before any GRA schema is written.

Rollback

Every change is additive: two new wrapper methods, one new schema file, added assertion lines in four specs. git revert the commit and npm uninstall zod restores the exact prior behaviour — no existing test's semantics change at any point in the pilot.
