The premise doesn't hold in this repo

Reading every subject line, the large majority are new page objects and new coverage across the 8 GRA storefronts, not selector repairs. ✅

The correct architecture already exists here

scripts/dom-inspector.mjs scores candidate locators deterministically, and .claude/agents/playwright-test-healer.md is an LLM agent that suggests a patch for a human to review at development time. This is the same shape as Playwright's own first-party Healer agent. The remaining work is closing two gaps in what's already there, not building something new.

1
Summary

The question evaluated: whether to add AI self-healing locators, a mechanism that finds a replacement automatically when a locator fails, so the test keeps running instead of going red.

The stated motivation is maintenance burden from selector churn. Measured against this repo's actual history, that burden is a small minority of the work reflected in src/pages commits. What dominates is coverage growth: new storefronts, new flows, new page objects.

Two mechanisms that a well-designed healing system would provide already exist in this repo, and they sit at the correct point in the lifecycle, development time with a human reviewing the change, rather than the dangerous one, CI runtime with an automatic substitution and no one watching. dom-inspector.mjs is a deterministic locator scorer that already encodes this project's own locator priority (role and label selectors score highest, structural selectors are penalized). playwright-test-healer.md is a dev-time LLM agent that inspects a failure and proposes a fix for review, matching Playwright's own first-party Test Agents design.

Recommendation: don't add runtime self-healing, deterministic or LLM-based, to ElementHelper, BasePage, or any CI path. Close two small gaps in the existing dev-time tooling now. Pilot Playwright's first-party toMatchAriaSnapshot() for structural resilience on one component. Reject full LLM auto-heal outright.

Options

Option A: Close gaps in existing tooling ✓ Recommended

Build nothing new. Give dom-inspector.mjs a storefront flag, and add a no-auto-commit guardrail plus an evidence requirement to the healer agent.

✓ Zero production risk · zero new deps · zero config/CI change
✗ Doesn't add a runtime capability, which is deliberate

Option C: ARIA snapshot pilot ✓ Recommended, bounded

Playwright's first-party toMatchAriaSnapshot(), currently used zero times in this repo, scoped to one stable component (main nav).

✓ No dependency, no LLM, fails loudly with a readable diff
✗ 8 storefronts means 8 snapshot variants; must be measured before wider rollout

Option B: Deterministic multi-locator fallback in ElementHelper

Store 2 or 3 strategies per element; try each in order. Sounds safe, but serves the legacy string-selector path new code is steered away from, and can't touch checkout-page.ts at all, whose 36 locator fields are regex text patterns, not selectors.

✓ No LLM, no external calls, easy to review
✗ Reintroduces the ambiguity strict mode exists to prevent; duplicates DomScanHelper

Option D: LLM diagnostic, suggestion-only

On failure, ask an LLM for a suggestion, attach it to the report, still fail the test. Safer than auto-heal, but blocked on the helper layer having no test context, and duplicates what the healer agent already does after the fact.

✓ Never masks a regression
✗ New SDK, new secret, new redact.ts work, per-failure latency across 6 CI legs

Option E: Full runtime LLM auto-heal ✗ Rejected

Dump DOM to an LLM, substitute the returned selector, keep running, optionally auto-PR. The pattern the old doc sketch illustrated, with its AI call left as a commented-out stub.

✓ (None that outweigh the risk below)
✗ One shared page object serves 8 storefronts; a heal from one brand's DOM would apply to all 8 with nothing checking the other 7
4
Recommended approach

Adopt Option A now. Pilot Option C. Defer Option D behind the test-context prerequisite in §5. Reject Option E. Don't adopt Option B as a general mechanism.

  • The measured churn doesn't justify healing infrastructure. 89 commits, overwhelmingly feature work. CLAUDE.md's own Behavioral Guidelines (§2 simplicity, §3 surgical changes) push against building for a problem the git history doesn't show.
  • The capability already exists in the correct shape: dev-time, human-reviewed, deterministic-first. A second, runtime version would be strictly worse.
  • The application makes LLM healing structurally weak. Magento PWA Studio with hashed styled-components classes means there's no stable class for an LLM to find. An LLM inspecting the same DOM a human already inspected has no better information.
  • The 8-storefront shared-page-object model is incompatible with per-run healing (see Option E above).
  • Retries already absorb transient failures (playwright.config.ts, api.config.ts both configure retries in CI). What survives retries is signal, exactly what healing would suppress.

Revisit this if a future quarter's git log on src/pages shows selector-repair commits becoming the majority, or if the application adopts stable data-testid attributes.

5
Risk assessment
⚠️

Masked regressions, and a concrete blocker

Both wait-helper.ts and element-helper.ts carry the same comment three times: // WHY: helper layer has no test context; console is the only available channel here. The helper layer can't call testInfo.attach(). A heal performed there can emit nothing to any of the five configured reporters (html, json, junit, list, monocart-reporter). A silent heal turns a hard failure into a green pass with zero signal anywhere. No healing mechanism at the helper layer is acceptable until a heal produces a report-visible artifact.

🔓

Data exposure

redact.ts exists because customer PII previously reached artifacts that deploy to public Cloudflare Pages report sites. It's a key-based denylist over JSON with no HTML-aware sanitizer. A raw HTML dump on an authenticated checkout page carries session state, form values, and internal staging hostnames, and bypasses that discipline entirely.

Rollback: Option A touches one script and one agent file, neither imported by production code: a plain revert. Option C is additive; deleting the assertions and the generated snapshot directory removes it cleanly. Options D/E would add a runtime external dependency to the UI test path, so a vendor outage becomes a test-suite failure mode; rollback means removing the dependency, the fixture, and the secret from two workflows.

6
Implementation steps

Sequenced for an implementation agent. Per CLAUDE.md, research doesn't auto-flow into implementation: this needs explicit approval via qa-orchestrator WORKFLOW-10 before any step below runs.

Phase 1: Guardrail the existing healer

  • Add a "never auto-commit" rule to playwright-test-healer.md: the agent may edit files but never runs git commit, git push, or opens a PR.
  • Require an output contract per change: old selector, new selector, DOM evidence for why the old one broke, and a dom-inspector score ≥ 0.90 for the replacement.
  • Add a cross-storefront rule: any change to a shared src/pages/ecommerce/ page object must be verified against all 8 storefronts before it's offered for review.
  • Fix the stale helper count in that file (it lists 8; BasePage composes 11).

Phase 2: Reach the storefronts with dom-inspector.mjs

  • Read src/data/ecommerce/storefronts.ts to confirm the exported shape.
  • Add --storefront <code> and --page <key> resolution, keeping --url and FRONT_SITE_URL working unchanged.
  • Add popup dismissal before probing (Vans AU's Bloomreach popup currently suppresses the visibility filter).
  • Update the script's usage docblock and the invocation examples in the healer agent file.

Phase 3: ARIA snapshot pilot

  • Pick one stable component subtree, main header navigation, not a whole page.
  • Add one toMatchAriaSnapshot() assertion for one storefront first.
  • Generate the baseline with --update-snapshots; review the generated YAML by hand.
  • Run against the remaining 7 storefronts to measure the per-brand variant cost before deciding whether to expand.

Explicitly out of scope for implementation: element-helper.ts, base-page.ts, base-test.ts, playwright.config.ts, api.config.ts, redact.ts, package.json, and any workflow file. No LLM SDK dependency. No new CI secret.

Validation
  • 0
    Gate 0: the prerequisite any future healing proposal must pass
    Seed a genuinely broken selector, run the suite, confirm the run is not green, and confirm the failure is visible in monocart-report and results.json, not only in a console line. No runtime option can pass this today.
  • 1
    Phase 1: healer guardrails
    Ask the agent to fix a known-broken test; confirm it leaves changes uncommitted. Confirm the output contract is followed. npm run lint stays clean; the diff touches only the agent file.
  • 2
    Phase 2: dom-inspector.mjs
    Run against all 8 storefront codes; record which return empty candidates. For 3 elements with known-good committed locators, confirm the tool's top-ranked candidate matches. Track wall-clock time from a SELECTOR_STALE CI failure to a verified fix, before and after.
  • 3
    Phase 3: ARIA snapshot pilot
    Alter a nav item's accessible name and confirm the assertion fails with a readable diff. Run the pilot 5× against the same storefront to confirm stability. Run on both chromium and firefox. Count snapshot files needed for full 8-storefront coverage before expanding.
  • ✓
    The paired acceptance criterion for any future healing proposal
    Median time-to-fix for selector-stale failures must decrease, and in a seeded-defect trial (N genuine application regressions introduced on purpose) the suite must still fail on all N, with zero silent heals. A mechanism that improves the first number while degrading the second is a net negative for a QA framework.
