Custom Fixtures That Attach Failure Context Automatically

Section 05 of the internal study guide (docs/study/advanced-api-handle.html) proposes a fixture that attaches request status only when a test fails. This report checks that proposal against what the framework already does, verifies the underlying Playwright 1.61 fixture and testInfo semantics against the installed source rather than assuming the study got them right, and lays out what, if anything, is worth building.

Summary

What section 05 proposes, and what this framework already has
EN

The study document proposes a third attachment mechanism for this framework: a fixture called smartRequest that wraps the built-in request fixture, lets the test run, then checks testInfo.status !== testInfo.expectedStatus at teardown and attaches a JSON blob with the status and error message, but only when the test failed.

VI

Tài liệu study đề xuất một cơ chế đính kèm thứ ba cho framework này: một fixture tên smartRequest bọc quanh fixture request có sẵn, để test chạy qua, rồi kiểm tra testInfo.status !== testInfo.expectedStatus ở bước teardown và đính kèm một blob JSON gồm status và error message, nhưng chỉ khi test đó fail.

EN

Có hai cơ chế đã bao phủ phần lớn phạm vi này, và chúng đang chạy thật trong dự án, không phải chỉ là đề xuất:

EN

Top-line conclusion: the proposed smartRequest fixture should not be adopted as written. It is inert in this repo, and on the API side it solves a problem that is already solved twice over.

VI

Kết luận chính: không nên áp dụng fixture smartRequest đúng như đề xuất. Nó không có tác dụng gì trong repo này, và ở phía API nó giải quyết một vấn đề đã được giải quyết sẵn, thậm chí hai lần.

Three findings behind that conclusion
Finding 1 · The fixture captures nothing new
EN

await use(request) hands the test the same APIRequestContext object back. APIRequestContext has no request or response events, so the fixture cannot observe traffic the way the study implies. Its attachment body is just status plus the first error message, both of which every reporter in this repo already shows (html, json, junit, list, monocart). Net new information is zero, which is the opposite of the section's own stated motivation.

VI

await use(request) trả về đúng đối tượng APIRequestContext ban đầu cho test. APIRequestContext không có event nào cho request hay response, nên fixture không thể quan sát traffic theo cách mà study document ngụ ý. Nội dung đính kèm chỉ là status và error message đầu tiên, cả hai đều đã hiển thị sẵn trên mọi reporter của repo (html, json, junit, list, monocart). Thông tin mới thêm vào bằng không, ngược hẳn với chính mục đích mà mục 05 nêu ra.

Finding 2 · It never touches the code paths this repo uses
EN

No API spec in this repo consumes Playwright's built-in request fixture. ApiClient.init() (src/api/ApiClient.ts:75) builds its own context through request.newContext(), and every fixture in ApiTest.ts hands the test one of those clients instead. A fixture that wraps request sits outside every call path in the suite.

VI

Không có spec API nào trong repo dùng fixture request có sẵn của Playwright. ApiClient.init() (src/api/ApiClient.ts:75) tự dựng context riêng qua request.newContext(), và mọi fixture trong ApiTest.ts đều đưa cho test một trong các client đó thay vì request gốc. Một fixture bọc quanh request nằm ngoài toàn bộ đường gọi thực tế của suite.

Finding 3 · The real gap is on the UI side, and it is narrower than section 05 suggests
EN

Playwright 1.61 already writes an error-context.md ARIA snapshot on any failing test with a browser context, and screenshots and video are already configured for failures. What is missing on a first-attempt UI failure is browser console errors, uncaught page errors, and failed network requests. Trace would carry those, but TRACE_MODE defaults to on-first-retry (src/config/environment.ts:114), so local runs (retries: 0) and the first CI attempt get no trace at all.

VI

Playwright 1.61 đã tự ghi ARIA snapshot error-context.md cho mọi test fail có browser context, cùng với screenshot và video khi fail. Thứ còn thiếu ở lần fail đầu tiên trên UI là console error của browser, page error chưa bắt, và các request bị fail. Trace sẽ ghi lại những thứ đó, nhưng TRACE_MODE mặc định là on-first-retry (src/config/environment.ts:114), nên chạy local (retries: 0) và lần chạy đầu trên CI hoàn toàn không có trace.

Playwright 1.61.1 semantics, verified against installed source
EN

Every claim below was checked against node_modules/playwright/lib, not assumed from the study text or from general Playwright knowledge.

VI

Mọi khẳng định dưới đây đều được đối chiếu trực tiếp với node_modules/playwright/lib, không suy đoán từ nội dung study document hay từ kiến thức Playwright chung chung.

ClaimVerdictEvidence
testInfo.status is final by the time a test-scoped fixture tears down Confirmed, with a caveat Teardown runs in the "After Hooks" step, after the test body and every afterEach. A fixture that tears down later can still fail and flip status after yours already ran.
testInfo.error?.message is populated at that point Confirmed The error getter returns errors[0]; _failWithError appends to errors during the test body.
Soft assertions are visible to the gate before teardown Confirmed, brief's worry does not hold A failed soft-assert step calls _failWithError immediately, which sets status = 'failed' right away, not at end of test.
status !== expectedStatus is the correct guard Partially: the study's version is subtly wrong Playwright's own predicate is status !== 'skipped' && status !== expectedStatus. The bare comparison can fire on skipped tests.
Behaviour with test.fail() / test.skip() Handled, one blind spot Runtime modifiers mutate expectedStatus. A test.fail() test that fails as expected gets no attachment, correct but unhelpful for debugging. An unexpectedly-passing test.fail() test does attach.
Fixture teardown order is deterministic Confirmed Teardown is the strict reverse of setup order. Auto fixtures are set up first, so they tear down last, after the ecommerce fixtures' Firefox about:blank navigation.
Teardown gets its own time budget after a timeout Confirmed The After Hooks phase gets a fresh slot sized to the larger of the project and test timeouts, so an attachment on a timed-out test still gets written.
Retries duplicate attachments Per result, not per test Each retry is its own TestResult with its own attachments. With retries: 2 in CI, a persistently failing test can end up with three copies.
API calls are traceable if tracing were enabled Confirmed ArtifactsRecorder.didCreateRequestContext() starts a trace chunk for every APIRequestContext, including ones from request.newContext(). Neither config sets a trace option today.
The report-size fact that reframes the question
EN

monocart inlines body attachments straight into index.json as a content string, with no size cap. That is confirmed two ways: by reading the local monocart-api-report/index.json directly, and from the reporter source (visitor.js, saveAttachmentBodyHandler()). If the content type is text-like, which covers plain text and JSON, the body goes straight into item.content with no threshold check.

VI

monocart nhúng thẳng nội dung attachment vào index.json dưới dạng chuỗi content, không giới hạn kích thước. Điều này được xác nhận theo hai cách: đọc trực tiếp monocart-api-report/index.json ở local, và từ source của reporter (visitor.js, saveAttachmentBodyHandler()). Nếu content type dạng văn bản (bao gồm plain text và JSON), nội dung được gán thẳng vào item.content, không có bước kiểm tra ngưỡng nào cả.

⚠
EN

The CI pipeline runs a find ... -size +25M -delete sweep before every Cloudflare Pages deploy. If attachments push index.json past 25 MiB, that step deletes the entire report data file, and the deploy still proceeds because the gate only checks that index.html exists. The result is a published report with no data behind it. This is a live risk on the existing VERBOSE_LOGS-default-ON path today, independent of anything proposed here.

VI

Pipeline CI chạy bước quét find ... -size +25M -delete trước mỗi lần deploy lên Cloudflare Pages. Nếu attachment khiến index.json vượt quá 25 MiB, bước đó sẽ xóa toàn bộ file dữ liệu report, và deploy vẫn tiếp tục vì điều kiện gate chỉ kiểm tra sự tồn tại của index.html. Kết quả là một report được publish nhưng rỗng dữ liệu. Đây là rủi ro đang tồn tại thật trên đường đi VERBOSE_LOGS mặc định BẬT hiện nay, không liên quan gì đến đề xuất trong report này.

Scope

Which files change, and only under which option
EN

The affected files depend entirely on which option gets picked in section 03. None of them touch BasePage or the eleven shared helpers, except Option C, which only reaches into ConsoleHelper.

VI

Danh sách file bị ảnh hưởng phụ thuộc hoàn toàn vào phương án được chọn ở mục 03. Không phương án nào động đến BasePage hay 11 helper dùng chung, ngoại trừ Option C, và Option C cũng chỉ chạm vào đúng ConsoleHelper.

API side
  • src/api/ApiTest.ts: fixture interface and registration (Options A, B)
  • src/api/ApiClientExt.ts: attachVerboseLog() / isVerboseLoggingEnabled() (Option B only, buffer-then-flush conversion)
  • api.config.ts: only if trace is enabled (Option D); no trace key today
  • src/utils/redact.ts: reused as-is for any API payload attachment; must be extended before any new field class gets attached
UI side
  • src/config/base-test.ts: CustomFixtures interface and registration (Option C). This type declares 23 members (18 page objects plus percyHelper, softAssert, consoleHelper, makeAxeBuilder, attachTestLogs). Per CLAUDE.md this is an advisor-gated, high-impact file: every UI test loads it.
  • src/pages/helpers/console-helper.ts: ConsoleHelper already buffers console messages and is the natural home for a failure-gated attach (Option C)
  • src/config/environment.ts: traceMode default (Option D)
  • playwright.config.ts: unchanged under every option; trace is env-driven
CI and reporting
  • .github/workflows/playwright-with-slack.yml: shard artifact upload, npx monocart merge, the 25 MiB strip, and public deploys to the three Cloudflare Pages sites
  • .github/workflows/api-restful-tests-with-slack.yml: same pattern for the API suite
  • VERBOSE_LOGS is unset in every workflow and in .env.testing, so it stays ON for every CI API run, and those redacted payloads reach a public Pages site. This is the binding constraint on every option that touches attachments
03

Options

Five ways to close the gap, from adopting section 05 almost as written to doing nothing
EN

Each option below is independent. Adopting one does not require adopting another, and Options A through D are not mutually exclusive with Option E, which is the baseline they get compared against.

VI

Mỗi phương án dưới đây độc lập với nhau. Chọn một phương án không bắt buộc phải chọn thêm phương án khác, và Option A đến D đều được so sánh với Option E, phương án nền để đối chiếu.

Option A: Failure-gated auto-fixture on top of attachVerboseLog (API)
EN

Add a new auto fixture to ApiTest.ts that attaches a summary blob, status and the first error message, only when a test fails, while attachVerboseLog keeps running exactly as it does today.

VI

Thêm một auto fixture mới vào ApiTest.ts, chỉ đính kèm một blob tóm tắt gồm status và error message đầu tiên khi test fail, trong khi attachVerboseLog vẫn chạy y như hiện tại.

ProsCons
Purely additive; no behaviour change for passing testsDuplicates data already in the report unless it also buffers payloads, and buffering payloads duplicates attachVerboseLog instead
Cheap to revert, one fixture to deleteAdds a third attachment pattern to a codebase that already has two, which runs against the framework's own "simplicity first" convention
Matches the study's proposed shape, so it is defensible as a teaching artefactGrows the report on exactly the tests that already carry the largest attachments, the failing ones
NoneDoes nothing for the index.json bloat risk
Option B: Convert attachVerboseLog to buffer-then-flush-on-failure (API)
EN

Buffer the redacted payloads during the test; a teardown fixture flushes them into one attachment, only when the failure gate says the test failed. This is the only variant of the section-05 pattern that shrinks report size instead of adding to it.

VI

Đệm (buffer) các payload đã redact trong lúc test chạy; một fixture ở bước teardown gom chúng lại thành một attachment duy nhất, chỉ khi cổng kiểm tra failure xác nhận test đó fail. Đây là biến thể duy nhất của pattern mục 05 làm report nhỏ đi thay vì phình to.

ProsCons

Fewer, larger attachments merge better in monocart than many small onesLoses pass-case debugging: today a passing-but-suspicious test's payloads are inspectable, afterward they are gone
Shrinks the public-report surface, since redacted payloads for passing tests stop being published at allThe buffer must outlive individual client instances, so it needs a shared sink keyed by test ID, similar to how TestLogger already works
Redaction reuse is free, same redact.ts call, just deferredMemory cost: a long spec's payloads sit in RAM until teardown instead of streaming out per call
NoneBehaviour change for anyone currently relying on per-call attachments during triage
Option C: Failure-gated UI capture folded into ConsoleHelper
EN

Make consoleHelper an auto fixture, add listeners for page errors and failed requests alongside the console listener it already has, and attach the buffered result only when the test failed.

VI

Biến consoleHelper thành auto fixture, thêm listener bắt page error và request thất bại bên cạnh listener console đã có sẵn, và chỉ đính kèm kết quả đã buffer khi test fail.

Option D: Zero new code, change the trace policy instead
EN

Set TRACE_MODE=retain-on-failure for UI runs, or add a trace option to api.config.ts. Trace already carries console, network, DOM and source information.

VI

Đặt TRACE_MODE=retain-on-failure cho các lần chạy UI, hoặc thêm option trace vào api.config.ts. Trace vốn đã ghi lại console, network, DOM và source.

Strictly more failure context for UI than any hand-rolled attachmentTrace size: retain-on-failure on a broad UI failure can add tens of megabytes per test
Closes the first-attempt-failure gap that on-first-retry leaves openWhether path-based attachments survive the monocart merge step into the public report is unverified, so the benefit may not reach the published site at all
Reversible with one environment variableDoes not help the API suite without accepting the redaction regression

04

Recommended approach

Reject for API, adopt narrowly for UI, and separate the size-risk decision out
✓
EN

Reject the section-05 smartRequest pattern for the API suite (Option E for API). Adopt Option C for the UI suite, scoped tightly. Raise Option B with the user as a separate, explicitly flagged decision, not bundled into this change.

VI

Từ chối áp dụng pattern smartRequest của mục 05 cho phía API (chọn Option E cho API). Áp dụng Option C cho phía UI, với phạm vi giới hạn chặt chẽ. Đưa Option B ra riêng cho user quyết định, không gộp chung vào lần thay đổi này.

1. The API side needs nothing
EN

attachVerboseLog already attaches full redacted request and response payloads for every *WithWrapper call. A failure-gated fixture that only attaches status and an error message tells you less than the report already shows. Structurally, smartRequest wraps a fixture that no spec in this repo consumes.

VI

attachVerboseLog đã đính kèm đầy đủ payload request và response đã redact cho mọi cuộc gọi *WithWrapper. Một fixture chỉ đính kèm status và error message khi fail cung cấp ít thông tin hơn những gì report đã hiển thị sẵn. Về mặt cấu trúc, smartRequest bọc quanh một fixture mà không spec nào trong repo dùng đến.

2. The UI gap is real, and ConsoleHelper already has the shape to fill it
EN

error-context.md, screenshots and video already cover the visual and structural side of a UI failure. Console errors, page errors and failed requests are the missing signal, and that is exactly what ConsoleHelper was built to collect.

VI

error-context.md, screenshot và video đã bao phủ phần hình ảnh và cấu trúc của một lần UI fail. Console error, page error và request thất bại là tín hiệu còn thiếu, và đó chính xác là thứ ConsoleHelper được dựng ra để thu thập.

3. Zero current usage of consoleHelper is the deciding evidence
EN

It shows both halves of the argument at once: the machinery already exists, and opt-in has not been a viable way to ship it in this repo. Making it auto and gating it on failure is what turns the capability into something that actually runs.

VI

Điều này chứng minh cả hai vế cùng lúc: cơ chế đã có sẵn, và kiểu opt-in không phải cách khả thi để đưa nó vào sử dụng trong repo này. Biến nó thành auto và chỉ kích hoạt khi fail mới là cách khiến khả năng này thực sự được chạy.

4. Option B is genuinely valuable, but it is not an implementation-level call
EN

It reverses a decision CLAUDE.md records as deliberate and accepted, and it trades away visibility into passing tests, even though it is the only option that would shrink the index.json risk. That trade belongs to the user, decided on its own, not folded into a UI change.

VI

Nó đảo ngược một quyết định mà CLAUDE.md ghi nhận là chủ đích và đã chấp nhận rủi ro, đồng thời đánh đổi khả năng quan sát các test đang pass, dù đây là phương án duy nhất giúp giảm rủi ro index.json. Đánh đổi đó thuộc quyền quyết định của user, cần được xét riêng, không gộp vào thay đổi phía UI.

⚠
EN

Do not adopt Option D for the API suite while reports stay public; traces bypass redact.ts entirely. Option D for UI (TRACE_MODE=retain-on-failure) is a reasonable low-cost complement to Option C, but should be decided separately, on artifact-size grounds.

VI

Không áp dụng Option D cho phía API khi report vẫn công khai; trace bỏ qua hoàn toàn redact.ts. Option D cho UI (TRACE_MODE=retain-on-failure) là một lựa chọn bổ sung hợp lý, chi phí thấp cho Option C, nhưng nên được quyết định riêng, dựa trên yếu tố kích thước artifact.

05

Risk assessment

What could break, and how each option is rolled back
EN

Two risks below already exist in the codebase today, independent of any option here; the rest apply only to the option named in the "applies to" column.

VI

Hai rủi ro đầu tiên dưới đây đã tồn tại sẵn trong codebase hiện tại, không liên quan đến phương án nào ở đây cả; các rủi ro còn lại chỉ áp dụng cho phương án được ghi ở cột "áp dụng cho".

EN

Rollback plan. Option C is one fixture-option change (drop auto: true) plus deleting the teardown branch in ConsoleHelper; no test files change, so rollback is a single-commit revert with no downstream edits. Option B is a larger revert, touching ApiClientExt internals plus a new fixture, but it stays behaviourally isolated behind isVerboseLoggingEnabled().

VI

Kế hoạch rollback. Option C chỉ là một thay đổi ở option của fixture (bỏ auto: true) cộng với xóa nhánh teardown trong ConsoleHelper; không file test nào thay đổi, nên rollback chỉ cần revert một commit, không kéo theo chỉnh sửa nào khác. Option B là một revert lớn hơn, động vào nội bộ ApiClientExt và một fixture mới, nhưng vẫn được cô lập về hành vi phía sau isVerboseLoggingEnabled().

06

Implementation steps

Ordered for Option C, the recommendation, and only if the user approves
EN

None of these steps run automatically. They are here for a future implementation pass, after the user signs off on this report.

VI

Không bước nào dưới đây được thực hiện tự động. Chúng chỉ dùng cho lần triển khai sau này, sau khi user đồng ý với report này.

  1. Extend src/utils/redact.ts first. Confirm redactSensitiveText() covers the value classes that appear in browser console output and request URLs; add any missing pattern before any attachment code lands.
  2. In src/pages/helpers/console-helper.ts, add page.on('pageerror', ...) and page.on('requestfailed', ...) listeners inside attach(), buffering into the existing messages array or a sibling array with a distinct type tag. Buffer only, no page reads.
  3. Add a method such as buildFailureReport(): string that renders the buffer as plain text and passes it through redactSensitiveText(). Return an empty string when the buffer is empty so nothing attaches for a clean failure.
  4. In src/config/base-test.ts, convert the consoleHelper fixture to the auto-fixture tuple form. In the teardown branch: gate on testInfo.status !== 'skipped' && testInfo.status !== testInfo.expectedStatus; attach the redacted buffer as console-failure-context.log with content type text/plain; wrap the branch in a try/catch that swallows, following the attachVerboseLog precedent; never touch page in this branch.

Validation

What a report should look like before and after, and how to check it
Before: baseline to capture first
  • Passing UI test: attachments are test-steps.log only
  • Failing UI test (first attempt, local, retries: 0): test-steps.log, screenshot, video, the error-context ARIA snapshot. No console output, no failed-request list, no trace
  • Passing API test: test-steps.log plus one api-verbose-METHOD-timestamp.json per *WithWrapper call
After: expected once Option C lands
  • Passing UI test: attachments unchanged, test-steps.log only. This is the key regression check: zero new attachments on green runs
  • Failing UI test: the same set as before, plus exactly one console-failure-context.log containing console errors, page errors and failed requests, with emails, JWTs, card numbers and secret query params replaced by redaction markers
  • Failing UI test with an empty console buffer: no new attachment, the empty-buffer short-circuit
  • API reports: byte-identical to before; no API code path touched
How to verify
  1. Write a throwaway spec with one passing and one deliberately failing UI test. Run npm run test:simple and inspect monocart-report/index.json for the attachment lists above.
  2. Soft-assertion case: a test whose only failure is a softAssert.* call must still produce the attachment, confirming the _failWithError status-mutation finding holds in practice.
  3. Skip case: a test.skip()-ed test must produce no attachment.
  4. Redaction case: emit a console error containing a fake JWT and an email from a page under test, and confirm both are replaced in the attachment.
  5. Firefox case: run the failing test on the firefox project against an ecommerce fixture, and confirm the attachment is still produced and non-empty, proving the buffer-not-live-read rule held across that fixture's about:blank teardown.
  6. Size check: compare monocart-report/index.json before and after on a full run; growth should stay bounded to a few kilobytes times the failing-test count.
  7. Delete the throwaway spec.
