Summary

What "harness" means here. A non-interactive runner that starts an LLM agent with:

  • a fixed task
  • an explicit tool allowlist and denylist
  • a pinned permission mode
  • turn and budget caps
  • a JSON output schema
  • deterministic pre- and post-processing

That lets it run from a script or from CI with nobody at the keyboard. Today every agent in this repo runs only inside interactive Claude Code sessions on one Windows machine.

Bottom line

  • Worth doing, but narrowly: a read-only failure-triage harness.
    • Build it as a local script first, then run it in CI only when a test workflow fails.
    • It reuses the devops-cicd-specialist 8-category taxonomy.
    • Estimated cost is $0.15 to $0.75 per run on Sonnet 5.5.
    • It touches no framework code: no changes to playwright.config.ts, api.config.ts, base-test.ts or any helper.
  • Two non-code decisions block it.
    • An org-sanctioned model credential (Anthropic API, Bedrock or Vertex).
    • Written approval to send redacted staging failure data to that provider.
    • Neither is confirmed today.
  • Not now: write-capable agents in CI (healer, generator or architect opening PRs). They depend on five per-machine tools that aren't in the repo, and nobody has measured how often they actually fix things.
  • Unsuitable: AI running inside the tests (Stagehand, Midscene, ZeroStep, auto-playwright). This confirms the 2026-07-25 rejection again.
  • Option 4 (refresh init-agents): don't run it in place. It overwrites .mcp.json, which drops lightrag, and it overwrites the customised agents. The drift that matters is in installed dependencies, not in the prompt text.
  • Option 5 (eval harness): build it locally, alongside Phase 1, as the gate before anything moves to CI.

Two facts change the risk picture

  1. The GitHub repo is public, on a personal account. Anything a CI harness writes to run logs or $GITHUB_STEP_SUMMARY is public.
  2. Failure reports are already deployed to public Cloudflare Pages sites. redact.ts says so itself.

So the new exposure isn't that failure data leaves the runner; it already does. The new exposure is:

  • (a) unredacted material reaching a model provider: traces, screenshots, video, error-context.md, .auth/, .env*
  • (b) model output putting data back out in public places

Options

How each option is placed:

  • Where it runs: interactive local, scripted local, or CI.
  • What it may do: read-only, or write.

Option 1: Headless Claude Code (claude -p or anthropics/claude-code-action)

Placement. Scripted local or CI; read-only or write. Recommended slice: CI, read-only, raw CLI with --bare.

Verified capabilities

  • Versions: Claude Code CLI 2.1.309 (npm, needs Node ≥22.0.0). anthropics/claude-code-action latest is v1.0.259 (2026-10-22), used as @v1.
  • Headless flags:
    • -p
    • --output-format json|stream-json
    • --json-schema (result arrives in structured_output)
    • --allowedTools (auto-approves; does not restrict on its own)
    • --disallowedTools
    • --permission-mode default|acceptEdits|plan|dontAsk|auto|bypassPermissions
    • --permission-prompts none (v2.1.259+)
    • --max-turns
    • --max-budget-usd
    • --settings, --mcp-config, --agents, --append-system-prompt-file
  • Since v2.1.302, -p runs with no mode set start in Manual.
  • --bare skips hooks, skills, commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md. The docs call it "the recommended mode for scripted and SDK calls" and say it "will become the default for -p in a future release".
    • Without --bare, -p runs the project's .claude/settings.json hooks and connects .mcp.json servers, with no trust dialog.
    • Bare mode never reads OAuth or keychain credentials. It needs ANTHROPIC_API_KEY or Bedrock, Vertex or Foundry credentials.
  • In dontAsk, calls covered by permissions.allow rules still run. A non-bare run in this repo therefore inherits Bash(npx playwright test *) (a staging test run) and Bash(gh api *) (arbitrary GitHub API writes).
  • Action specifics:
    • On PRs it restores .claude/, .mcp.json, CLAUDE.md and .husky/ from the base branch. A raw CLI step does not.
    • It checks that issue or PR triggers come from users with write access, and rejects bots.
    • It makes a best-effort scrub of secrets from subprocess environments.
    • It commits to a new branch and does not open PRs automatically for @claude mentions.
    • The official Claude GitHub App's permission set is broad (Actions, Contents, Workflows and Repository hooks all read/write) and can only be accepted as a whole. A custom app or a job-scoped github_token is the narrower alternative.
    • Bedrock, Vertex and Foundry are supported via OIDC.
  • "Reusing the existing agents" works only in part. Bare mode doesn't load .claude/agents; they must be passed with --agents. Their tools: lines name MCP servers that won't exist in CI, and two of them hold write tools (see Current state).
Pros Cons
No new package dependency. The CLI is installed only in the CI job CLI churn: several behavioural changes in recent minor versions (2.1.286 bare limits, 2.1.302 default mode). The version must be pinned
One flag set covers budget, turn cap, schema output, permission mode and deny rules Non-bare runs inherit risky allow rules and hooks; bare runs lose CLAUDE.md, so context must be fed explicitly
--bare gives the same result on every machine and ignores hooks or plugins from ~/.claude Agent prompts must be distilled for headless use: they tell the agent to call gh, GitHub MCP and advisor
The Action protects .claude/ from PR-head tampering and has a ready-made PR-review flow PR review has almost no value here (3 PR merges in 445 commits)
Standard GitHub-hosted runners are free for public repos Output in a public repo's logs or step summary is public

Cost (rough, Sonnet 5.5 at $2 input / $10 output / $2.50 5-minute cache write / $0.10 cache read per MTok)

  • Read-only triage: about 8-15 turns, context growing to 60-90k tokens and mostly cache reads, 3-10k output tokens. About $0.15-$0.75 per run; cap with --max-budget-usd 1.
  • Opus 5.5 ($4 / $20) roughly doubles that.
  • About 27 pushes a month (82 commits in 90 days) across the UI and API workflows, at an unknown failure rate, comes to about $8-$32 a month at the cap.
  • PR review with the Opus reviewer: its prompt is about 9k tokens plus CLAUDE.md at about 13k, so $0.50-$2.50 per PR.
  • CI minutes: free (public repo, standard runners).

Fit with prior decisions

  • Clears the Pi bar only if the permission mode, deny rules and budget are pinned. It departs from the "never in CI" position; the case for doing so rests on read-only access plus the input allowlist described under Risk assessment.

Option 2: Claude Agent SDK scripted harness (TypeScript)

Placement. Scripted local or CI; read-only or write. Recommended slice: deferred. Adopt it when the eval harness (Option 5) grows to cover write-capable agents.

Verified capabilities

  • Package @anthropic-ai/claude-agent-sdk 0.3.309 (published 2026-10-22), Node ≥18.
  • License "SEE LICENSE IN README.md": Anthropic terms, not an OSI license.
  • It bundles a native Claude Code binary as an optional platform dependency.
  • query() options:
    • allowedTools, and disallowedTools (scoped denies apply even in bypassPermissions)
    • permissionMode (default, acceptEdits, bypassPermissions, plan, dontAsk, auto)
    • canUseTool
    • programmatic hooks (these also fire inside subagents)
    • maxTurns, maxBudgetUsd
    • outputFormat: { type: 'json_schema' }
    • agents, mcpServers, strictMcpConfig, settingSources
  • Result messages carry total_cost_usd, num_turns, usage, permission_denials and structured_output. Error subtypes are error_max_turns, error_max_budget_usd, error_during_execution and error_max_structured_output_retries.
  • Loading behaviour
    • Omitting settingSources loads user, project and local settings: CLAUDE.md, .claude/settings.json hooks, .claude/agents, commands and skills.
    • [] disables all of that.
    • ~/.claude.json and auto memory (~/.claude/projects/<project>/memory/) are read regardless. Disable auto memory with CLAUDE_CODE_DISABLE_AUTO_MEMORY=1.
Pros Cons
In-process canUseTool and PreToolUse callbacks can enforce file-path rules on what the agent reads and log every denial New dependency with a non-OSI license and 0.x release churn; both are vendor-review items
Typed results; cost and turn capture without parsing CLI JSON Scripts aren't type-checked by npm run lint without a tsconfig change; there is no tsx/ts-node in the repo
Works the same way locally and in CI; a natural base for Option 5 The default settingSources silently pulls in this repo's hooks and the user's plugins. Every call must pass []
For read-only triage it adds almost nothing over claude -p --bare

Cost: same token costs as Option 1. Effort is higher: dependency, tsconfig, a runner and tests.

Fit: neutral. It is the right vehicle once the eval harness covers the healer.

Option 3: AI inside tests (Stagehand, Midscene.js, ZeroStep, auto-playwright)

Placement. Runs inside every test execution, locally and in CI. It is effectively write-at-runtime: locators or actions get decided by a model during the run, with no review.

Verified facts

  • @browserbasehq/stagehand is 4.3.0, MIT, published 2026-10-23. The documented Playwright integration has Stagehand own the browser while Playwright attaches via chromium.connectOverCDP, then calls act and extract with a model key.
  • @midscene/web is 1.16.5, MIT, published 2026-10-22, with peer @playwright/test ^1.45. It plugs in through PlaywrightAiFixture via test.extend, exposes aiTap, aiQuery and aiAssert, takes its model from MIDSCENE_MODEL_* env vars, works from screenshots, and has a "Cache AI plans & DOM locators" page.
  • @zerostep/playwright 0.1.5 was last published 2023-12-08. auto-playwright 1.16.1 was last published 2025-05-01. Both look unmaintained.
Pros Cons
Natural-language steps are quick to write for exploratory flows Bypasses the POM and the CLAUDE.md locator rules (private readonly fields, semantic locators, no hierarchical selectors) entirely
Midscene has a caching layer Nondeterministic by design, which undermines a QA framework's reason to exist
Egress on every run, not just failures: DOM or screenshots of staging pages for 526 UI tests on 2 browsers on every push
Cost scales with tests × steps × runs
One shared page object serves 8 storefronts; a runtime heal from one brand's DOM is applied to all 8 with no cross-brand check (the July report's own rejection reason)
Requires a base-test.ts fixture (high impact)
Stagehand's CDP integration (my inference) doesn't cover the Firefox project

Cost: unbounded in practice. It is per-step model calls across the whole suite.

Fit: directly contradicts the 2026-07-25 decision. Nothing has changed since then that would reopen it.

Verdict: unsuitable

Option 4: Playwright native test agents (npx playwright init-agents)

Placement. Interactive local (already adopted); write.

Verified drift. The repo's three agents no longer resemble the 1.61.1 templates.

  • Upstream 1.61.1 templates
    • The healer drives the MCP tools test_run, test_debug, browser_snapshot and browser_generate_locator.
    • The healer is told to "continue this process until the test runs successfully": no bound. It may also call test.fixme() whenever it judges the test correct.
    • The planner's tool browser_run_code was renamed browser_run_code_unsafe, and browser_network_request was added.
  • Repo versions
    • Use Bash with --debug=cli and the global playwright-cli, plus scripts/dom-inspector.mjs.
    • Keep only the verify_* and wait_for MCP tools.
    • Add the framework rules, the CLAUDE.md §4 loop contract and the cross-storefront output contract.
  • tests/seed.spec.ts is the generated default and imports from @playwright/test, which breaks the repo's import rule.
Pros Cons
A refresh would pick up the two upstream tool-name changes and, with --prompts, four prompt templates Running it in place overwrites the customised agents (losing the loop contract, framework rules and cross-storefront contract) and .mcp.json (dropping lightrag)
Shows what upstream now considers baseline The renamed tools aren't used by the repo's agents anyway; the prompt templates overlap /write-tests and /fix-test
It doesn't fix the real gap: the MCP server is user-scope and Windows-only, playwright-cli is global, and --debug=cli implies headed mode (CI would need xvfb)

Cost: none in tokens. A few minutes for a scratch-directory diff.

Fit: neutral.

Verdict: don't refresh in place. If wanted, run it in a scratch copy and hand-port anything useful. The worthwhile work is a list of what each agent needs installed (part of Phase 0).

Option 5: Agent eval harness (golden-task regression)

Placement. Scripted local, read-only towards the repo. It runs agents inside a disposable work copy to measure them.

Basis

  • The 2026-10-01 research (Option B, phased, local-first) and the LangSmith decision ("Option A, local JSONL") both point local-first.
  • scripts/eval-lightrag.mjs is a ready methodology template: golden set, saved runs, --rescore, --compare with McNemar, Wilson intervals.

Candidate golden tasks, easiest first

  • Triage classification. Labelled historical results.json failures; metric is category agreement.
  • Reviewer seeded defects. Diffs that plant known violations (inline locator, @playwright/test import, magic timeout, waitForTimeout, hierarchical selector); metrics are precision and recall.
  • Healer seeded breakages. Done in a git worktree; metrics are fix rate, convention compliance via npm run lint plus the reviewer, and loop-contract adherence. Healer tasks against live staging can't be repeated reliably. A stable target (recorded or static pages) is an open design problem.
Pros Cons
Turns "should agents run in CI?" into a measured decision Needs the same credential and billing approval as everything else; that is what blocked it on 2026-10-01
Local-first, controlled inputs, low egress Golden sets need human labelling effort
Reuses an existing, proven eval methodology Repeated runs are needed (nondeterminism), which multiplies cost
Gives a fix-rate baseline before any write-capable automation

Cost: about $10-$60 per full eval run (for example 25 triage items × ~$0.40 × 2 repeats ≈ $20; 15 reviewer items × ~$1.50 ≈ $22).

Fit: consistent with every prior decision. Recommended, scoped to triage first.

What a write-capable path would require (deferred; included because the brief asks)

Loop contract (CLAUDE.md §4), headless version

  • Bound: 3 fix-then-verify cycles per failing test, plus whole-run --max-turns and --max-budget-usd.
  • Convergence check: computed by the harness, not the model. Compare the failure signature (Step 0b type + failing step + locator/assertion) taken from results.json across iterations.
  • Carried state: a JSON state file in the job workspace, keyed by test ID: iteration, previous signature, change made.
  • Stop action: the advisor() replacement. Write the per-iteration log as an artifact, exit non-zero, and open or update an issue or draft-PR comment labelled for a human. Never test.fixme().
    • The advisor is available in -p and the SDK (v2.1.260+), but only on the direct Anthropic API: not Bedrock, Vertex or Foundry.
    • It is also off when DISABLE_TELEMETRY or CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC is set, which are exactly the variables you'd set to harden CI.
    • So the stop action can't depend on it.

/code-simplifier gate (§7)

  • Install code-simplifier@claude-plugins-official in CI (Action plugin_marketplaces/plugins, or --plugin-dir).
  • Pass the exact file list the agent reports.
  • Keep the snapshot-then-rollback-if-npm run lint-fails behaviour from .claude/commands/code-simplifier.md.
  • Fail open.
  • Read-only phases touch no .ts, so the gate doesn't apply to them.

Approval gate

  • Output must be a draft PR and never a push to main.
  • PRs created with the default GITHUB_TOKEN don't trigger CI, so an app token is needed.
  • Branch protection on main is unverified.
  • bitbucket-mirror.yml force-pushes main to the Bitbucket mirror on every push, so anything merged propagates.

Still unavailable in the repo or on CI runners

  • playwright-test MCP: only a Windows command exists.
  • @playwright/cli: global install.
  • xvfb for --debug=cli.
  • Staging credentials for dom-inspector.mjs and the 8-brand cross-storefront check.
  • codebase-memory-mcp.

Recommended approach

Read-only before write. Local before CI. Each gate is a concrete artifact or decision.

  1. Phase 0: prerequisites, no model calls.
    • User decisions: credential and egress approval (see Open questions).
    • Then build the deterministic triage bundle builder (allowlist, fails closed) and the harness config (prompt, schema, deny-rule settings).
    • Optionally, a short provisioning list explaining why write-capable CI is deferred.
    • Gate to Phase 1: credential approved in writing and the bundle builder passes the planted-secret test (see Validation).
  2. Phase 1: scripted local, read-only triage using claude --bare -p from an npm script, plus a minimal Option 5 triage eval run alongside it.
    • Gate to Phase 2: agreement at or above a user-chosen threshold on at least 20 labelled past failures, across at least 2 repeat runs; zero permission escapes in the negative tests; median cost under the cap.
  3. Phase 2: CI read-only triage on workflow_run failure (same-repo runs only) and workflow_dispatch. Output goes to the step summary, which is treated as public, and an artifact.
    • Gate to anything further: about 4 weeks of runs with no redaction-scan hits, cost inside budget, and the user judging the briefings useful.
  4. Deferred: write-capable CI (healer → draft PR). Revisit only after the eval harness measures a healer fix rate on seeded breakages and the dependencies above are provisioned.
  5. Not recommended now: a PR-review job. PRs are almost never used. Revisit if the workflow moves to PRs.
  6. Option 4: no in-place refresh. A scratch diff is optional.
  7. Unsuitable: Option 3.

Why the CLI and not the SDK for Phases 1-2. claude -p --bare already gives budget and turn caps, schema output, a pinned permission mode, deny rules via --settings, and isolation from hooks and plugins. It needs no package.json dependency and no tsconfig change. The SDK becomes worth it when evals need in-process hooks or canUseTool, which means the healer.

How this relates to the July report. The triage harness is the after-the-fact, out-of-process form of the deferred "Option D: LLM diagnostic, suggestion-only". Its blocker was that "the helper layer has no test context". That doesn't apply here, because the harness reads the failure-context attachments those fixtures now produce, after the run, and never changes a test result.

Risk assessment

1. Egress (highest priority)

Baseline today

  • Redacted API, console and step logs, plus failure videos (and probably traces and screenshots), already go to public Cloudflare Pages.
  • The repo and its run logs are public.

What must be true before any artifact leaves the runner

  1. A sanctioned credential, and written egress approval naming the data classes:
    • redacted staging failure messages
    • redacted API, console and step logs
    • public source code
  2. Only this allowlist is sent:
    • failures.json, built from results.json with error text truncated to about 2,000 characters and passed through redactSensitiveText
    • test-steps.log, api-verbose-failure-context.json, console-failure-context.log (all already redacted at source; redact again as a safety layer)
    • tracked source files (already public)
  3. Never sent: trace.zip, screenshots, video, error-context.md (an unredacted page snapshot), HTML or monocart reports, raw results.json, stdout logs, .auth/ storage states, .env*, tests/manual/, .remember/, .claude/.state/.
  4. The bundle builder fails closed:
    • any non-allowlisted file present → exit 1
    • any JWT, email or card-number hit after redaction → exit 1
    • it writes a manifest of what was included and what was excluded
  5. The harness workdir contains only tracked files plus the bundle: git archive HEAD locally; in CI, a separate job with no staging secrets that downloads only the bundle artifact. Deny rules are a second layer.
  6. Model output is treated as public. Schema fields are length-capped, the model is told never to quote payload values, and every string is redacted again before it is written anywhere. A CI step fails the job if any redaction pattern matches the summary.
  7. Credential terms:
    • Do not use a personal CLAUDE_CODE_OAUTH_TOKEN. Consumer plans have a training opt-in and 30-day or 5-year retention.
    • Commercial API, Team or Enterprise: no training, 30-day standard retention; ZDR only by Enterprise arrangement.
    • Bedrock or Vertex keep data in your cloud account, but there is no advisor.
    • ShopAIKey's terms are unknown. It should not be assumed sanctioned for CI.

Known redaction gaps. redact.ts matches no order numbers, cart IDs, IP addresses, or personal names in free text. Those can appear in assertion messages ("Expected: …").

3. Breaking changes and vendor

  • CLI churn: v2.1.286 tightened bare mode, v2.1.302 changed the -p default mode, and bare is slated to become the -p default. Pin the CLI version in CI, and have the runner refuse anything older than 2.1.302.
  • The SDK is pre-1.0 with a non-OSI license.
  • claude-code-action releases often (v1.0.258 and v1.0.259 came out the same day). Pin to a commit SHA if it is ever used.
  • Prompt duplication: the harness prompt copies the devops-cicd-specialist taxonomy, which already appears again in /check-ci. It needs a mirror note, the same convention as the .bitbucket.js copies.

4. Security (other than egress)

  • Prompt injection: staging page text and API errors flow into the bundle.
    • The read-only harness has no Bash, write, network or GitHub-write tools, so injection can at worst distort the summary.
    • Restrict to same-repo upstream runs, because workflow_run executes with base-repo secrets.
    • Never check out an untrusted head SHA into the workspace root (Action security doc).
  • Cost abuse: prevented by the same-repo filter, concurrency, timeout-minutes and --max-budget-usd.

5. Rollback

  • Phases 0-1: delete scripts/agents/, the npm scripts and the .gitignore entries. No framework, test or config files are touched.
  • Phase 2:
    • Delete agent-triage.yml and the bundle-upload steps.
    • Delete the repo secret and revoke the key in the Console; deleting the secret alone leaves the key valid.
    • Artifacts expire with their retention setting (7 days).

6. Side effects

  • Phase 2 changes to the test workflows: a few seconds per failed run and one extra small artifact.
  • Pre-existing findings, outside this scope but worth recording:
    • Failure videos (and probably traces and screenshots, unredacted) are already published to public Cloudflare Pages. This is worth a separate WORKFLOW-8 security review.
    • settings.local.json holds a stale enabledMcpjsonServers entry.
    • technical-research-agent.md lists mcp__context7__get-library-docs, while the allowlist and the actual tool are mcp__context7__query-docs. query-docs wasn't even exposed in this session.
    • tests/seed.spec.ts imports from @playwright/test.
    • The Stop hook still runs the deprecated sync-memory-to-vault.mjs.
    • The project-level defaultMode: "bypassPermissions" probably does nothing in current Claude Code (per docs, for terminal sessions).

Work copy

Invocation

  --settings scripts/agents/triage/settings.json \
