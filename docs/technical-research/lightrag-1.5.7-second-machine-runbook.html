The backend server, its venv, its data, and its env file all live under .lightrag-venv/, .lightrag/, and .lightrag.env — all gitignored. Git moves code; it does not touch an already-installed Python venv or an already-running server's bind address until you restart it.

Arrives with git pull

Carried over from the 1.5.2→1.5.4 runbookRoot .env file, per machine

If this machine already went through the earlier 1.5.2→1.5.4 upgrade, a root .env with LIGHTRAG_RUNTIME_TARGET=host should already exist (lightrag-server ≥1.5.3 crashes/blocks startup without some .env file present — gitignored, so it never travels with the repo). Confirm it's still there before restarting; if this is a genuinely fresh machine that skipped that upgrade, create it now: echo LIGHTRAG_RUNTIME_TARGET=host > .env.

Per-machine steps

  1. Confirm nothing is mid-ingestion, then stop the server

    Don't upgrade the venv or touch .lightrag/ while a pipeline is running.

    curl http://localhost:9621/health netstat -ano | findstr :9621

  2. Back up the index

    File-based storage means a directory copy is a complete, restorable snapshot. Name it distinctly from any prior backup already on this machine (e.g. don't overwrite an existing .lightrag.bak-1.5.2).

    xcopy .lightrag .lightrag.bak-1.5.4 /E /I /H

  3. Check the installed version before assuming the pin file means it's upgraded

    This venv is uv-managed with no pip module inside it — pip show will fail here. Check the dist-info folder name instead.

    dir .lightrag-venv\Lib\site-packages\lightrag_hku-*.dist-info

  4. Upgrade to 1.5.7, using uv

    Plain pip install fails inside this venv — there is no pip module to invoke.

    uv pip install --python .lightrag-venv\Scripts\python.exe "lightrag-hku==1.5.7"

  5. Restart and watch the console

    Look for the version banner and any migration output — lightrag/storage_migrations.py runs automatically at storage init.

    scripts\start-rag.bat

  6. Reconnect Claude Code's MCP session

    MCP servers are discovered at startup — restart Claude Code, or run /mcp, so the updated .mcp.json (mcp<2 pin) is picked up. No install step: uvx resolves the adapter fresh each launch.

    /mcp

Validation

  • Health endpoint reports the new version, healthycurl http://localhost:9621/health → core_version: "1.5.7"
  • Server is bound to loopback only, not all interfacesnetstat -ano | findstr :9621 → 127.0.0.1:9621 LISTENING
  • Full vault sync reports everything unchanged — the decisive index-integrity checknode scripts/sync-vault-to-lightrag.mjs → 0 new, 0 updated, N unchanged
  • MCP query round-trip against a known vault notemcp__lightrag__query_document (mode: hybrid)

An unexpected non-zero "new" count on the sync check means the index did not survive the upgrade intact — the doc store lost track of existing files. Recovery: stop the server, delete .lightrag/, restart, and re-run the sync script to rebuild the index from the vault (58 notes as of this writing; costs some LLM/embedding spend, otherwise unattended).

Rollback

If validation fails, revert in four steps — state is file-based, so the backup is a full restore:

  1. Stop lightrag-server
  2. Delete .lightrag, restore .lightrag.bak-1.5.4 in its place
  3. Inside .lightrag-venv, run uv pip install --python .lightrag-venv\Scripts\python.exe "lightrag-hku==1.5.4"
  4. Restart via scripts\start-rag.bat and re-check /health

The bind-address fix and the adapter's mcp<2 pin are both plain git-tracked file changes — rolling those back, if ever needed, is an ordinary git revert, independent of the venv/index rollback above.
