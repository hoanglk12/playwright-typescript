1. Summary

What

The plan is one small harness layer (scripts/agents/harness/) plus a series of agents added in phases. Each agent runs first as a local npm script and only later as a GitHub Actions workflow. Every agent run has the following:

  • No built-in tools: tools: []. Read, Bash, Write, WebFetch and the rest are never in the model's context.
  • One in-process MCP server. Its handlers are code we write, and they are the only way data reaches the model. Allowlisting, size caps and redaction all happen inside them.
  • Isolated configuration: settingSources: [], strictMcpConfig: true, persistSession: false, permissionMode: 'dontAsk' and allowedTools: ['mcp__<agent>__*'].
  • A minimal environment. The subprocess gets an explicit, minimal env (the TypeScript option replaces process.env [V]), a throwaway CLAUDE_CONFIG_DIR and an empty temporary cwd.
  • Limits and a schema: a JSON-schema output, plus maxTurns and maxBudgetUsd.
  • Runtime checks: deterministic assertions on the SDK init message before any output is trusted.
  • Output cleaning: every output string is redacted again, mentions are neutralised, and a leak scan runs before delivery. Delivery happens in a separate job that holds the write credentials.

Why the Agent SDK and not claude -p --bare

  1. --bare cannot use a subscription token. It "does not read CLAUDE_CODE_OAUTH_TOKEN… authenticate with ANTHROPIC_API_KEY or an apiKeyHelper instead" [V authentication doc]. The prior report's design therefore can't run on a subscription login at all.
  2. Non-bare -p loads this repo's own configuration. That includes the .claude/settings.json hooks, the allow rules (Bash(npx playwright test *), Bash(gh api *)) and .mcp.json [P]. The SDK with settingSources: [] and tools: [] loads none of them, and its only data path is our code.

Bottom line

  • The design works technically on a Team-seat token from claude setup-token.
    • The SDK spawns its bundled Claude Code binary, which reads CLAUDE_CODE_OAUTH_TOKEN from the environment. That variable ranks 5th in credential precedence, below ANTHROPIC_API_KEY [V].
    • The same code also runs on a Console API key or on OIDC workload identity federation. Authentication is a configuration switch, not an architectural change.
  • Pilot with the Convention Reviewer. It sends only code that is already public, so it raises the smallest egress question.
  • Failure Triage and the Flaky-Test Analyst send redacted Accent Group staging failure data. They stay blocked until the data owner signs off.

2.3 Terms: the evidence both ways

For an internal CI harness on your own subscription

  • The authentication doc says to use setup-token "For CI pipelines, scripts, or other environments where interactive browser login isn't available". It describes CLAUDE_CODE_OAUTH_TOKEN as "Use this for CI pipelines and scripts" [V].
  • The env-vars doc calls CLAUDE_CODE_OAUTH_TOKEN an "Alternative to /login for SDK and automated environments" [V].
  • The server-managed settings doc gives a CI-job example that authenticates with a Team OAuth token [V].
  • The GitHub Actions doc accepts claude_code_oauth_token [V].
  • The legal page's prohibition targets "third-party developers [offering] Claude.ai login into their own applications" and routing "through Free, Pro, or Max plan credentials on behalf of their users" [V]. This harness serves only its owner, on the owner's repo, and is offered to nobody. That application is my reading.
  • The legal page also says "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK" [V]. It names the SDK as something subscription users run.

Against

  • The legal page: "OAuth authentication … is designed to support ordinary use of Claude Code and other native Anthropic applications" [V].
  • The legal page: "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication through Claude Console or a supported cloud provider" [V].
  • The SDK overview and quickstart: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods…" [V].
  • Consumer Terms §3 prohibit automated access "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it" [V; effective 2025-10-08]. The same terms say you "may not make your Account available to anyone else" [V], and any collaborator with write access can read repo secrets [V GitHub].
  • The SDK's own use is governed by Anthropic's Commercial Terms whatever your plan [V overview].
  • "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice" [V]. Any enforcement would land on the seat you use every day.

My reading. This use is not clearly prohibited for first-party, single-user internal automation. It is also not the path the docs recommend. The question is whether a self-written SDK program counts as "Claude Code / native Anthropic application" use.

How to resolve D1. Get a written answer from Anthropic support or sales through Away Digital's account before Phase 2. Then:

  • "API key only": switch the harness to an API key or WIF. No code change is needed.
  • "Subscription only through Anthropic's own surfaces": fall back to Option C, the Action, which Anthropic documents with claude_code_oauth_token.

2.4 Setup steps for the token

  1. Generate it in your own terminal, outside any Claude Code session.
    • Use a plain PowerShell window and run claude setup-token.
    • Never run it through an agent's Bash tool. The token would land in the model transcript and in ~/.claude/projects.
    • The token prints once and isn't saved anywhere [V].
  2. In the browser approval, choose the Away Digital organisation.
    • setup-token enforces only forceLoginMethod, so it "can mint a token in a different organization" [V].
    • Confirm the organisation in step 5.
  3. Store it for CI as an environment secret.
    • In the repo, go to Settings > Environments and create claude-agents. Set its deployment branches to main only.
    • Add the environment secret CLAUDE_CODE_OAUTH_TOKEN, through the UI or with gh secret set CLAUDE_CODE_OAUTH_TOKEN --env claude-agents (which reads from stdin).
    • Why an environment: "Any user with write access to your repository has read access to all secrets" [V], and the branch restriction narrows that.
    • Only the owner can manage environment secrets on a personal repo [V].
    • Required reviewers are optional. They would block the automatic runs.
  4. Use a second, separate token for local runs. This deliberately departs from the brief's "existing login, no secret" (see §3.5).
    • Set it only in the shell session that runs npm run agent:*.
    • Never put it in .env*; the framework loads those files.
    • Never make it a persistent user environment variable. Any Claude Code session launched from that environment would pick it up at precedence 5 [V], and its Bash tool could read it.
  5. Verify.
    • In that shell, with a temporary CLAUDE_CONFIG_DIR and a temporary working directory, run claude doctor. Read the "Managed settings (remote)" line; it needs v2.1.248 or later, and the local CLI is 2.1.309 [V doc; U output].
    • Confirm the organisation with /status in an interactive session started with the same environment [U exact row names].
    • Run the Phase 1 harness once and confirm the init message shows apiKeySource === 'none'.
  6. Rotate before expiry.
    • The token lasts one year [V]. Set a reminder at 11 months.
    • Generate a new token, update the secret, run a workflow_dispatch smoke test, then deactivate the old token.
    • Prove the old token fails: a harness call must end with authentication_failed [V error code; U whether revocation propagates].
  7. Revoke after a compromise.
    • Deactivate the token in claude.ai settings, delete the GitHub secret, and prove the token fails.
    • If it still works, ask an Away Digital Owner to act and contact Anthropic support.
    • Deleting the secret alone leaves the credential valid [V for API keys; same logic].

Variants

  • Personal plan: the same steps. First confirm model training is turned off in claude.ai privacy settings.
  • API key: use a Console key in a workspace with a spend limit, stored as the secret ANTHROPIC_API_KEY. Set AGENT_AUTH_MODE=api-key; the harness then asserts apiKeySource === 'ANTHROPIC_API_KEY'.
  • OIDC: grant id-token: write and create a Console federation rule. Set the federation environment variables [V names; U the GitHub-OIDC-to-file step].

3.5 Local-first and the configuration-directory conflict

  • The conflict. Credentials live under the configuration directory: %USERPROFILE%\.claude\.credentials.json on Windows, or under CLAUDE_CONFIG_DIR when it is set [V]. Relocating CLAUDE_CONFIG_DIR therefore hides your existing login.
  • Decision: (a) local runs also take a token from the shell. Local behaviour is then identical to CI, including config isolation and the server-managed fetch path. It costs one extra long-lived credential on your machine.
  • Rejected alternative: (b) don't relocate CLAUDE_CONFIG_DIR locally. That reads ~/.claude.json and makes local runs differ from CI.
    • It is acceptable as a fallback if you refuse a second token. strictMcpConfig and settingSources: [] still keep the MCP servers and hooks out.
    • This overrides the brief's "uses the developer's existing login, no secret". See open question 10.

8.3 Breaking changes and vendor

  • SDK churn. The SDK is 0.x with almost daily releases [V]. The bundled binary is pinned to the SDK version, and the docs advise taking patches continuously and reviewing the changelog before each minor [V]. Pin exactly; upgrade monthly through a dedicated research and review pass.
  • Cross-platform lockfile bug. npm #4828 / #8320 can drop other platforms' optional packages from a lockfile generated on Windows. #8320 reports it on npm 11.4.1 [third-party report]; local npm is 11.6.2 [V]. Generate the nested lockfile from a clean state and assert the linux-x64 entry exists. If the binary is missing, the SDK fails fast with "Claude Code not found" [V troubleshooting reference].
  • Install footprint. About 290 MB is extracted per agent job. Only agent workflows pay it, thanks to the nested package. Cache the npm cache keyed on the nested lockfile.
  • Type-stripping constraints. No paths aliases, explicit .ts extensions, import type required, no enums or parameter properties [V Node docs].
  • workflow_run constraints. It uses the workflow file from the default branch and allows at most 3 chained levels [V].
