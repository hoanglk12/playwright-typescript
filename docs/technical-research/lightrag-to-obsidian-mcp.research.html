Technical research report

Replacing LightRAG
with an Obsidian MCP server

Can this repo drop LightRAG and use an Obsidian MCP server as its memory layer, along with every script, hook, agent and doc that depends on it? Mostly yes, but an MCP server only covers the agents. The recall hook that runs on every prompt can't call an MCP server, so it needs its own fix, and that fix carries most of the value.

1 Summary

Two things use LightRAG today, and an Obsidian MCP server can replace only one of them.

ConsumerWhat it usesReplacement
The recall hook (.claude/hooks/user-prompt-submit.js), plain Node HTTP on every promptlocalhost:9621/queryOwn decisionCan't call an MCP server.
Five agentsmcp__lightrag__query_documentMCPAn Obsidian MCP server

The recall hook is where both the value and the trouble are. node scripts/eval-lightrag.mjs --recall-stats over 2026-10-02 to 2026-10-29 shows 125 prompts queried: 101 timed out at 9 s (81%) and 14 got memory injected (11%). Short prompts fared no better, with 63 of the 85 prompts under 100 characters timing out. Hybrid mode makes two LLM calls per query, so the delay is built in. The one query_document call the agent made during this research took 55.8 s.

Decisions

1 · Recall hook

In-process BM25F search in Node, with no server

On the existing golden set the prototype put the right note in the top 3 for 66 of 69 answerable questions, and in the top 5 for 67. A fresh node process starts, indexes and answers in 79 ms at p50, and prompts no longer leave the machine. Treat those numbers as an optimistic upper bound (section 3, Q7).

2 · Agents

An optional read-only filesystem MCP server

The pick is @bitbonsai/mcpvault@0.17.1, pinned in package.json and the lockfile and launched with node. The fallback is obsidian-mcp@2.0.1, which the GRA-vault project already uses but which takes more setup. Writes stay on the built-in Write and Edit tools so the vault hooks keep firing. Agents already have Grep, Read and Glob, and the vault's own memory-vault/.claude/CLAUDE.md says exact lookups don't need an MCP server. What the server adds is ranked search, frontmatter-only reads and a tag list, so skipping it (Option C) is a fair choice too.

3 · Sync

Sync goes away

There is no index to keep current. A small validator that only warns takes its place, and it already has work to do: four wikilinks point at notes that don't exist and two notes have no description.

4 · Data

No data lives only in LightRAG

All 64 indexed documents are vault notes. Three of the newest notes are missing from the live index even though the server was healthy and idle, which shows how easily sync falls behind.

5 · Eval

Reuse the golden set, retire the old harness

Reuse the golden-set code in a new eval and retire the 887-line LightRAG harness at decommission. Run one billed LightRAG eval in Phase 0, because no saved run covers the current question set.

6 · Cutover

Run both systems side by side

Cut over only once the eval scores match. Deleting .lightrag/ and .lightrag-venv/ is a separate final phase, done one machine at a time.

2.4 External facts (fetched 2026-10-29)

  • Claude Code MCP docs: ${VAR} and ${VAR:-default} expand in command, args, env, url and headers. An unset variable with no default stays as literal text and logs a warning. CLAUDE_PROJECT_DIR is set in the spawned server's environment, not in Claude Code's, so using it in args needs a default such as ${CLAUDE_PROJECT_DIR:-.}. Servers in a project .mcp.json need approval or an enabledMcpjsonServers entry. The current page has no Windows cmd /c note.
  • Claude Code permissions docs: rules are checked in the order deny, ask, allow. A deny rule on a bare tool name removes that tool from context (lines 56 and 60 of the fetched page).
  • The incumbent, a local-scope entry in ~/.claude.json for the GRA-vault project, is "command":"npx","args":["-y","obsidian-mcp","<abs path>"]. That is plain npx with no cmd /c, unpinned, in the v1 positional syntax.

3 Answers to the seven questions

Q1. Recall in the hook

The answer is (b), in-process Node search.

OptionLatencyRequiresWhat it findsVerdict
(a) Local REST API plugin, /search/simple/A local network round-trip; not measuredObsidian running, plugin 5.5.2, an API key, self-signed HTTPS on port 27124 (plain HTTP on 27123 is off by default)Obsidian's fuzzy search over filenames and snippetsRejectedRecall quietly stops working whenever Obsidian is closed, and the key is one more secret.
(b) In-process BM25F79 ms at p50, measuredNothing, or minisearch 7.2.0 (one MIT dependency, last published 2025-09-16)hit@3 66/69; facts in the injected text 52/69Recommended
(c) Drop auto-recallNoneNothingOnly what agents look up themselvesFallbackStill better than today, where 81% of queries time out and 8 of 12 injections are filler, but it gives up a measured gain.

Design for (b)

  • Query ownWords, the prompt with pasted content removed, capped at about 1000 characters.
  • Skip notifications, continuations, and prompts under about 25 characters or that look like acknowledgements.
  • Require at least two distinct terms and a top score at or above a floor that the eval re-derives. Start at the p10 value of about 8.2. It will move as the vault grows and term weights shift.
  • Inject a block labelled "Possibly relevant vault notes (keyword match)": the top three notes as path: description lines, then an excerpt from the best match, 1500 characters in total.
  • Log to the same .claude/.state/lightrag-recall-log.jsonl with mode:"bm25f". The existing --recall-stats grouping (eval-lightrag.mjs:692-697) then separates old and new rows without code changes.

Q2. What gets lost

LLM synthesis across notes

The graph and vector hybrid wrote an answer. Recall now injects excerpts instead.

Paraphrase matching

Notes that share no words with the question can be missed. Keyword search is weaker on task-style prompts, where hit@1 was 8 of 14.

Clean abstention

LightRAG declined all 4 off-topic questions. BM25 always returns something, and the floor blocks 7 of 9 unanswerable questions only by losing 5 answerable ones.

The entity graph

graph_chunk_entity_relation.graphml (2.9 MB), which nothing outside LightRAG queries.

The agent covers most of this by reading the top notes and doing the synthesis itself, with a stronger model than the gpt-4.1-mini LightRAG uses. The vault's 150 wikilinks, its descriptions (65 of 67) and tags (60 of 67), which memory-vault-curator maintains, and 00-index.md as a map do the rest. That should hold up to roughly 250 to 300 notes, when 00-index.md reaches about 70 to 80 KB, or around 20k tokens to read. The ceiling is an estimate.

If a semantic layer is wanted later, the lightest option is smart-connections-mcp@2.0.1 (npm, 2026-08-22, Node 20 or later, three versions so far). It reuses embeddings built by the Smart Connections community plugin, so it needs the Obsidian app, the vault's first community plugin and a gitignored .smart-env/. Add it only if the eval shows paraphrase misses that matter.

Q3. Which MCP server

@bitbonsai/mcpvault@0.17.1, pinned exactly and run read-only, with obsidian-mcp@2.0.1 as the fallback. Section 5.2 compares them in full.

mcpvault suits a read-only setup on two machines better. It has a server-level --read-only flag and --exclude for __parsed__. Its search_notes ranks results with BM25, and get_frontmatter and list_all_tags are cheap reads. It doesn't need .obsidian/, writes no journal into the vault and needs Node 20 or later (CI runs 22, per the setup-node lines in .github/workflows/*.yml).

Its risks: it is still 0.x and moves fast, from 0.8.2 to 0.17.1 in seven months. It was renamed without an announcement: @mauricio.wolff/mcp-obsidian stopped at 0.8.2 on 2026-03-08 while the same GitHub repo carried on as @bitbonsai/mcpvault (inferred from the repo's package.json). It installs 69 packages, and nobody has tested it on Windows yet.

obsidian-mcp, the incumbent, installs 5 packages and has a stable 2.x. But it needs .obsidian/ in the vault root (verified: VAULT_NOT_INITIALIZED on a copy without one) and an absolute --vault id=<abs> (VAULT_PATH_NOT_ABSOLUTE). It writes .obsidian-mcp/{trash,transactions} at the vault root (src/constants.ts INTERNAL_DIRECTORY, README lines 93-95), which memory-vault/.gitignore doesn't cover. It documents no read-only or exclude option, and it rejects reparse points. The GRA-vault project's unpinned npx -y obsidian-mcp <path> now resolves 2.0.1, which runs in the deprecated v1 mode with renamed tools (search-vault became obsidian_search_vault).

Pinning

npx pkg@x.y.z pins only the top-level package. In a scratchpad install, ^2.0.0 pulled in @modelcontextprotocol/server@2.4.0, the same kind of floating dependency that broke lightrag-mcp. Pin as an exact devDependency with package-lock.json and launch with node node_modules/<pkg>/<entry>.js. That also removes the Windows npx and cmd /c question, in line with hooks-never-spawn-npx.md:9-16.

Q4. Two machines

.mcp.json supports ${VAR:-default}, but ${CLAUDE_PROJECT_DIR:-.} in args just becomes . because the variable isn't in Claude Code's own environment. That's no better than a plain relative path. obsidian-mcp would need a launcher script or a separate entry on each machine, and a launcher's own path is relative to the working directory too. mcpvault takes a positional path that defaults to the working directory.

The first choice is a committed .mcp.json with relative paths (node, node_modules/@bitbonsai/mcpvault/dist/server.js, memory-vault/20-memory), provided Phase 0 confirms the server starts in the repo root on both machines. The hooks already assume that root through $CLAUDE_PROJECT_DIR. Otherwise, add a local-scope entry on each machine with absolute paths (claude mcp add --scope local ..., nothing committed), which is how GRA-vault does it, and document it in memory-vault/SETUP.md. Either way, each machine adds the server to enabledMcpjsonServers in its gitignored .claude/settings.local.json, or approves the prompt once. With node as the command, cmd /c isn't needed.

The replacement is scripts/check-vault.mjs, run as a warn-only PostToolUse hook on vault .md writes and as npm run vault:check. It checks the required frontmatter (name, description, type, tags, last_verified), that wikilink targets exist and that filenames are unique across folders, skipping __parsed__. Q6. Data that exists only in LightRAG

None. All 64 documents map one-to-one to vault filenames, checked against both the on-disk stores and the live API. .remember/ was never indexed (lightrag-sync-lifecycle.md:38-41). Repeat the comparison before decommissioning in case something gets inserted during the parallel run.

Q7. Validation through the existing eval

  • Reuse readVault, validateGolden (lines 120-180), wilson, mcnemar and the golden JSON by moving them into a shared module.
  • Add scripts/eval-vault-recall.mjs, about 200 lines. Its main metric is hit@1, hit@3 and hit@5. It also reports facts found in the actual injected text (the same first-1500-characters rule as scoreRow, eval-lightrag.mjs:350-357), abstention at the configured floor, in-process and cold-start latency, and a suggested floor. A --compare-lightrag <saved run> mode scores a saved LightRAG run on the same questions and runs McNemar's test on the per-question "delivered" results.
  • Retire the LightRAG-only parts at decommission: the /query/data diagnosis, the lightrag.log phase join, the cache-busting nonce, the index-status checks and the budget sweep.
Read the numbers with care

The golden questions were written from each note's own wording, which suits keyword search, so the prototype results are an upper bound. The two engines also inject different things (a written answer against excerpts), so a headline like "75% against 54%" wouldn't compare like with like. One billed npm run eval:lightrag (about 10 minutes) in Phase 0 gives a comparison on the same questions.

5 Options

5.1 Full approaches

Recommended

A. In-process recall plus a read-only filesystem MCP server

The hook uses BM25F. Agents get search_notes and related tools from mcpvault in --read-only mode.

Pros

Recall is about 100 times faster than the 9 s budget, with no server, no cost and no prompts leaving the machine. qa-orchestrator, which has no Bash, gets ranked search. Writes still go through the hooks.

Cons

One pinned third-party server (69 packages, 0.x). Keyword matching only. Portability depends on the Phase 0 working-directory check.

Best for

Getting an Obsidian MCP server while keeping the hook guarantees.

Not recommended

B. An MCP server backed by the Local REST API

obsidian-mcp-server 3.7.2 plus the REST plugin. The richest tools: section patching, JSONLogic, frontmatter and optional Omnisearch.

Pros

Very active project. Server-side read-only mode and path allowlists.

Cons

Obsidian must be running, plus plugin 5.5.2 and an API key. Needs Node 24 or later while CI runs 22. Frequent releases (68 versions since January 2025). Doesn't solve the hook either.

Best for

Someone who always keeps Obsidian open.

Valid alternative

C. No MCP server

In-process recall plus Grep, Read, Glob, 00-index.md and an optional npm run vault:search CLI on the same scorer.

Pros

No new dependencies. The hook and the agents rank results the same way. Least upkeep.

Cons

qa-orchestrator gets only Grep, with no ranking and no frontmatter-only reads.

Best for

The smallest setup that works.

Also considered and rejected: basic-memory (AGPL-3.0, Python, its own SQLite index and note conventions), @modelcontextprotocol/server-filesystem 2.1.0 (generic, no Obsidian features), and the npm package mcp-obsidian@1.0.0, a stale 2024 package unrelated to MarkusPfundstein's Python mcp-obsidian (REST-based, 107 open issues).

6 Recommended approach

Option A, with the recall hook shipped first

The hook carries most of the value and doesn't depend on which MCP server is chosen.

  1. Recall hook. In-process BM25F with no dependencies, in scripts/vault-search.cjs, designed as in Q1. It sits behind engine: "bm25f" | "lightrag" so the parallel run can roll back instantly. minisearch can drop in later if fuzzy or prefix matching is wanted. It scored about the same (hit@5 of 68 against 67) and adds a 95 ms index build.
  2. Agents. mcpvault 0.17.1 as an exact devDependency with a lockfile, launched as node node_modules/@bitbonsai/mcpvault/dist/server.js memory-vault/20-memory --read-only --exclude __parsed__. The server is named memory-vault so it doesn't clash with obsidian in the other project. The five scoped agents get search_notes, read_note, read_multiple_notes, get_frontmatter and list_all_tags, with exact names confirmed through tools/list in Phase 0. Their vault lookup becomes search_notes (limit 5) then read_multiple_notes when the server is available, and Grep over memory-vault/20-memory/ when it isn't. The health-check step goes away.
  3. Fallback. If mcpvault fails Phase 0, use obsidian-mcp 2.0.1. That means rooting it at memory-vault/ (it needs .obsidian/), deleting __parsed__ (safe per lightrag-vault-parsed-dir-false-alarm.md:14, with your confirmation), keeping the archive outside memory-vault/ and gitignoring memory-vault/.obsidian-mcp/. Its eight write tools get bare-name deny rules in settings.json. Because it needs an absolute path, it is either committed with a launcher script or set up per machine.
  4. Sync. The warn-only validator replaces it. There is no index.
  5. Eval. The shared code is reused and the old harness retired at decommission.

This fixes the measured failure (81% timeouts) at about 79 ms and no cost, and stops sending prompts to a third-party LLM. The hook-based safety nets (capture nudge, YAML check, validator) stay in place. It also follows the vault's own lessons about pinned tools that fail open.

It depends on Phase 0 passing on both machines and on the eval cutover gate in section 8.

Choose something else if

You need answers that combine several notes inside the recall block itself, without the agent reading notes, or you want agents to write through MCP tools. In the second case, vault-capture-nudge.js and the validator would first need to learn the MCP tool names.

10 Follow-up questions

Asked and answered in the same session after the report came back.

Does the Obsidian MCP server need an API key like LightRAG?

Short answer

The recommended servers don't.

OptionAPI keyWhy
@bitbonsai/mcpvault (recommended)NoIt reads the .md files straight from disk, with no network calls and no LLM.
obsidian-mcp (the GRA-vault server)NoIt also works on the files directly.
obsidian-mcp-server (Option B, rejected)YesIt goes through Obsidian's Local REST API plugin, which issues a local key. The key never leaves the machine, but it's one more secret to keep out of git, and Obsidian has to be running.
BM25 recall hookNoPlain Node over local files.

LightRAG needs a key because it is an LLM pipeline. Every query and every indexing pass calls a hosted model configured in .lightrag.env, so each call costs money and sends the prompt off the machine. A filesystem MCP server only lists, reads and searches files, so there's nothing to authenticate against and nothing to pay for. The trade-off is that it can't write a combined answer across notes. The agent reading the notes does that.

A key would only come back with the optional smart-connections-mcp add-on, and only if its Smart Connections plugin were set up with a hosted embedding provider. Whether its default embeddings run locally wasn't checked. Once LightRAG is retired, revoke the key in .lightrag.env at the provider (Phase 5).

Can it sync across machines?

Short answer

Yes, though git does the syncing, not the MCP server.

A filesystem MCP server keeps no data of its own and reads whatever .md files are on disk. The vault is committed to the repo, so git pull updates the files on either machine and the server searches the new notes straight away.

That's better than today. LightRAG's index in .lightrag/ is gitignored and separate on each machine, so a pulled note can't be searched until a sync runs. That is how three notes from the last two commits went missing from this machine's index.

LightRAG todayFilesystem MCP server
Data travels bygit, then re-indexing on each machinegit only
A pulled note becomes searchableAfter a sync run, if the server is upImmediately
Each machine needsPython venv, server, API key, indexnpm ci and enabling the server once
Obsidian Sync

.obsidian/core-plugins.json has Obsidian Sync turned on. If Sync is also moving this vault, two systems are syncing the same files and can conflict (open question 6). Git alone is enough.

Can it answer questions that span several notes?

Short answer

Yes, in two steps instead of one.

LightRAG takes a question and returns one combined answer. With the MCP server the work splits:

  1. 1
    Search

    search_notes "checkout payment" returns ranked matches from the whole vault, say five notes.

  2. 2
    Read

    read_multiple_notes fetches them in one call.

  3. 3
    Combine

    Claude reads them and writes the combined answer, following wikilinks to related notes.

The 67 notes come to about 390 KB, roughly 1.5k tokens each, so reading five costs around 7k to 8k tokens. LightRAG's record here is weak anyway. The one orchestrator query took 35 s and found nothing useful, and 8 of 12 recall injections were filler.

What you give up is matching on meaning and the entity graph. Search is keyword-based, so a question worded differently from the note ("payment declined" against a note that only says "Forter fraud rejection") can miss it in step 1, where LightRAG's embeddings would have caught it. LightRAG can also connect notes through shared entities even when they don't link to each other. The MCP server only knows the 150 links the notes actually contain. If the eval shows meaning-based misses that matter, smart-connections-mcp brings embeddings back without LightRAG's server.

How do @bitbonsai/mcpvault and obsidian-mcp differ?

Both are filesystem servers that need neither the Obsidian app nor an API key. The difference is how well each suits a read-only vault shared by two machines. Section 5.2 has the full table. These points decide it:

Setup on two machines

mcpvault takes a path that can point at memory-vault/20-memory, and whether a relative path works is a Phase 0 check. obsidian-mcp needs an absolute path and a .obsidian/ folder in its root, so it has to sit at memory-vault/ with a separate entry on each machine.

Read-only

mcpvault's --read-only flag removes the write tools. obsidian-mcp has no such option, so its eight write tools would need deny rules, and whether those hold under bypassPermissions is unverified. The server flag is the safer control, because tools that don't exist can't be called.

Footprint in the vault

mcpvault writes nothing unless its write tools are used. obsidian-mcp creates .obsidian-mcp/trash and .obsidian-mcp/transactions at the vault root.

Write safety

obsidian-mcp is clearly ahead, with version checks against overwrites, a trash, transactions and moves that update backlinks. mcpvault confirms paths and deletes permanently by default. This only matters if agents write through the MCP server, which this plan avoids.

Maturity

obsidian-mcp is a stable 2.x with 5 packages. mcpvault is 0.x with 69 packages and frequent releases. Package count doesn't settle it, though: obsidian-mcp's ^2.0.0 range pulled in @modelcontextprotocol/server@2.4.0 on its own, so either server needs an exact pin and a lockfile.

Windows

obsidian-mcp accepted a drive path in testing but rejects reparse points, which matters if the Lincoln.Pham machine's Documents folder is redirected to OneDrive. mcpvault hasn't been tested on Windows. That is the biggest unknown, and Phase 0 step 4 covers it.

Watch the names. mcpvault's GitHub repo is called bitbonsai/mcp-obsidian and it used to publish as @mauricio.wolff/mcp-obsidian. Neither is related to the abandoned npm package mcp-obsidian@1.0.0 or to MarkusPfundstein's Python mcp-obsidian, which uses the REST plugin.
