Microsoft Teams Workflow Webhook: Lighthouse CI Notifications

How to stand up the Teams channel notification used by the Bitbucket Lighthouse pipeline (Platypus AU/NZ)
Bitbucket Pipelines Teams Workflows Adaptive Card

Why a Workflow, not a Connector

Microsoft retired the old Office 365 Connector-based incoming webhook in favor of Workflows, which runs on Power Automate under the hood. The payload contract also changed: a Workflow webhook expects a message envelope wrapping an Adaptive Card, not the legacy MessageCard (@type: MessageCard) format.

teams-payload-template.json in this repo is already built for the Workflow format, so nothing in the payload needs to change. Only the webhook URL needs to exist and get wired into Bitbucket.

Setup steps

1Open the target channel

In Microsoft Teams, go to the channel that should receive Lighthouse CI results (the existing pipeline posts to lighthouse-ci-test).

2Add a webhook-triggered workflow
  1. Click ··· next to the channel name → Workflows
  2. Search for webhook
  3. The gallery may not list a template named exactly "Post to a channel when a webhook request is received." Microsoft has renamed this over time. Look instead for "Send webhook alerts to a channel" (description: "Get updates in Teams from tools like GitHub, Zapier, or any apps compatible..."). It's the same underlying flow type with the same payload contract.
3Configure the workflow
  • Sign in with your Microsoft account if prompted
  • Confirm the Team and Channel match the one from step 1
  • Click Add workflow
4Copy the generated webhook URL

Teams shows a unique HTTPS URL (an Azure Logic Apps trigger endpoint). Copy it now: the full URL isn't easy to retrieve again later without regenerating it. Click Done.

5Store it as a secured Bitbucket repository variable

Repository settings → Pipelines → Repository variables:

NameValueSecured
TEAMS_WEBHOOK_URLthe URL from step 4Yes
6Test the webhook directly

Before trusting a full pipeline run, confirm the URL actually posts:

curl -sS -X POST -H 'Content-type: application/json' \
  --data '{"type":"message","attachments":[{"contentType":"application/vnd.microsoft.card.adaptive","content":{"$schema":"http://adaptivecards.io/schemas/adaptive-card.json","type":"AdaptiveCard","version":"1.2","body":[{"type":"TextBlock","text":"Test message"}]}}]}' \
  "<paste-webhook-url>"

A card should land in the channel within a few seconds.

7Run the pipeline end to end

bitbucket-pipelines.yml only runs on a custom: (manual) trigger. Go to Pipelines → Run pipeline and select the custom pipeline to fire a real run.

What happens under the hood

The pipeline step (bitbucket-pipelines.yml, the Lighthouse Audit stage) runs envsubst against teams-payload-template.json to fill in ${STATUS}, ${BITBUCKET_BRANCH}, ${BITBUCKET_BUILD_NUMBER}, ${LHCI_RUNS}, and ${FIREBASE_URL}, then POSTs the result to $TEAMS_WEBHOOK_URL.

Two constraints already baked into the template

No clickable buttons. Teams Workflow webhooks silently drop Action.OpenUrl, which is why the Firebase report link is a plain markdown link inside a TextBlock instead of a button.

Restricted envsubst. The pipeline calls envsubst with an explicit five-variable allowlist. Without it, envsubst would also try to expand the literal $schema key in the JSON, since it looks like a shell variable reference, and corrupt the payload.

Repointing to a different channel

Repeat steps 1-5 for the new channel, then update the TEAMS_WEBHOOK_URL repository variable. Steps 6-7 and the payload template stay the same, since both are channel-agnostic.
