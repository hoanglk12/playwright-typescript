1. Trigger & Context

On the Confluence page "Non-Functional Testing Proposal: Frontend Performance." Both are explicitly labelled for trend monitoring. A reviewer left this inline comment anchored to that row:

"Your Reporting tool" refers to the Cloudflare Pages dashboard at playwright-lighthouse-reports.pages.dev, built by the proposal author (Lincoln Pham) as a POC and demoed in section 3.8 of the same document.

2. Current State (Confirmed in Repo)

The dashboard already exists and is fully implemented, but it is a single-run snapshot only. scripts/generate-lhci-index.js reads the current run's manifest.json (desktop + mobile) and overwrites lighthouse-reports/index.html on every deploy. No historical data is persisted anywhere: not in the repo, not in a GitHub Actions cache, not in Cloudflare.

4. Options Compared

Option A: Read-back from the live Cloudflare Pages deployment RECOMMENDED

Before generating the landing page, the CI job fetches the currently-deployed history.json from https://playwright-lighthouse-reports.pages.dev/history.json (treating a 404 as an empty first-run history), appends this run's record, and redeploys the updated file alongside the regenerated index.html. The generator renders inline SVG sparklines, so no charting library is needed.

This layout has since been built and reviewed as a standalone HTML mockup. See Section 6 for the validated tab and card structure, which now supersedes the general description above.

ProsCons
  • Literally "within your Reporting tool," so it satisfies the ask exactly
  • Zero new npm dependencies
  • Zero new infrastructure or server-side code
  • Immune to GitHub Actions cache eviction
  • Matches this repo's established "plain Node.js, no new deps, static host" precedent
  • Single point of failure if the Cloudflare Pages project is ever deleted (mitigated with a 90-day artifact backup)
  • Generator must be extended to read per-run report JSON, not just the manifest

Option B: GitHub Actions cache (reuse monocart pattern) NOT RECOMMENDED

Store history.json in a branch-scoped actions/cache, following the same mechanism CLAUDE.md documents for monocart trend charts.

ProsCons
  • Reuses a mechanism already familiar in this repo
  • The existing monocart implementation uses a static cache key. actions/cache skips the post-job save on an exact-key match, so if this were copied verbatim, history would never actually grow
  • Fixing this needs a unique key per run plus a restore-keys prefix, adding complexity
  • GitHub evicts cache entries unused for more than 7 days, which sits exactly on the boundary of the weekly-production cadence and risks silent history loss
  • History is invisible outside CI: it doesn't live "within the Reporting tool" itself

Option C: LHCI Server mode (@lhci/server) NOT RECOMMENDED

Google's official Lighthouse CI server provides native trend graphs and build-to-build regression comparison out of the box.

ProsCons
  • Native trend/regression dashboard, maintained by Google
  • Richer comparison features than a hand-rolled sparkline
  • Requires standing up and hosting a persistent Node server plus a database (SQLite/MySQL/Postgres)
  • Replaces the current static dashboard rather than extending it, so it does not satisfy "within your Reporting tool"
  • Contradicts the static-host, zero-infra precedent this repo has followed so far
  • New hosting cost and operational burden for an incremental ask

Honorable mentions (not primary options)

ApproachVerdict
Git lighthouse-history data branchDurable and free, but noisy automated commits and needs a write-enabled token. Good as a backup to Option A, not a replacement.
Cloudflare D1 / KV / R2Cloudflare-native and durable, but a static Pages site can't query it at render time without adding Pages Functions. That's more moving parts than this small amount of data justifies.

5. Recommendation

Recommended: Option A, read back and append history on the live Cloudflare Pages deployment
  • Fetch history.json from the live dashboard URL before each run (empty on first run / 404)
  • Extend generate-lhci-index.js to read CWV values from each representative run's report JSON
  • Append one record per {storefront, environment, formFactor}, trimmed to the last N runs (proposed: 26, roughly 6 months weekly)
  • Render inline-SVG sparklines per storefront/metric using the validated layout in Section 6; no new dependencies
  • Redeploy history.json alongside index.html so the site is its own history store
  • Back up history.json as a 90-day GitHub Actions artifact in case the Pages project is ever lost
  • Never merge staging and production series, or desktop and mobile series. Segment every line by both.
  • Reuse the layout and rendering logic from the reviewed mockup (Section 6) rather than re-deriving the dashboard structure during implementation

This beats Option B on durability (no cache-eviction risk) and Option C on scope and cost (no new infrastructure), and it is the only option that literally places the trend "within" the existing Reporting tool, as the reviewer requested.

6. Approved Dashboard Layout (Validated by Mockup)

Before touching generate-lhci-index.js, the proposed layout was built as a standalone, static HTML mockup (docs/technical-research/lighthouse-trend-monitoring.mockup.html), using synthetic data across four representative storefronts: Platypus AU, Skechers NZ, Vans AU, and Dr. Martens NZ. It has been reviewed and approved. The structure below is now the specified target for implementation, not an open design question.

ElementDecision
Primary navigationEnvironment tabs (Staging / Production) plus a Desktop / Mobile form-factor toggle, above the trend cards. Series are never merged across either axis.
Per-storefront unitOne card per storefront, containing two metric groups: 4 category-score tiles (Perf / A11y / Best Practices / SEO) and 4 Core Web Vitals tiles (LCP / CLS / TBT / FCP), 8 sparklines per card in total, all shown, none curated (see Open Question 1 in Section 10, still pending final sign-off).
Per-tile contentCurrent value, a 10-point sparkline (area fill, faint grid, emphasized endpoint dot), and a week-over-week delta chip, for example "▲ +3 pts", "▼ 0.3s faster", or "▼ 0.01 better" for CLS.
Color legendCategory tiles use Lighthouse's own 90 / 50 score bands; Web Vitals tiles use Google's published Core Web Vitals thresholds. Both map to the same good/warn/poor palette, so a reader learns one legend for the whole page.
Production tabRenders an explicit empty state ("No production runs recorded yet…") instead of being hidden. This keeps the gap described in the Risk Assessment (Section 7, "Production trend line stays empty") visible in the tool itself until the weekly production LHCI config exists.
Rendering approachAll environment × form-factor segments render into the same static page and are shown or hidden with CSS classes toggled by a small inline script. There is no server involved, and no segment is regenerated on click.

The mockup is a design reference, not implementation-ready code: it renders client side (document.createElement / appendChild at page load), while generate-lhci-index.js builds an HTML string at build time and writes it with fs.writeFileSync. Section 8, Step 2 specifies exactly what carries over as is versus what needs rewriting for that difference.

Cloudflare Pages project deleted → history lost (Option A's SPOF) Medium Low Also upload history.json as a 90-day artifact, or commit to a lighthouse-history data branch
Staging and production merged into one misleading trend line Medium Medium Segment every series by {environment, formFactor}; never merge
Production trend line stays empty Low Certain today No production LHCI config exists yet. Design for segmentation now (the Section 6 layout already renders this as an explicit empty state), and wire production config as a separate follow-up.
CWV numeric values missing because generator only reads the manifest today Medium Medium Extend the script to read each representative run's *.report.json
history.json grows unbounded over time Low Low Trim to the last N runs per series on every append (proposed N = 26)
Cloudflare 25 MiB per-file limit Very Low Very Low history.json is KB-scale. The rendered index.html now also inlines sparkline SVG for every environment × form-factor segment: roughly 8 storefronts × 2 form factors × 8 metrics at a 26-run retention window, an estimated 150-300 KB once Staging and Production are both populated, which is still far under the limit. The existing find -size +25M -delete guard remains untouched.

Rollback Plan

The trend feature is purely additive. To roll back: revert generate-lhci-index.js to the current snapshot-only version and remove the fetch-history and artifact-backup workflow steps. The live dashboard reverts to today's single-snapshot table on the next run. Deleting the deployed history.json is optional and harmless.

8. Implementation Steps (For the Implementation Agent, After Approval)

1

Confirm segmentation keys and retention window

Confirm with stakeholder: segment by {environment, formFactor, storefront}; retain last 26 runs per series (roughly 6 months at weekly cadence).

2

Extend scripts/generate-lhci-index.js

Accept an existing lighthouse-reports/history.json (default [] if absent). For each representative manifest entry, open its jsonPath report and extract numericValue for LCP / CLS / TBT / FCP. Append one record per storefront/form-factor with timestamp, trigger, commit, the 4 category scores, the CWV values, and an environment tag. Trim each series to the last N runs. Write history.json back out. Keep the script pure and network-free; the workflow does the fetching.

Render the Section 6 layout by porting logic from the reviewed mockup, split by what actually transfers to a build-time Node script that writes an HTML string (the mockup instead builds DOM nodes in a browser at load time). CWV_THRESHOLDS, sparkline(), scoreColor, vitalColor, fmtScore, fmtVital, scoreDelta, vitalDelta, and statusFlag are already pure functions that return strings or values, so they port over unchanged. scoreTile and vitalTile currently build a DOM node and set its .innerHTML; each one just needs to return an HTML string directly instead, following the renderTable() string-templating pattern the script already uses. el(), renderCard(), and renderSnapshotRow() have no DOM to build against in Node, so those need to be re-authored as string templating. And the generator now also has to emit the environment-tab and form-factor-toggle interaction as an inline <script> in the generated page: this step used to mean markup only, and now it means behavior too.

3

Add a history fetch step to lighthouse-ci.yml

Insert before the landing-page generation step:

- name: Fetch existing trend history
  if: always()
  run: |
    curl -f https://playwright-lighthouse-reports.pages.dev/history.json \
      -o lighthouse-reports/history.json \
      || echo '[]' > lighthouse-reports/history.json
  continue-on-error: true

Pass trigger/environment metadata to the generator via new env vars, reusing the existing GITHUB_SHA / GITHUB_REF_NAME pattern (for example, add LHCI_ENVIRONMENT and LHCI_TRIGGER).

4

Add a durability backup step

Upload lighthouse-reports/history.json as a 90-day actions/upload-artifact (or commit it to a dedicated lighthouse-history branch if write permissions allow), independent of the Cloudflare Pages deploy.

package.json

No new dependencies required. Optionally add a convenience script to run the generator locally against a fixture history.json for testing.

9. Validation

Local

  • Seed a fixture lighthouse-reports/history.json with 2-3 synthetic runs across both environments and form factors; run node scripts/generate-lhci-index.js → confirm index.html shows the existing table plus sparklines, and history.json grew by one run
  • Delete the fixture history.json and re-run → confirm no crash (empty-history path handled) and a valid single-point series
  • Confirm CWV values in the rendered sparkline match the displayValue/numericValue in the representative *.report.json
  • Seed a fake production record and confirm staging and production render as separate, non-merged series
  • Confirm SVG gradient IDs stay unique across the full rendered page. All environment × form-factor segments render simultaneously and toggle via CSS, so an ID derived from a values hash can collide when two segments share identical data (caught in the mockup; use a monotonic counter instead)
  • Confirm Core Web Vitals delta copy reads "better/worse" for CLS and "faster/slower" for LCP/TBT/FCP, not the same wording for every metric (also caught in the mockup)

CI (after merge)

  • Trigger the workflow; confirm the history-fetch step succeeds (or falls back to [] on first run)
  • Confirm the deployed dashboard shows sparklines and https://playwright-lighthouse-reports.pages.dev/history.json is fetchable
  • Trigger a second run; confirm history.json grew by exactly one entry per storefront/form-factor and each sparkline gained a point
  • Confirm the 90-day history.json artifact is attached to the run
  • Confirm the existing 25 MiB deploy guard and continue-on-error behaviour are unaffected
