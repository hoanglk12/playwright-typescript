Extending Zod to the GRA Suite

The dummyjson pilot proved the mechanism and deliberately stopped there. This report answers the question it deferred: should GRA's 8-brand GraphQL suite get schema validation, and if the staging quirks documented in tests/api/CLAUDE.md say no to a blanket yes, what does a scoped yes look like.

Where this picks up

The approved pilot plan set four ground rules: z.looseObject never strictObject, safeParse never parse, no z.coerce.*, and no z.discriminatedUnion on GRA's __typename. Then it stopped, because GRA's staging environment has documented, accepted quirks that a strict schema would turn into hard failures across all 8 brands at once: broken price_range data, a productSearch field missing from the schema entirely, unreliable __typename discriminators, and per-brand low stock nulling fields out.

That reasoning checked out against the live spec code, and it turned up one quirk the original plan didn't name: GraphQL null-propagation on staging nulls whole array elements, not just fields (gra-catalog.spec.ts:395 already guards for this). The deferral stands. What follows is a way to say yes to part of the suite without reopening that risk for the whole thing.

The open technical question: __typename

Ground rule 04 says what not to do (z.discriminatedUnion) but not what to do instead. Four options, one answer:

One looseObject per operation

Recommended

Base fields required, inline-fragment fields (... on ConfigurableProduct) .optional(), __typename: z.string() and never z.literal. Matches the actual wire shape and keeps path-precise error output.

Non-discriminated z.union

Rejected

On mismatch, Zod reports every branch's failures at once. That destroys the exact-path error message the whole pilot was approved for.

z.discriminatedUnion

Rejected

Barred by rule 04, and independently wrong: staging returns ConfigurableProduct for simple products, so the discriminator itself lies.

Branch in test code on __typename

Rejected

Requires trusting the exact field that's documented as unreliable. Pushes branching into specs instead of the schema.

Two rules this adds on top of the pilot's four

Rule 05 Nullable discipline

Any path already listed in an assertNoCriticalErrors ignore list, and any array a spec null-guards today, must be .nullable() in the schema. A schema that contradicts a deliberate, already-accepted tolerance isn't stricter. It's wrong.

Read the ignore list as a hint, though, not as a verdict. gra-account-creation-signin.spec.ts:142 tolerates both loyalty and loyalty_program_status, but only the first one ever nulls: loyalty_program_status came back false on all four drm/van projects, AU and NZ. Marking it .nullable() on the strength of its ignore-list entry would weaken the schema against the evidence. Check each path against a real payload before applying the rule to it.

Rule 06 No literal __typename

z.string(), never z.literal('SimpleProduct'). Staging returns ConfigurableProduct/ConfigurableWishlistItem even for simple items. Type-specific assertions stay where they already live: as ordinary value assertions outside the schema.

Phased plan

  1. Phase 0

    Write the two new rules down, touch no tests

    Why: rule 05/06 plus two mechanical rules. Never call the schema assertion inside beforeAll (a failure there cascades to every test in the spec under fullyParallel: false), and always place it after the error-tolerance check, never before (otherwise the failure says "received null" instead of naming the real cause).

    Recorded in tests/api/CLAUDE.md under a new "Zod Schemas: GRA" heading. No code changes.

  2. Phase 1 · gate

    Evidence pilot: 2 specs, 4 tests, 32 executions

    Why these two: gra-address-book-countries and gra-support-features have zero measured hazards and already contain hand-rolled typeof loops, so Phase 1 doesn't just prove "no false failures." It proves Zod is strictly better than what's there today.

    New schema files under src/data/api/schemas/, added assertDataSchema() calls alongside (not replacing) the existing checks. Run on all 8 projects. Teeth-test each schema: break one required field, confirm the failure names the exact path, revert. Stop and report; do not continue automatically.

    Place each schema call after the soft loop it sits beside, never before. assertDataSchema() is a hard assertion (GraphQLResponse.ts:162) and the loops are softExpect, so a schema call placed first throws and the loop's per-field failures never register — losing exactly the field-level comparison Phase 1 exists to make. That's a second ordering constraint alongside "after the error-tolerance check."

    One calibration on how much this proves: countries returns exactly one element on all 8 brands, so TC_02's loop over "every country" walks a single three-field object. The address-book schema is thin evidence. gra-support-features carries the heavier half — its four ewave_dynamicpromoblocks_*_enable flags came back boolean on every endpoint, so that schema can require them and still not be vacuous.

  3. Phase 2 · separate approval

    Tier A remainder + Tier B: 11 specs, 89 tests

    Why split into 2a/2b: Tier A remainder (customer-profile, my-details, authentication) is still zero-hazard. Tier B needs rule 05 applied deliberately per spec: the drm/van loyalty partial-error, null-guarded shipping/wishlist arrays, the order-history schema-gap branch.

    Shared sub-shapes (Money, UserError) hoisted once to gra-common-schemas.ts first. Gate to Phase 3 is two consecutive clean 8-project runs, not one.

    The loyalty shape is measured now rather than assumed. data.customer comes back fully populated on all 8 brands and only loyalty nulls, so the schema takes loyalty: LoyaltySchema.nullable(), not customer: CustomerSchema.nullable(). Four more payload facts worth writing in rather than rediscovering as false failures: on the loyalty brands every loyalty sub-field is null except rewards: [], so a required-field LoyaltySchema would fail on pla and skx too; apparel21_id is null everywhere except pla-nz and skx-nz, where it's a string; qff_member_number is null on AU and an empty string on NZ; dynamic_promo_blocks.message.success_phrase is null on all 8.

  4. Phase 3 · conditional, separate approval

    Catalog only, and only if the evidence says it's worth it

    Why conditional: a throwaway local diagnostic (never committed) logs real safeParse failures across all 8 brands first, to derive nullability empirically instead of guessing. If items, price_range, and aggregations all end up nullable, the honest finding may be that a catalog schema isn't worth having. That's a valid outcome of this phase, not a failed one.

    aggregations is not one of the things this phase has to solve. It's selected only by DISCOVER_PRODUCTS_QUERY, which runs in beforeAll and is already barred from carrying a schema assertion, and by gra-search.spec.ts, which is out of scope. PLP_QUERY and PDP_QUERY never ask for it, so it forces nothing optional. What's left is the nullability inside items[]: price_range, and the null array elements. That is what the diagnostic is for.

    Cart-minicart, search, and both loyalty specs stay out of scope indefinitely: cost, conditionality, and per-project exclusion respectively, not quirks that a phase can resolve.

Rollback

Every phase is one additive commit: new schema files plus added assertion lines, nothing existing removed or changed. git revert on any phase's commit restores exact prior behaviour for that phase alone; earlier phases are unaffected. npm uninstall zod is not part of GRA rollback, since the dummyjson pilot still depends on it.

Questions since answered

Four questions this report originally left open, closed on 2026-08-15 by re-reading the specs and by three throwaway probes run against all eight staging endpoints. The probes created eight customer accounts and eight guest carts, which is what every npm run test:api:gra run already does per brand.

  • Keep the hand-rolled typeof loops. Read line by line they turn out to be mostly value assertions, not type assertions, and most of what they check a schema can't say. __typename === 'Country' is barred by rule 06. available_currency_codes containing site.currency is parameterised on the site fixture at runtime. The toBeNull() checks on dynamic_promo_blocks.discount and gift assert live staging state, which rule 05 would only relax to .nullable(). The one genuinely redundant block is the four typeof … 'boolean' lines at gra-support-features.spec.ts:97-100, and four lines don't outweigh keeping every phase revertable. The schema still earns its place beside them: a null array element gives Zod a clean path-precise failure where country.id.length at line 68 throws a raw TypeError.
  • No path-scoped sibling for assertDataSchema(). The premise doesn't survive contact with the queries. aggregations appears only in DISCOVER_PRODUCTS_QUERY (beforeAll, barred from schema assertions) and in gra-search.spec.ts (out of scope). PLP_QUERY and PDP_QUERY don't select it, and GraphQL returns only what's selected, so it forces zero fields optional. Scoping to products.items would also scope around the real pressure rather than into it, since price_range and the null elements both live inside items[]. For those two queries data holds nothing but products anyway, so the whole-data schema is already one wrapper deep. The rollout still touches no shared file.
  • The CI gap is attribution, not coverage. playwright-with-slack.yml carries an "API Tests (GRA)" job running npm run test:api:gra under paths-ignore filters that exclude only docs, so Phase 1's commits already trigger a full 8-project run on push, and the run history confirms the job executes rather than skipping. It is also red at baseline and buried among six UI shards. The dedicated API workflow's filters, meanwhile, are broken rather than merely narrow. Detail and the recommended filter list are in the risk table above.
  • The loyalty partial-error nulls the field, not the object. Confirmed on all eight brands with a fresh account and token each. data.customer comes back fully populated, loyalty is null on drm and van, and the error carries path: ["customer","loyalty"] with category: graphql-input and the message "Loyalty Program is not available on the current website." Phase 2 writes field-level nullability. The pessimistic customer: CustomerSchema.nullable() isn't needed, and would be looser than the payload warrants.

Still open

  • Rule 06 bans z.literal on __typename because staging's product discriminators lie. countries has no polymorphism for that reasoning to bite on: __typename came back "Country" on all eight brands with no variance. So either narrow rule 06 to product types and let the countries schema assert the literal, or keep the ban categorical and leave gra-address-book-countries.spec.ts:71 as an ordinary assertion outside the schema for good. The second option costs one line and no thinking. Either way it's a call to make out loud rather than by default.
