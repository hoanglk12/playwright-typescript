1. Summary

The sentence being tested

The Langfuse report ([LF], 2026-10-02) dismissed Phoenix in one line: "LightRAG has no native hook for them, so they'd need the same launcher work as A2, and they aren't obviously lighter." Here is each of its three claims, checked against source.

Claim Verdict Evidence
"No native hook" Half true. LightRAG has no Phoenix- or OpenInference-specific hook, but 1.5.7 deliberately carries the request's OpenTelemetry context into its LLM and embedding queue workers. utils.py:2216-2225, 2352-2358, 1449-1462; upstream PR HKUDS/LightRAG#3386, merged 2026-07-14, which fixes #3382 "Tracability compatibility".
"Same launcher work as A2" Refuted. No Python launcher is needed. openinference-instrumentation-openai registers an opentelemetry_instrumentor entry point, and OTel's sitecustomize auto-instrumentation can be switched on by one PYTHONPATH line in the gitignored .lightrag.env. The probe ran on a sibling uv trampoline in the same venv (normalizer.exe), which honoured PYTHONPATH/sitecustomize; lightrag-server.exe is the same kind of uv launcher and is expected to behave the same, which V2/V3 confirm (U1).
"Not obviously lighter" Refuted against Langfuse self-host, confirmed against Option D. Phoenix is one Python process with SQLite, and its own chart requests 1 GiB and caps at 2 GiB, against Langfuse's 6 containers and 16 GiB VM guidance. It still needs a second Python env of 158 packages, 16 packages in the LightRAG venv and an always-on process, where D needs nothing.

Does Phoenix beat Option D?

Not for the question that's open today.

D can already split the ~9 s per query. At INFO level, lightrag.log writes four timestamps per uncached query: the keyword-cache save, Query nodes, Final context and the answer-cache save. operate.py:5179-5212 shows that the query-embedding batch runs between the first two. Join those with the client's send time (the eval knows it, and the recall log records it as ts/ms) and you get four phases: keyword LLM, embedding, local retrieval and answer LLM.

Today's log already answers the question [LF] wanted its trial to settle ("what share of the ~9 s does the answer call take?"):

Phase Today's samples
Answer LLM call 4.3 s, 4.8 s and 11.2 s
Query embedding 1.4 s and 1.8 s
Local retrieval ≤ 0.3 s

These come from lightrag.log:73060-73115 and are single samples, so treat them as indicative. They also come from mixed callers with different parameters: the Query nodes lines show top_k of 20, 40 and 30, and the 11.2 s answer phase was the research agent's own MCP query_document call with rerank requested, not the recall hook's configuration. They still support D, because D3 will produce numbers at the hook's own settings.

Phoenix does add things D can't give you: per-call prompt and completion token counts, each embedding call as its own span, ShopAIKey retries and errors as spans, per-/query trees that stay correct when hook, MCP and eval traffic overlap (where D's timestamp join gets ambiguous), and a UI. Those are real gains. None of them is needed to act on the current finding.

Recommendation

Do Option D now: D2 (per-run JSON) plus D3 (the log-phase join). Treat P1, a local Phoenix server in its own venv hooked in through PYTHONPATH with no launcher, as the escalation, and only take it when one of the triggers in §9 fires.

If P1 is ever enabled, these conditions are non-negotiable:

  1. Batch span export. The OTel auto-config path already defaults to it. phoenix.otel.register() defaults to synchronous export, which would stall LightRAG's whole event loop whenever Phoenix is down.
  2. The full set of masking env vars.
  3. PHOENIX_HOST=127.0.0.1. Phoenix binds 0.0.0.0 by default, and its gRPC port 4317 always binds [::].
  4. PHOENIX_ALLOW_EXTERNAL_RESOURCES=false, because a Scarf telemetry pixel and Google Fonts load by default.
  5. A finite retention period. The default keeps traces forever.

The remaining options don't fit. Docker (P3) is out because this machine's Docker VM has about 0.9 GiB and 1 CPU, which is below Phoenix's own 1 GiB request. Phoenix Cloud (P4) brings back egress. A launcher (P2) means the repo's first .py file, grpcio in the LightRAG venv, and a synchronous-export default that has to be overridden.

4. Confirmed facts (with evidence)

4.1 Per-/query grouping (question b): verified yes at source level

LightRAG copies the caller's context when it enqueues a call. Both submission paths call contextvars.copy_context(): _limited_wait at utils.py:2216-2221, whose comment reads "Capture the enqueuer's context (e.g. an active OpenTelemetry span) so the worker executes func() under it", and wait_func at utils.py:2352-2358. The context rides along in the queue tuple (2225, 2368/2374).

Each call then runs under that context. worker() unpacks ctx (1416-1423) and runs exec_task = ctx.run(asyncio.ensure_future, func(*args, **kwargs)) (1460-1462), and limited_worker() does the same (1709-1714). So every call becomes a fresh Task whose context is a copy of the enqueuer's, not the long-lived worker's.

This was a deliberate upstream fix. Issue #3382 says the old behaviour caused "observations that detach into their own trace" and "cross-request pollution", and PR #3386 (merged 2026-07-14) fixed it.

Nothing on the /query path breaks the context. query_text (query_routes.py:518) awaits rag.aquery_llm(...) directly (:602). A grep found no run_in_executor or threading.Thread anywhere in lightrag/ outside the webui. The query embedding is a single batched call made before vector search (operate.py:5179-5212), and it goes through the same queue decorator.

FastAPI instrumentation would supply the parent span. opentelemetry-instrumentation-fastapi replaces fastapi.FastAPI with _InstrumentedFastAPI at instrument time (otel-fastapi.py:491-493, 504-514). LightRAG imports FastAPI at module level (lightrag_server.py:5) and builds the app at :1697. sitecustomize runs before that import, so the app gets instrumented. The installed FastAPI, 0.136.3, satisfies _instruments = ("fastapi ~= 0.92",).

With FastAPI server spans, then, the keyword ChatCompletion, the CreateEmbeddings batch and the answer ChatCompletion spans nest under POST /query (span names from pin/oi-_request.py:314, 375). This hasn't been confirmed at runtime yet; V3 covers it.

A W3C traceparent header from Node would link as well. The ASGI middleware extracts context with the global propagator (default tracecontext,baggage), so a traceparent: 00-<32hex>-<16hex>-01 header sent by eval-lightrag.mjs would make the server span a child of that trace ID, and node:crypto can generate the header with zero dependencies. The flag must be 01: the default sampler is parent-based, so 00 would drop the whole trace. If the eval doesn't export its own parent span, the server span's parent will be missing in Phoenix, and how Phoenix displays that is UNVERIFIED (U6). The trace ID still lets you look up each eval question exactly.

Correction to [LF] §4.1. [LF] said "No request context reaches the wrapper." For 1.5.7 that's wrong; context does reach it. Calls were ungrouped in Option A because nothing created a request-level span, not because the queue severed the context.

Without FastAPI instrumentation you can still group by timestamp adjacency, by span name (ChatCompletion vs CreateEmbeddings) and by token count, since the answer call carries the large context, up to DEFAULT_MAX_TOTAL_TOKENS = 30000 (constants.py:61). OpenInference's session.id and metadata context attributes (pin/oi-_request.py:330, 391, get_attributes_from_context()) would need code running inside the LightRAG process.

4.2 A hook with no new files (question a): yes through PYTHONPATH, but not through the opentelemetry-instrument command

The entry point exists and the version range matches. pin/oi-pyproject.toml:42-43 (0.1.61) and main (0.1.63) both declare [project.entry-points.opentelemetry_instrumentor] openai = "openinference.instrumentation.openai:OpenAIInstrumentor", along with an openinference_instrumentor group (:45-46). oi-package.py:1 sets _instruments = ("openai >= 2.8.0",), which the installed openai 2.41.1 satisfies. The loader checks conflicts per entry point and skips on a mismatch (otel-auto-load.py:81-92). The instrumentor wraps AsyncOpenAI.request at class level (pin/oi-__init__.py:50-57), which covers LightRAG creating a fresh client on every call (openai.py:282 AsyncOpenAI(**merged_configs); AsyncAzureOpenAI subclasses it).

A distro is mandatory. Auto-instrumentation runs distro.configure(), then _load_configurators() (otel-auto-init.py:135), then _load_instrumentors() (:136), all inside a try that logs and swallows failures (:138). Without opentelemetry-distro nothing configures an SDK provider, and tracing becomes a silent no-op (issue #5180). The distro's entry points are opentelemetry_configurator and opentelemetry_distro (distro pyproject at v0.65b0, lines 39-43).

Some of the distro's defaults fail silently on this setup. otel-distro.py:28-31 (v0.66b0, unchanged at v0.65b0) defaults OTEL_EXPORTER_OTLP_PROTOCOL=grpc and sets OTEL_METRICS_EXPORTER/OTEL_LOGS_EXPORTER=otlp. With only the HTTP exporter installed, resolving otlp_proto_grpc raises inside _load_configurators(), the error is swallowed (:138), and the instrumentors never load. You get no tracing and no visible error. Three settings are therefore required: OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf, OTEL_METRICS_EXPORTER=none and OTEL_LOGS_EXPORTER=none (none gives an empty exporter list, otel-sdk-config.py:198).

The endpoint has to be set too. The SDK default is http://localhost:4318 (otel-http-common.py:49), and /v1/traces is appended to the base endpoint (:138). Set OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:6006; Phoenix accepts OTLP-HTTP at POST /v1/traces (router traces.py:441 @20.19.0).

opentelemetry-instrument lightrag-server misbehaves on Windows. run() sets PYTHONPATH to the auto-instrumentation dir and then calls os.execl(executable, ...) (otel-auto-init.py:105, 108). In a scratch test on this machine with the venv's Python 3.12.13, os.execl started a new PID (25412 → 32896), the parent exited, and cmd printed "cmd regained control" before the child had finished. Inside start-rag.bat, that would hand the prompt back while the server kept writing to the same console, which makes foreground behaviour and Ctrl+C confusing.

The same mechanism works without the exec. .../auto_instrumentation/sitecustomize.py contains nothing but initialize(). With PYTHONPATH pointed at a scratch dir holding a sitecustomize.py, the uv trampoline .lightrag-venv\Scripts\normalizer.exe loaded it and reported the venv python as sys.executable. activate.bat clears PYTHONHOME but leaves PYTHONPATH alone (lines 51-55). One line in .lightrag.env, PYTHONPATH=<abs>\.lightrag-venv\Lib\site-packages\opentelemetry\instrumentation\auto_instrumentation, is therefore enough. No .py file is needed, and start-rag.bat keeps calling lightrag-server directly. The full chain (install → sitecustomize → spans in Phoenix) stays UNVERIFIED until something is actually installed (V2/V3).

The start-rag.bat loader keeps every proposed value intact. Running the identical for /f "usebackq eol=# tokens=1,* delims==" loop on a scratch copy showed that openinference.project.name=lightrag keeps its embedded =, that comma lists survive, and that ^(?!.*/query) survives because delayed expansion is off. Python's re then excluded /health and /documents/pipeline_status but kept /query and /query/stream.

For the exclusion rules: ExcludeList compiles "|".join(urls) and runs search against the full URL (util-http v0.65b0 :77-83), the URL has the form scheme://host + path (asgi :452-478), and the env var is read at module import (otel-fastapi.py:277).

The phoenix.otel.register(auto_instrument=True) route is weaker. It loads only the openinference_instrumentor group (px-otel.py:829-841), so there are no FastAPI spans and no grouping. It needs code inside the process, which means a launcher, and it defaults to batch=False (px-otel.py:69, 174-177). arize-phoenix-otel also depends on opentelemetry-exporter-otlp (both transports) and imports the gRPC exporter at the top of the module (px-otel.py:13), which pulls grpcio into the LightRAG venv (see the dry-run in §4.7).

4.3 Export mode, latency and fail-open (question c): verified

register() exports synchronously by default. SimpleSpanProcessor.on_end calls self.span_exporter.export((span,)) inline (otel-sdk-export.py:116-127, 1.45.0) on whichever thread ends the span, and for async OpenAI calls that is LightRAG's single asyncio event-loop thread (/health reports uvicorn with 1 worker). The OTLP-HTTP client retries until a 10 s deadline (otel-common-http.py:30-31, _MAX_RETRIES=6, _DEFAULT_TIMEOUT=10.0), treating connection errors as retryable with 2^n × jitter backoff (:139-140, 186-234).

With Phoenix down, each span end could therefore block the whole server for about 7 s: roughly 1 + 2 + 4 s of backoff before the next wait would overrun the deadline. That estimate comes from reading the source and hasn't been measured. At around 4 spans per query, it would blow the 9 s budget for every client. Even with Phoenix up, Simple mode makes a synchronous localhost HTTP POST on the event loop for every span, and px-otel.py:354-364 itself prints "strongly advised to use a BatchSpanProcessor in production".

The SDK's auto-config path uses Batch by default. _init_tracing sets export_processor = export_span_processor or BatchSpanProcessor (otel-sdk-config.py:223 at 1.45.0, :250 at 1.44.0). BatchSpanProcessor.on_end calls emit(), which does self._queue.appendleft(data) and drops the span with a warning when the queue is full (shared_internal/__init__.py:192-205). It never blocks. The defaults are a 5 s schedule delay, batches of 512, a queue of 2048 and a 30 s export timeout (otel-sdk-export.py:41-44), and export and retries run on the worker thread.

In Batch mode it fails open: calls go ahead when Phoenix is down, spans are retried in the background and then dropped, and the exporter writes WARNING/ERROR lines to the LightRAG console.

At shutdown, Batch shutdown joins the worker thread for up to timeout_millis (30 s by default; shared_internal:207-217), and a pending retry wait is interrupted by _shutdown_event (otel-common-http.py:234-237). How long Ctrl+C takes with Phoenix stopped is UNVERIFIED (V6).

So P1 (the sitecustomize path) is Batch by default and fine as it stands. P2 (register) is Simple by default, which makes batch=True a hard requirement there.

4.4 Content controls (question d): verified, driven by env vars

Masking is read from env vars. When no config is passed in, TraceConfig() is constructed (pin/oi-__init__.py:40) and reads each field from the environment (oi-config.py:459-480). Every default is False, so everything is captured (pin/oi-config.py:124 onward). Redacted values become "__REDACTED__" (:116).

Here is what each flag covers (oi-config.py:338-420 on main; the env names are the same in the pin):

  • OPENINFERENCE_HIDE_INPUTS hides input.value, the input MIME type and all llm.input_messages.*.
  • OPENINFERENCE_HIDE_OUTPUTS does the same for outputs.
  • OPENINFERENCE_HIDE_EMBEDDINGS_TEXT is needed as well, because embedding text is a separate per-index attribute (embedding.embeddings.N.embedding.text; oi-_request_attributes_extractor.py:259-268).
  • OPENINFERENCE_HIDE_EMBEDDINGS_VECTORS matters for storage as much as for content. LightRAG requests base64 encoding ([LF]), and the instrumentor decodes each vector back into a list of floats, 3072 per text for text-embedding-3-large (pin/oi-_response_attributes_extractor.py:170). The older OPENINFERENCE_HIDE_EMBEDDING_VECTORS is a deprecated alias.

Boolean parsing fails toward capturing content. _cast_value accepts only true or false, case-insensitive (pin/oi-config.py:495-503). Any other value, such as 1 or yes, logs a warning and falls back to the default False, which means captured. Use the literal true.

Masking still keeps span names and timings, llm.model_name and llm.provider/llm.system, token counts (llm.token_count.*, oi-_response_attributes_extractor.py:270-316), and llm.invocation_parameters, which are model parameters rather than content and can be hidden separately. Failures are still recorded as ERROR spans with the exception (pin/oi-_request.py record_exception). FastAPI spans keep the method, route, status and client address. Headers are captured only if OTEL_INSTRUMENTATION_HTTP_CAPTURE_HEADERS_* is set, and by default it isn't.

The recommended default is to hide everything, with all four flags set to true. Unmask only for a named debugging session, and record that in the vault note.

For context, LightRAG already keeps verbatim prompts on local disk. .lightrag/kv_store_llm_response_cache.json (13.3 MB, gitignored at .gitignore:160) held 1,859 original_prompt entries (utils.py:4227), and keyword-cache rows store prompt=text, which is the user query (operate.py:5079-5086). lightrag.log also keeps prompt-derived keywords at INFO, for example Query nodes: Arizona, Phoenix, LightRAG (:73085). An unmasked Phoenix would be a second local copy rather than a new kind of exposure. The hook's "never log prompt text" rule (user-prompt-submit.js:52) currently holds only for the hook's own log.

6. Technical findings

6.1 What Phoenix (P1) would and wouldn't show, compared with Langfuse and D

With FastAPI instrumentation on, P1 would show one trace per /query: POST /query → ChatCompletion (keyword) → CreateEmbeddings (one batch) → ChatCompletion (answer). Each span carries its latency and its prompt and completion token counts, and the answer call's prompt tokens show how big the context was. Errors and tenacity retries against ShopAIKey 529/503/429 responses appear as ERROR spans; /health shows failed_total of 3 query, 1 keyword, 1 extract and 2 embedding today. Gaps between spans reveal queue waits when max_async=4 saturates.

It would also show two things Langfuse couldn't:

  • requests the hook aborted, as POST /query spans longer than 9000 ms (U7);
  • cache hits, as a POST /query with no ChatCompletion children.

It wouldn't show LightRAG's internal graph and vector retrieval steps, since no LightRAG instrumentor exists. The cost column would be wrong, prompt and answer content would be hidden by design under the recommended masking, and the eval's quality metrics (hit, facts, inTime) would stay out of it. The eval and recall-stats remain the source of truth for those.

Vault-sync indexing (POST /documents/text|upload → background extraction) produces root-level ChatCompletion and CreateEmbeddings spans. Under the recommended exclude regex, the indexing requests themselves aren't spanned.

D already gets four phases per uncached query, from lightrag.log timestamps joined to the client's send time:

  • keyword LLM: send → keyword-cache save;
  • embedding: keyword save → Query nodes, the batch at operate.py:5179-5212;
  • retrieval: Query nodes → Final context, at operate.py:6028 and 5832;
  • answer LLM: Final context → answer-cache save.

Live hook traffic can be joined the same way using the recall log's ts/ms (user-prompt-submit.js:140-148). "POST /query" 200 access lines exist too, but they carry no duration. What D lacks is token counts, per-embedding-call detail, visibility into retries beyond ERROR log lines, unambiguous grouping under concurrent traffic, and a UI.

8. Options compared

P1. Local Phoenix server in its own venv, hooked in with no new code (PYTHONPATH → OTel sitecustomize)

The variant that uses the OTel opentelemetry-instrument wrapper is rejected because of the Windows execl behaviour (§4.2).

Pros: no .py file and no launcher. Export is Batch by default and fails open. FastAPI spans give per-/query grouping, masking is set through env vars, and with the flags set nothing leaves the machine. Neither package.json nor CI changes, rollback is one line plus a fresh-terminal restart, and it's roughly 10× lighter than Langfuse self-host.

Cons: a second Python env of 158 packages to maintain on two machines, and 16 packages in the LightRAG venv. It's an always-on process using a few hundred MB to ~1 GB on a machine with 3 GB free. The PYTHONPATH is absolute and per machine. The gRPC port 4317 is exposed on all interfaces (it only ingests, and the firewall can block it). The OTel distro's silently failing defaults mean the env lines have to be exactly right. Span names are generic, and there are no retrieval spans.

Best for: the point where D3 can no longer answer the question (see the triggers in §9) and you need per-call tokens and retries on live traffic without egress.

P2. Local Phoenix plus a Python launcher using phoenix.otel.register(batch=True, auto_instrument=True)

Pros: it uses Phoenix's own helper, and the project name lives in code.

Cons: it's the repo's first .py file, and start-rag.bat changes on both machines. grpcio goes into the LightRAG venv. Export is Simple by default, which is easy to get wrong. There are no FastAPI spans unless you add them by hand, so no grouping. And phoenix-otel has already broken once on a new OTel release (#16549).

Best for: nothing here that P1 doesn't do better.

P3. Phoenix in Docker (arizephoenix/phoenix:version-20.16.0, -p 127.0.0.1:6006:6006, 4317 not published)

Pros: it binds to localhost only, which avoids the [::]:4317 exposure. There's no 158-package host venv, and it's easy to throw away.

Cons: this machine's Docker VM has ≈ 0.9 GiB and 1 CPU, below Phoenix's 1 GiB request, and 5 containers already run in it. Raising the limit is a global Docker Desktop change. Docker has to be running whenever you want traces, the image is 362 MB, and the tracer side is the same as P1's.

Best for: a machine whose Docker VM has 2 GiB or more to spare.

P4. Phoenix Cloud (app.phoenix.arize.com)

Pros: no local server.

Cons: it brings back full content egress ([LF] §6.2), the free tier is unverified (U11), and there's an API key to manage.

Best for: never, in this context. It ranks last.

D. Stay local with no tracer (recommended)

D2 has the eval write a per-run JSON (rows, settings and summary). D3 has the eval record sentAt/receivedAt for each question and, after the run, parse lightrag.log within each window into the 4 phases. It flags windows that are ambiguous or hit the cache, and prints p50/p90 per phase.

Pros: no dependencies, no extra process, no egress and no CI impact. It answers the open question of where the 9 s go, and it makes run-to-run diffs possible.

Cons: no token counts, and it's weaker under concurrent traffic. It depends on the format of LightRAG's INFO log lines, which could change on an upgrade, so the upgrade runbook should re-check them. There's no UI.

Best for: now.

9. Recommendation

The recommended option is D (D2 + D3), with P1 researched and ready as the escalation.

D is the boring option: it has no dependencies and already breaks latency down into the phases that matter. Today's log samples point at the answer LLM call as the dominant phase (4.3-11.2 s), with the query embedding at about 1.4-1.8 s. Those samples came from mixed callers and parameters (top_k 20/40/30, one MCP call with rerank), so the first D3 run at the hook's own settings is what confirms the split.

The likely next moves don't need tracing to judge: a smaller context, a different mode or model, or a different recall budget. Each one is a parameter change plus an eval run, and D2's run diff measures the effect. Phoenix's extra signal (tokens, retries, per-request trees) wouldn't change those decisions yet, and it costs a second Python env, 16 packages in the LightRAG venv and an always-on process on a machine with 3 GB free.

Escalate to P1 when any of these holds:

  1. After two or more D3 runs, the phase split is unstable or unexplained. One example is high variance in the answer phase that might be ShopAIKey retries rather than context size.
  2. Tuning needs per-call prompt-token counts, to relate context size to latency.
  3. You need to analyse live hook or MCP traffic, where D3's timestamp join is ambiguous because requests overlap.

If you do escalate, P1 needs all of the following:

  • the exact pins in §4.6;
  • the env lines in §11 Part B, including the protocol, the none exporters, the endpoint and all four OPENINFERENCE_HIDE_*=true;
  • PHOENIX_HOST=127.0.0.1, PHOENIX_ALLOW_EXTERNAL_RESOURCES=false, PHOENIX_TELEMETRY_ENABLED=false, PHOENIX_DISABLE_AGENT_ASSISTANT=true, PHOENIX_ENABLE_MCP_SERVER=false and PHOENIX_DEFAULT_RETENTION_POLICY_DAYS=14;
  • setlocal added to start-rag.bat;
  • a passing V5 latency gate;
  • a 2-week time box.

When not to do P1, or any Phoenix option:

  • while RAM is tight, for instance during Playwright suite runs with browsers open (stop Phoenix then);
  • if masking can't stay on by default;
  • if you're not willing to maintain the second env on both machines, or to leave the second machine untraced;
  • never call register() without batch=True;
  • never use the opentelemetry-instrument wrapper on Windows;
