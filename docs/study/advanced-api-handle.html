01

Global setup and reusable auth state

Log in once, hand the session to every test
Context
EN

Enterprise API suites can carry hundreds or thousands of test cases, and nearly all of them need a valid token or cookie before they can do anything.

VI

Hệ thống test API của doanh nghiệp có thể có hàng trăm, hàng nghìn test case, và gần như tất cả đều cần token hoặc cookie hợp lệ trước khi làm được bất cứ điều gì.

Why it's hard
EN

Calling /login separately in every file or every scenario slows the whole suite down by five to ten times, burns test-environment resources, and puts unnecessary load on the login gateway.

VI

Gọi lại /login riêng ở từng file hoặc từng kịch bản làm cả suite chạy chậm đi năm đến mười lần, tốn tài nguyên môi trường test, và dồn tải không cần thiết lên gateway đăng nhập.

Solution
EN

Split the authentication flow out using Playwright's project dependency feature: run one setup project before anything else, save the resulting token or cookie to a temporary JSON file, and load it automatically into every request afterward.

VI

Tách luồng xác thực ra bằng tính năng project dependency của Playwright: chạy một project setup duy nhất trước mọi thứ khác, lưu token hoặc cookie thu được vào file JSON tạm, rồi tự động nạp lại cho mọi request sau đó.

In practice
EN

In playwright.config.ts, declare a project named setup that runs the login file. In the main api-tests project, set dependencies: ['setup'] and load the token automatically with storageState: 'path/to/auth.json'.

VI

Trong playwright.config.ts, khai báo một project tên setup chạy file đăng nhập. Ở project chính api-tests, đặt dependencies: ['setup'] và nạp token tự động bằng storageState: 'path/to/auth.json'.

EN

Logging in before every test works, but it gets slower as the suite grows, and CI feels it first. Playwright can authenticate once inside a dedicated setup project, save the resulting cookies and tokens to a JSON file, and hand that file to every other project through storageState. Tests start already signed in.

VI

Đăng nhập lại ở từng test vẫn chạy được, nhưng suite càng lớn thì càng chậm, và CI là nơi cảm nhận rõ nhất. Playwright cho phép đăng nhập một lần trong một project setup riêng, lưu cookie và token vào file JSON, rồi truyền file đó cho các project còn lại qua storageState. Test bắt đầu chạy là đã ở trạng thái đăng nhập sẵn.

→
EN

The saved token file is credentials on disk, gitignore it. This repo already excludes .auth/ for exactly that reason.

VI

File token đã lưu chính là credential nằm trên đĩa, nên phải gitignore nó. Repo này đã loại trừ .auth/ vì đúng lý do đó.

playwright.config.ts TypeScript 
import { defineConfig } from '@playwright/test';

export default defineConfig({
  projects: [
    // Runs once, authenticates, and writes the token/cookie file
    {
      name: 'setup',
      testMatch: /global\.setup\.ts/,
    },
    // Inherits the saved state, starts every test already logged in
    {
      name: 'api-tests',
      use: {
        storageState: 'playwright/.auth/user.json',
      },
      dependencies: ['setup'],
    },
  ],
});
02

Isolated API contexts for multi-role tests

Admin and regular user, side by side, in one test
Context
EN

Integration scenarios need to verify permissions across several roles acting at once: an admin creating a post, a manager approving it, and a member who shouldn't be able to edit it at all.

VI

Kịch bản kiểm thử tích hợp cần xác thực phân quyền giữa nhiều vai trò hoạt động cùng lúc: admin tạo bài viết, manager phê duyệt, và member thì không được phép chỉnh sửa.

Why it's hard
EN

Playwright's default { request } fixture shares one configuration and one login token per run, so there's no way to act as several roles inside a single test.

VI

Fixture { request } mặc định của Playwright dùng chung một cấu hình và một token đăng nhập cho mỗi lần chạy, nên không thể đóng vai nhiều role trong cùng một test.

Solution
EN

Spin up fully isolated HTTP contexts straight from Playwright's core library, right inside the body of one test.

VI

Khởi tạo các HTTP context hoàn toàn biệt lập ngay từ thư viện lõi của Playwright, ngay trong thân của một test.

In practice
EN

Instead of the default { request }, pull { playwright } into the test function. Create separate contexts, e.g. const adminContext = await playwright.request.newContext({ extraHTTPHeaders: { Authorization: 'Bearer ADMIN_TOKEN' } }), and do the same for each other role to fire requests in parallel.

VI

Thay vì { request } mặc định, gọi { playwright } vào hàm test. Tạo context riêng, ví dụ const adminContext = await playwright.request.newContext({ extraHTTPHeaders: { Authorization: 'Bearer ADMIN_TOKEN' } }), và làm tương tự cho các vai trò khác để gửi request song song.

EN

Permission tests need two identities at once: an admin who should succeed, and a regular user who should get blocked. playwright.request.newContext() creates a fresh HTTP context with its own headers and cookies, completely separate from any other context. Open one per role, assert on both, and neither one leaks into the other.

VI

Test phân quyền cần hai vai trò trong cùng một test: admin (phải thành công) và user thường (phải bị chặn). playwright.request.newContext() tạo ra một HTTP context mới với header và cookie riêng, hoàn toàn tách biệt với context khác. Mở riêng một context cho từng vai trò, assert trên cả hai, và không context nào ảnh hưởng đến context kia.

→
EN

A context created this way shares nothing with page either, useful when a test also drives the browser and needs the API calls kept separate from the UI session.

VI

Context tạo theo cách này cũng không chia sẻ gì với page, hữu ích khi test vừa thao tác trên browser vừa cần tách riêng API call khỏi session của UI.

multi-role.spec.ts TypeScript 
import { test, expect } from '@playwright/test';

test('admin can post, a regular user cannot delete', async ({ playwright }) => {
  const adminContext = await playwright.request.newContext({
    extraHTTPHeaders: { Authorization: 'Bearer ADMIN_SECRET_TOKEN' },
  });

  const userContext = await playwright.request.newContext({
    extraHTTPHeaders: { Authorization: 'Bearer USER_REGULAR_TOKEN' },
  });

  const resAdmin = await adminContext.post('/api/posts', {
    data: { title: 'Advanced Playwright' },
  });
  expect(resAdmin.status()).toBe(201);

  const resUser = await userContext.delete('/api/posts/1');
  expect(resUser.status()).toBe(403);
});
03

Polling asynchronous jobs

When the API answers before the work is done
Context
EN

Some systems queue work in the background. Calling an API that exports a large financial report or processes video doesn't return a result right away, it just answers 202 Accepted with a jobId.

VI

Nhiều hệ thống xử lý job ngầm. Gọi API xuất báo cáo tài chính lớn hay xử lý video sẽ không trả kết quả ngay, mà chỉ trả 202 Accepted kèm một jobId.

Why it's hard
EN

A test can't check the result immediately, the background job needs anywhere from a few seconds to a few minutes. A fixed sleep wastes time on average and still fails outright if the server lags more than expected.

VI

Test không thể kiểm tra kết quả ngay lập tức, vì job ngầm cần từ vài giây đến vài phút để xong. Sleep cố định vừa lãng phí thời gian trung bình, vừa fail hẳn nếu server lag hơn dự kiến.

Solution
EN

Playwright's built-in smart polling loop keeps checking on its own and stops the moment the condition is met.

VI

Vòng lặp polling thông minh có sẵn của Playwright tự kiểm tra lại theo chu kỳ và dừng ngay khi điều kiện đạt.

In practice
EN

Use await expect.poll(async () => { ... }, { intervals: [...], timeout: 30000 }). Inside the callback, call the job-status endpoint; the loop stops and passes once the result matches .toBe('COMPLETED').

VI

Dùng await expect.poll(async () => { ... }, { intervals: [...], timeout: 30000 }). Trong callback, gọi endpoint kiểm tra trạng thái job; vòng lặp dừng và pass khi kết quả khớp .toBe('COMPLETED').

EN

Some endpoints hand a job to a background worker and respond immediately with 202 Accepted. expect.poll calls a status endpoint on a schedule until the condition passes or the timeout runs out, so the test never needs a manual sleep loop.

VI

Một số endpoint giao job cho worker chạy nền và trả response ngay với 202 Accepted. expect.poll sẽ gọi lại endpoint kiểm tra trạng thái theo lịch cho đến khi điều kiện đúng hoặc hết timeout, nên test không cần tự viết vòng lặp sleep.

→
EN

Keep timeout longer than the sum of the intervals array, otherwise expect.poll gives up before the job has a real chance to finish.

VI

Giữ timeout dài hơn tổng của mảng intervals, nếu không expect.poll sẽ bỏ cuộc trước khi job có cơ hội chạy xong thật sự.

async-job.spec.ts TypeScript 
import { test, expect } from '@playwright/test';

test('waits for a background report job to finish', async ({ request }) => {
  const jobId = 'job_report_2026';

  await expect.poll(async () => {
    const response = await request.get(`/api/jobs/${jobId}`);
    const body = await response.json();
    return body.status;
  }, {
    message: 'Timed out waiting for the job to reach COMPLETED',
    intervals: [2_000, 5_000, 10_000],
    timeout: 45_000,
  }).toBe('COMPLETED');
});
04

Intercepting and mocking at the network layer

Answer the request yourself, skip the real server
Context
EN

Enterprise apps (SaaS, ERP, e-commerce) almost always gate the interface behind a successful login. A UI automation suite can carry hundreds or thousands of test cases that all need to get past that login screen before they can touch the feature underneath.

VI

Các hệ thống ứng dụng doanh nghiệp (SaaS, ERP, e-commerce) hầu hết đều yêu cầu đăng nhập thành công mới hiển thị giao diện thao tác. Bộ test UI automation có thể có hàng trăm, hàng nghìn test case đều cần vượt qua bước đăng nhập này trước khi chạm được vào tính năng nghiệp vụ bên trong.

Why it's hard
EN

If every spec file or every test drives the browser through the login page, types a username and password, and waits for the dashboard to load, the whole suite's CI runtime balloons, sometimes to several hours. Firing thousands of logins at once during parallel runs also chokes the test environment's auth gateway, producing random timeout failures.

VI

Nếu mỗi file kịch bản hay mỗi test case đều bắt trình duyệt mở trang login, gõ username/password rồi đợi Dashboard tải xong, thời gian chạy của cả suite trên CI/CD sẽ phình to, có khi lên tới nhiều tiếng đồng hồ. Việc dồn hàng nghìn lượt đăng nhập cùng lúc khi chạy song song cũng làm nghẽn gateway auth của môi trường test, gây ra lỗi timeout ngẫu nhiên.

Solution
EN

Set up the same global setup and auth storage bypass used for API tests, but through Playwright's project dependency feature for UI. One dedicated login spec runs once at the start of the run, captures the full session state (JWT token, cookies, and local storage) into a temporary JSON file, and that file gets injected into every other UI test's browser so it lands on the target page in about a second, no login screen involved.

VI

Áp dụng cùng cơ chế Global Setup và Auth Storage Bypass như ở test API, nhưng qua tính năng project dependency của Playwright cho UI. Một file setup đăng nhập riêng chạy đúng một lần ở đầu phiên, chụp lại toàn bộ trạng thái phiên (JWT token, cookie, local storage) vào một file JSON tạm, rồi file đó được "tiêm" vào trình duyệt của mọi test UI khác để vào thẳng trang đích trong khoảng một giây, không cần qua màn hình login.

In practice
EN

Create a dedicated setup file (e.g. auth.setup.ts) that opens the login page, fills in the test account, and saves the session with await page.context().storageState({ path: '.auth/user.json' }). In playwright.config.ts, declare a project named auth-setup that runs this file, then have the UI test projects depend on it and load the saved state through storageState.

VI

Tạo một file setup riêng (ví dụ auth.setup.ts) mở trang login, điền tài khoản test, rồi lưu trạng thái bằng await page.context().storageState({ path: '.auth/user.json' }). Trong playwright.config.ts, khai báo một project tên auth-setup chạy file này, sau đó cho các project test UI phụ thuộc vào nó và nạp lại trạng thái đã lưu qua storageState.

EN

page.route lets a test answer a browser request itself. That helps in two situations: building the frontend against an API that isn't ready yet, and forcing a rare error code, like a 500 or a 408, that's hard to reproduce against a live backend.

VI

page.route cho phép test tự trả lời một request của browser thay vì gửi đến server thật. Cách này hữu ích ở hai trường hợp: dựng frontend trước khi API thật sẵn sàng, và ép trả về một mã lỗi hiếm gặp như 500 hoặc 408, thứ khó tái hiện được trên backend thật.

→
EN

page.route only intercepts requests that go through the browser context. It has no effect on calls made through the standalone request fixture.

VI

page.route chỉ chặn được request đi qua browser context. Nó không có tác dụng với các call thực hiện qua fixture request độc lập.

route-mock.spec.ts TypeScript 
import { test, expect } from '@playwright/test';

test('shows a friendly error banner when the products API is down', async ({ page }) => {
  await page.route('**/api/v1/products', async (route) => {
    await route.fulfill({
      status: 500,
      contentType: 'application/json',
      body: JSON.stringify({ message: 'Internal Server Error' }),
    });
  });

  await page.goto('/dashboard');

  await expect(page.locator('.error-banner-message'))
    .toContainText('Something went wrong. Please try again.');
});
05

Custom fixtures that attach failure context automatically

Keep passing-test reports clean, capture detail only when it matters
Context
EN

When a suite runs unattended on CI, a plain failure report rarely shows what was actually wrong with the request that failed, so QA ends up re-running the same scenario locally just to see the payload.

VI

Khi suite chạy tự động trên CI, báo cáo lỗi thông thường hiếm khi cho thấy request bị fail thực sự có vấn đề gì, khiến QA phải chạy lại kịch bản đó trên máy cá nhân chỉ để xem payload.

Why it's hard
EN

Playwright doesn't attach request or response bodies and headers to the HTML report on its own, unless someone sprinkles console.log calls everywhere, which clutters the code and gets harder to maintain over time.

VI

Playwright không tự đính kèm body hay header của request/response vào report HTML, trừ khi ai đó rải console.log khắp nơi, việc này làm bẩn mã nguồn và ngày càng khó bảo trì.

Solution
EN

Extend the base test with a custom fixture that acts as a silent listener, capturing the request details and attaching them to the report only when the test actually fails.

VI

Mở rộng test gốc bằng một custom fixture đóng vai trò bộ lắng nghe ngầm, tự bắt thông tin chi tiết của request và chỉ đính kèm vào report khi test thật sự fail.

In practice
EN

Use base.extend to declare a custom fixture, for example apiDebug. Inside it, call await use(request) to let the test run, then check if (testInfo.status !== testInfo.expectedStatus) and call testInfo.attach() to attach the failing payload to the report.

VI

Dùng base.extend để khai báo một fixture tùy biến, ví dụ apiDebug. Bên trong, gọi await use(request) để test chạy qua, rồi kiểm tra if (testInfo.status !== testInfo.expectedStatus) và gọi testInfo.attach() để đính kèm payload lỗi vào report.

EN

Attaching the full request and response payload to every test report gets noisy fast, most tests pass and don't need it. A custom fixture can wrap the request context, let the test run, then check testInfo.status afterward and attach the payload only when the test actually failed.

VI

Đính kèm toàn bộ request và response vào report của mọi test sẽ nhanh chóng gây rối, vì phần lớn test pass và không cần đến nó. Một custom fixture có thể bọc request context, để test chạy xong rồi mới kiểm tra testInfo.status, và chỉ đính kèm payload khi test thật sự fail.

→
EN

This framework's own attachTestLogs fixture in base-test.ts and ApiTest.ts follows the same wrap-then-teardown shape, though it flushes on every test rather than gating on failure, since step logs are useful on passing tests too.

VI

Fixture attachTestLogs của chính framework này trong base-test.ts và ApiTest.ts dùng cùng cấu trúc bọc rồi xử lý ở teardown, nhưng nó flush ở mọi test chứ không chỉ khi fail, vì log các bước vẫn hữu ích cả khi test pass.

smart-request-fixture.ts TypeScript 
import { test as base, expect } from '@playwright/test';
import type { APIRequestContext } from '@playwright/test';

type Fixtures = {
  smartRequest: APIRequestContext;
};

export const test = base.extend<Fixtures>({
  smartRequest: async ({ request }, use, testInfo) => {
    await use(request);

    // Runs after the test body, testInfo.status is final by now
    if (testInfo.status !== testInfo.expectedStatus) {
      await testInfo.attach('failed-request-context', {
        body: JSON.stringify(
          { status: testInfo.status, error: testInfo.error?.message },
          null,
          2
        ),
        contentType: 'application/json',
      });
    }
  },
});

export { expect };

API chaining behind a controller

One method for a workflow that needs several requests
Context
EN

Real API scenarios almost always run as a chain: create a category, grab its ID to create a product, grab that product's ID to run checkout.

VI

Kịch bản API thật hầu như luôn chạy theo chuỗi: tạo danh mục, lấy ID vừa tạo để tạo sản phẩm, lấy ID sản phẩm đó để gọi thanh toán.

Why it's hard
EN

Writing every one of those HTTP calls nested directly inside the test file turns the code messy fast, hard to read, impossible to reuse for other flows, and it breaks basic clean-code practice.

VI

Viết toàn bộ các lệnh gọi HTTP đó lồng trực tiếp trong file test khiến mã nguồn nhanh chóng rối, khó đọc, không tái sử dụng được cho luồng khác, và vi phạm nguyên tắc clean code cơ bản.

Solution
EN

Wrap the chain behind a controller class: a dedicated class for one API's business logic that packages the chained steps into clear, named methods.

VI

Gói chuỗi lệnh gọi đó vào một controller class: một class riêng cho logic nghiệp vụ của một API, đóng gói các bước kết chuỗi thành các method rõ ràng, có tên gọi.

In practice
EN

Create a ProductController class that takes an APIRequestContext. Write an async createAndPublishProduct(payload) method inside it that runs the create-then-publish chain automatically. The test file only has to instantiate the class and call that one method.

VI

Tạo class ProductController nhận vào một APIRequestContext. Viết method async createAndPublishProduct(payload) bên trong để tự chạy chuỗi tạo rồi publish. File test chỉ cần khởi tạo class và gọi đúng một method đó.

EN

Real workflows rarely fit in one request. Creating a product, then publishing it, then confirming it shows up in search is three calls with a dependency between them: the second needs an ID the first one returned. Writing that chain inline inside a test file works once, then gets copy-pasted into the next test and drifts. A controller class wraps the chain in one method, so the test calls one thing and asserts on the outcome.

VI

Luồng nghiệp vụ thật hiếm khi gói gọn trong một request. Tạo sản phẩm, publish nó, rồi xác nhận nó xuất hiện trong kết quả tìm kiếm là ba lệnh gọi có phụ thuộc lẫn nhau: lệnh thứ hai cần ID mà lệnh đầu trả về. Viết chuỗi này trực tiếp trong file test thì chạy được một lần, rồi bị copy sang test tiếp theo và dần lệch nhau. Một controller class gói cả chuỗi vào một method, để test chỉ gọi một hàm và assert trên kết quả.

→
EN

Same idea as this framework's page objects, just for API calls instead of UI elements: put reused, multi-step logic in one place, keep the test file about assertions.

VI

Cùng ý tưởng với page object của framework này, chỉ khác là áp dụng cho API call thay vì element UI: đặt logic nhiều bước, dùng lại nhiều lần vào một chỗ, để file test chỉ tập trung vào assertion.

controllers/product-controller.ts TypeScript 
import { APIRequestContext } from '@playwright/test';

export class ProductController {
  constructor(private readonly request: APIRequestContext) {}

  async createAndPublishProduct(payload: { name: string; price: number }) {

    const publishResponse = await this.request.put(`/v1/products/${productId}/publish`);

    return {
      productId,
      publishStatus: publishResponse.status(),
      success: publishResponse.ok(),
    };
  }
}

Context
EN

VI

EN

VI

Solution
EN

Isolate test resources by combining Playwright's worker index with a library that generates unique random data.

VI

Cô lập tài nguyên test bằng cách kết hợp chỉ số worker của Playwright với một thư viện sinh dữ liệu ngẫu nhiên duy nhất.

In practice
EN

EN

Running with several workers means several test files hit the same environment at once. VI

→
EN

TEST_WORKER_INDEX resets between shards in a matrix CI run, so it's unique within one shard, not globally across every shard. Combine it with the shard index, or with faker-generated data, when the suite runs sharded.

VI

TEST_WORKER_INDEX reset lại giữa các shard trong một CI chạy theo matrix, nên nó chỉ duy nhất trong một shard, không duy nhất trên toàn bộ các shard. Kết hợp nó với chỉ số shard, hoặc với dữ liệu sinh bằng faker, khi suite chạy theo shard.

Context
EN

An API automation suite running daily against staging or UAT builds up tens of thousands of leftover records inside the company's database over time.

Context
EN

When the backend ships new code, an unoptimized database query can slip through and visibly slow an API's response time, hurting the user experience.

VI

Khi Backend đưa mã nguồn mới lên, một câu truy vấn database chưa tối ưu có thể lọt qua và làm chậm rõ rệt thời gian phản hồi của API, ảnh hưởng đến trải nghiệm người dùng.

Why it's hard
EN

Ordinary functional tests only check whether the data is right, not how long it took, so a serious performance regression can pass on CI without anyone noticing.

VI

Test chức năng thông thường chỉ kiểm tra dữ liệu đúng hay sai, không quan tâm thời gian phản hồi, nên một regression hiệu năng nghiêm trọng vẫn có thể pass trên CI mà không ai nhận ra.

Solution
EN

Fold an SLA (service level agreement) commitment directly into the test as a measurable check, using Node's performance timer.

VI

Đưa cam kết SLA (service level agreement) trực tiếp vào test như một điều kiện đo lường được, tận dụng bộ đếm thời gian performance của Node.js.

In practice
EN

Call performance.now() right before firing the request. After the response comes back from Playwright, take the end timestamp and compute const duration = endTime - startTime. Use expect(duration).toBeLessThan(500) to fail the test if the API takes longer than 500ms.

VI

Gọi performance.now() ngay trước khi gửi request. Sau khi nhận response từ Playwright, lấy mốc kết thúc và tính const duration = endTime - startTime. Dùng expect(duration).toBeLessThan(500) để đánh fail nếu API chạy quá 500ms.

EN

A test that only checks the status code misses a real class of regression: a slow endpoint that still answers correctly. Node's performance.now() measures wall-clock time around the request with sub-millisecond precision, and asserting on that duration turns an SLA commitment into a check that fails on CI the day it's broken, instead of showing up in a monitoring dashboard three days later.

VI

Một test chỉ kiểm tra status code sẽ bỏ sót cả một loại regression thật: endpoint trả lời chậm nhưng vẫn đúng dữ liệu. performance.now() của Node đo thời gian thực quanh request với độ chính xác dưới mili-giây, và assert trên khoảng thời gian đó biến một cam kết SLA thành một check fail ngay trên CI vào đúng ngày nó bị vi phạm, thay vì ba ngày sau mới xuất hiện trên dashboard giám sát.

→
EN

CI runners are shared hardware and slower than a laptop, so a threshold tuned locally will flake in CI. Read the SLA threshold from an env var so it can be relaxed for CI without touching the test.

VI

CI runner là phần cứng dùng chung và chậm hơn máy laptop, nên một ngưỡng canh trên máy cá nhân sẽ dễ flake trên CI. Đọc ngưỡng SLA từ một biến môi trường để có thể nới lỏng riêng cho CI mà không cần sửa test.

Signed and encrypted payloads

Compute the same HMAC signature the backend expects
Context
EN

To stop an attacker from intercepting or tampering with a financial transaction in transit, many systems require the payload to be fully encrypted or to carry a digital signature in a header, like X-Signature.

VI

Để ngăn kẻ tấn công nghe lén hoặc chỉnh sửa nội dung giao dịch tài chính trên đường truyền, nhiều hệ thống yêu cầu payload phải được mã hóa hoàn toàn hoặc kèm một chữ ký điện tử trên header, ví dụ X-Signature.

Why it's hard
EN

Sending a plain JSON payload without that signature gets caught by the backend gateway's security layer and rejected outright with a 401 Unauthorized.

VI

Gửi một payload JSON thông thường không có chữ ký sẽ bị lớp bảo mật ở gateway của Backend phát hiện và từ chối ngay với lỗi 401 Unauthorized.

Solution
EN

Write a small helper that hashes the payload with Node's built-in crypto library and a private key before the request goes out.

VI

Viết một helper nhỏ băm payload bằng thư viện crypto có sẵn của Node.js cùng một private key trước khi gửi request.

In practice
EN

crypto.createHmac('sha256', privateKey).update(JSON.stringify(payload)).digest('hex') produces the signature. Pass that string into the request header as headers: { 'X-Signature': signature }.

VI

crypto.createHmac('sha256', privateKey).update(JSON.stringify(payload)).digest('hex') cho ra chữ ký. Truyền chuỗi đó vào header request dạng headers: { 'X-Signature': signature }.

EN

Financial and healthcare APIs often reject a request outright unless it carries a signature proving the body wasn't altered in transit, usually an HMAC computed over the JSON payload with a shared secret. Node's built-in crypto module computes the same signature the backend expects, so a test can send a normal request and still pass the tampering check.

VI

API trong lĩnh vực tài chính và y tế thường từ chối thẳng một request nếu nó không mang chữ ký chứng minh phần body chưa bị thay đổi trên đường truyền, thường là một HMAC tính trên payload JSON bằng một secret dùng chung. Module crypto có sẵn của Node tính ra đúng chữ ký mà backend đang mong đợi, nhờ vậy test có thể gửi một request bình thường mà vẫn vượt qua kiểm tra chống giả mạo.

→
EN

Signing depends on byte-for-byte matching between what got signed and what got sent. Compute the signature from the exact object that goes in the data field, not a re-serialized copy, or a difference in key order can produce a mismatched signature.

VI

Two-way contract testing with Pact

Catch a broken contract on the backend's side, before it ships
Context
EN

On large projects, frontend and backend teams build independently, and the backend can quietly change a field's structure without telling the frontend team in time.

VI

Ở các dự án lớn, đội Frontend và Backend phát triển độc lập, và Backend có thể âm thầm đổi cấu trúc một trường dữ liệu mà không kịp báo cho Frontend.

Why it's hard
EN

One-way validation with Zod on the client side only catches the mismatch after the backend's code has already deployed to a shared environment, which means a late fix and a costly rollback.

VI

Xác thực một chiều bằng Zod ở phía Client chỉ phát hiện ra lỗi sau khi code của Backend đã deploy lên môi trường dùng chung, nghĩa là sửa muộn và phải rollback tốn kém.

Solution
EN

Pair the Pact library with Playwright to run bi-directional contract testing. Playwright generates a .pact file that describes exactly what data shape the frontend needs, and the backend's CI is required to run against that file and pass before it can merge.

VI

Kết hợp thư viện Pact với Playwright để chạy kiểm thử hợp đồng hai chiều. Playwright sinh ra một file .pact mô tả chính xác cấu trúc dữ liệu Frontend cần, và CI của Backend bắt buộc phải chạy qua file này và pass trước khi được merge.

In practice
EN

Declare new PactV3({ consumer: 'Frontend', provider: 'Backend' }). Use matcher functions like MatchersV3.email and MatchersV3.like to build the expected contract shape. Run the test to produce the .pact file, then configure CI to push it to the project's shared Pact Broker.

VI

Khai báo new PactV3({ consumer: 'Frontend', provider: 'Backend' }). Dùng các hàm matcher như MatchersV3.email, MatchersV3.like để dựng khung hợp đồng kỳ vọng. Chạy test để xuất file .pact, rồi cấu hình CI đẩy file đó lên Pact Broker chung của dự án.

EN

Zod schemas catch a broken contract, but only after the fact: the backend already shipped the breaking change, and the test only finds out the next time it runs. Pact inverts that order. The consumer test generates a contract file describing exactly what it expects from the backend, publishes it to a shared Pact Broker, and the backend's own CI pipeline is required to verify against that file before it can merge. A breaking change gets caught on the backend's side, before it reaches a shared environment.

VI

Schema Zod phát hiện được hợp đồng bị vỡ, nhưng chỉ sau khi việc đã rồi: backend đã deploy thay đổi phá vỡ cấu trúc, và test chỉ biết được ở lần chạy tiếp theo. Pact đảo ngược thứ tự đó. →
EN

VI

You're handed the job of writing API automation for an old legacy system, no API documentation, no Swagger, and the team that built it is long gone.

VI

Bạn được giao viết automation test API cho một hệ thống cũ (legacy), không có tài liệu API, không có Swagger, và đội làm ra nó đã nghỉ việc từ lâu.

Why it's hard
EN

Sitting down with Fiddler or Charles Proxy to manually trace every request, payload, and header behind each button click, then hand-typing it into Playwright API code, takes weeks for any workflow of real length.

VI

Ngồi bật Fiddler hay Charles Proxy để dò tay từng request, từng payload, từng header đằng sau mỗi cú bấm, rồi gõ lại thành code Playwright API thủ công, sẽ mất hàng tuần với bất kỳ luồng nghiệp vụ nào đủ dài.

Solution
EN

Use Playwright UI's built-in HAR recording (HTTP Archive) to silently capture network traffic and export it as JSON, then convert that file into API test source code with a script.

VI

Dùng tính năng ghi HAR (HTTP Archive) có sẵn trong Playwright UI Test để âm thầm "nghe" lưu lượng mạng và xuất ra file JSON, rồi dùng script chuyển file đó thành mã nguồn test API.

In practice
EN

When creating the browser context, set recordHAR: { path: './flows/checkout.har', mode: 'full' }. Run through the flow like a real user. Playwright exports a .har file with every request and response captured, and a short conversion tool or Node.js script turns that JSON straight into Playwright API test code.

VI

Khi khởi tạo browser context, bật recordHAR: { path: './flows/checkout.har', mode: 'full' }. Thao tác qua luồng như người dùng thật. Playwright xuất ra file .har chứa đầy đủ request/response, và một công cụ chuyển đổi hay script Node.js ngắn sẽ dịch file JSON đó thẳng thành mã nguồn test API Playwright.

EN

A legacy system with no API documentation and no Swagger file leaves manual request discovery as the only option, and that's slow. Playwright can record every request a browser context makes while a person, or a UI test, clicks through a real flow, and write it all to a .har file with full request and response bodies. Parsing that file for endpoint, method, and payload turns discovery into a script instead of a person clicking through dev tools.

VI

Một hệ thống legacy không có tài liệu API, không có file Swagger, khiến việc dò request bằng tay trở thành lựa chọn duy nhất, và cách đó rất chậm. Playwright có thể ghi lại từng request mà một browser context tạo ra trong khi một người, hoặc một UI test, thao tác qua một luồng thật, rồi ghi tất cả vào một file .har kèm đầy đủ request và response body. Parse file đó để lấy endpoint, method và payload biến việc dò tìm thành một script thay vì một người ngồi click qua dev tools.

→
EN

Full HAR capture includes response bodies, which can carry real customer data if the recording runs against a live environment. Record against a seeded test environment, never production.

VI

Ghi HAR ở chế độ full bao gồm cả response body, thứ có thể chứa dữ liệu khách hàng thật nếu việc ghi chạy trên môi trường live. Ghi trên một môi trường test đã được seed sẵn, không bao giờ ghi trên production.

import { test } from '@playwright/test';

test('records the network traffic behind a checkout flow', async ({ browser }) => {
  const context = await browser.newContext({
    recordHAR: {
      path: './artifacts/checkout-flow.har',
      mode: 'full',
    },

  const page = await context.newPage();
  await page.goto('https://company.com');

  await page.locator('.product-card').first().click();
  await page.locator('#add-to-cart').click();

  await context.close();
});

A data-driven authorization matrix

One loop instead of one test per role and endpoint combination
Context
EN

A large enterprise's internal management app can have very complex permissions: admin can do everything, manager can only approve, member can only view, guest can't get in at all.

VI

Ứng dụng quản lý nội bộ của doanh nghiệp lớn có thể có phân quyền cực kỳ phức tạp: admin làm được mọi thứ, manager chỉ được duyệt, member chỉ được xem, guest không được vào.

Why it's hard
EN

Writing a separate test file for every role against every endpoint balloons the test code to thousands of duplicated lines, and adding one new role means touching every one of those files.

VI

Viết riêng một file test cho từng vai trò với từng endpoint khiến mã test phình to hàng nghìn dòng trùng lặp, và thêm một vai trò mới nghĩa là phải sửa lại toàn bộ các file đó.

Solution
EN

Design data-driven testing built on a permission matrix expressed as a JSON table: define every combination of role, method, endpoint, and expected status code, then generate the test cases from a single loop.

VI

Thiết kế kiểm thử hướng dữ liệu dựa trên ma trận phân quyền dạng bảng JSON: định nghĩa mọi tổ hợp vai trò, method, endpoint và status code kỳ vọng, rồi sinh test case từ một vòng lặp duy nhất.

In practice
EN

Define the data array, e.g. const matrix = [ { role: 'admin', endpoint: '/users', expected: 201 }, { role: 'member', endpoint: '/users', expected: 403 } ]. Use for (const scenario of matrix) { test(...) } to generate every test case. Inside the test body, create a newContext with an Authorization header that matches whichever role's token is currently being checked.

VI

Định nghĩa mảng dữ liệu, ví dụ const matrix = [ { role: 'admin', endpoint: '/users', expected: 201 }, { role: 'member', endpoint: '/users', expected: 403 } ]. Dùng for (const scenario of matrix) { test(...) } để sinh mọi test case. Trong thân test, tạo newContext với header Authorization tương ứng với token của vai trò đang được kiểm tra.

EN

A permission system with several roles and several endpoints turns into a wall of near-identical tests if each combination gets its own test() block written by hand: same request, same assertion, only the role and the expected status differ. Looping over an array of role, method, endpoint, and expected status, and calling test() once per entry, generates the same coverage from one block. Adding a role or an endpoint to the matrix becomes a data change, not a new test to write.

VI

Một hệ thống phân quyền với nhiều vai trò và nhiều endpoint sẽ biến thành một bức tường test gần như giống hệt nhau nếu mỗi tổ hợp được viết tay thành một block test() riêng: cùng request, cùng assertion, chỉ khác vai trò và status kỳ vọng. Lặp qua một mảng gồm vai trò, method, endpoint và status kỳ vọng, rồi gọi test() một lần cho mỗi phần tử, sẽ sinh ra cùng độ phủ đó từ một block. Thêm một vai trò hay endpoint mới vào ma trận trở thành thay đổi dữ liệu, không phải viết thêm test.

→
EN

The matrix lives as inline data here because the example is small. Past a handful of rows it belongs in src/data/api/ as a named, typed export, same as any other test data in this framework.

VI

Ma trận ở đây để inline vì ví dụ này nhỏ. Khi vượt quá vài dòng, nó nên chuyển vào src/data/api/ dưới dạng export có tên và có kiểu, giống mọi dữ liệu test khác trong framework này.

authorization-matrix.spec.ts TypeScript 
import { test, expect } from '@playwright/test';

interface AuthzScenario {
  role: string;
  method: 'GET' | 'POST';
  endpoint: string;
  expectedStatus: number;
}

const authorizationMatrix: AuthzScenario[] = [
  { role: 'admin',   method: 'POST', endpoint: '/api/v1/users', expectedStatus: 201 },
  { role: 'manager', method: 'POST', endpoint: '/api/v1/users', expectedStatus: 201 },
  { role: 'member',  method: 'POST', endpoint: '/api/v1/users', expectedStatus: 403 },
  { role: 'member',  method: 'GET',  endpoint: '/api/v1/users', expectedStatus: 200 },
  { role: 'guest',   method: 'GET',  endpoint: '/api/v1/users', expectedStatus: 401 },
];

for (const scenario of authorizationMatrix) {
  test(`role ${scenario.role} gets ${scenario.expectedStatus} on ${scenario.method} ${scenario.endpoint}`, async ({ playwright }) => {
    const context = await playwright.request.newContext({
      extraHTTPHeaders: {
        Authorization: `Bearer TOKEN_FOR_${scenario.role.toUpperCase()}`,
      },
    });

    const response = await context.fetch(scenario.endpoint, {
      method: scenario.method,
      data: scenario.method !== 'GET' ? { name: 'Automation Test' } : undefined,
    });

    expect(response.status()).toBe(scenario.expectedStatus);
  });
}
