Elevator pitch and cheat sheet

The whole framework as one spoken answer, plus a table to drill the details
Spoken answer (interview-ready)

It's a TypeScript Playwright framework for a group of ecommerce storefronts: Platypus, Skechers, Vans and Dr. Martens, each in Australia and New Zealand, so eight sites. It covers the UI, REST and GraphQL, and it runs through two separate Playwright configs. The UI config runs Chromium and Firefox with half the machine's workers. The API config runs eight workers, one per brand and region, and keeps the tests inside a spec file in order, because the checkout specs build on each other's cart and address state.

Architecturally, I moved away from the classic page object model where every page inherits a bloated base class full of unrelated methods. Every page still extends a BasePage, but BasePage doesn't touch the browser itself. It holds eleven helper objects: waits, element interaction, computed styles, iframes, file uploads, storage and cookies, network mocking, tables, tabs and dialogs, read-only DOM scans, and popup dismissal. So a page class calls this.elements.clickElement() instead of page.click(), and a new kind of browser interaction goes into the right helper, not into BasePage.

Locators always live as private readonly fields at the top of the class, never inline inside a method or an evaluate call, and I prefer getByRole and getByLabel over CSS so tests don't break every time the DOM shifts.

Test setup uses dependency injection. A custom base-test.ts extends Playwright's own test object and registers every page object as a fixture, so a test asks for ecommercePDPPage or ecommerceCheckoutPage as an argument and Playwright hands it a fresh instance for that test.

Test data never sits in a spec. It lives in src/data, as a typed constant or a generator class, always behind a named interface. On the API side, responses are also checked against Zod schemas, so a field that changes type fails the test even when the status code is still 200.

Under that there's the plumbing that keeps a big suite readable: a soft-assertion helper that collects independent checks and reports every failure together, timeout constants that get longer in CI, a per-test step log attached to the report, console and API logs that are attached only when a test fails (with secrets redacted), and a monocart reporter that keeps trend history so I can see whether something is getting flakier.

The newer part is the AI layer. The repo is set up for Claude Code: CLAUDE.md files hold the conventions, and there are 14 agents with an orchestrator in front that picks a pipeline. A new test goes architect, then reviewer. A red build goes CI analyst, then healer, then reviewer. Hooks block destructive shell commands, type-check before Claude stops, and rerun any spec it just edited. Project knowledge lives in a markdown memory vault that LightRAG indexes, and each prompt gets the most relevant notes injected automatically.

ConsoleHelper is not a BasePage field. Tests get it as the consoleHelper auto-fixture.

Never call page.locator() or page.click() inside a page class. Go through the helpers (this.elements.clickElement(), this.waits.waitForElement()), and declare every locator as a private readonly field at the top of the class, not inline in a method body.
Correct
class ProductPage extends BasePage {
  // 1. Locators hoisted to class fields
  private readonly addToCartBtn =
    this.page.getByRole('button', { name: 'Add to Cart' });
  private readonly priceSelector =
    '[data-testid="product-price"]';

  async addToCart(): Promise<void> {
    // 2. Delegate to a helper
    await this.elements.clickLocator(this.addToCartBtn);
  }

  async getPrice(): Promise<string> {
    return this.elements.getText(this.priceSelector);
  }
}
Banned
class ProductPage extends BasePage {
  async addToCart(): Promise<void> {
    // WRONG: direct page.click()
    await this.page.click('button:has-text("Add")');

    // WRONG: selector inlined in a helper call
    await this.elements.clickElement(
      '[data-testid="add-to-cart"]');

    // WRONG: structural CSS selector
    await this.page.locator(
      'div > section > ul > li:nth-child(2) > button')
      .click();
  }
}

import { graTest as test, expect, softExpect } from './gra-test';
import { GraSearchData } from '../../src/data/api/gra-search-data';

const PRODUCT_SEARCH_QUERY = `
  query ProductSearch($search: String!, $pageSize: Int, $currentPage: Int) {
    products(search: $search, pageSize: $pageSize, currentPage: $currentPage) {
      total_count
      items { sku name }
    }
  }
`;

test.describe('GRA Search API @api @graphql @regression', () => {
  test('TC_01 - products - valid search term returns non-empty results',
    async ({ createGraphQLClient, site }) => {
    const client = await createGraphQLClient();
    // site comes from the brand project, so this one test runs 8 times
    const response = await client.queryWrapped(PRODUCT_SEARCH_QUERY, {
      search: site.catalogSearchTerm,
      pageSize: GraSearchData.pagination.pageSize,
      currentPage: 1,
    });

    await response.assertNoErrors(); // always first
    const data = await response.getData();
    expect(data.products).toBeDefined();
    softExpect(data.products.total_count).toBeGreaterThan(0);
  });
});

Rules that are easy to get wrong

RuleWhy
No test.describe.configure({ mode: 'serial' }) in new specsfullyParallel: false already keeps file order. Serial mode only adds cascade-skips that hide which tests really broke.
Setup that later tests depend on goes in beforeAllAfter a failure, the replacement worker reruns beforeAll but not the tests that already ran.
GraphQL operations are module-level constsThey move to src/data/api/gra-graphql-operations.ts only when two or more spec files use the same operation.
New sensitive fields get added to src/utils/redact.ts firstVERBOSE_LOGS is on by default, and redaction is a denylist of known keys rather than a guarantee.
Never interpolate variables into a GraphQL string. Pass them as the variables argument: queryWrapped(QUERY, { id }). Interpolation opens an injection hole and defeats query caching. Also check errors?.length, not a bare if (errors), because an empty array is truthy.

What happens to one prompt

1
The prompt hook adds context
user-prompt-submit.js appends the current branch and recent commits, the most relevant memory notes from LightRAG, the active coding rules, and a hint about which skill or agent fits. If LightRAG doesn't answer within 9 seconds, the prompt goes through without the memory part.
2
The main session picks a route
Small tasks it does itself. A matching skill or slash command gets loaded. Multi-step QA work goes to qa-orchestrator, which dispatches sub-agents in a fixed order (section 07).
3
Hooks watch the tool calls
pre-tool-use.js blocks destructive shell commands before they run. After an edit, sync-memory.js pushes changed vault notes to LightRAG and yaml-check.js parses any YAML file that changed. advisor-nudge.js suggests advisor() once the same test run or edit repeats three times.
4
Stop hooks check the result
Before Claude can finish, tsc --noEmit has to pass. run-changed-specs.js runs up to three spec files edited in the turn and wakes Claude if one fails. The vault sync status is reported, and Claude gets a nudge to save a memory note if the session learned something but wrote nothing to the vault.

Guardrails every agent works under

1
Research needs approval before anything is built
A research report never flows straight into implementation. The user reads and approves it first, and "just do it" doesn't skip that step.
2
Agent-written code goes through the simplifier
When the architect, generator, healer, debt fixer or implementation agent returns, whoever dispatched it runs /code-simplifier on exactly the .ts files that agent lists in its report. The simplified version is kept only if npm run lint passes. If the simplifier errors out, the agent's original output stands.
3
Fix loops have a limit
Any fix-then-verify loop states its iteration cap up front and compares the failure signature (error type plus failing step or locator) between rounds. If the same failure comes back twice, the agent stops, calls advisor() and reports. Marking a test test.fixme() to get out of a loop is not allowed.
4
Some problems go to the advisor straight away
A force: true click that changes nothing, a test that passes alone but fails in the suite, a second diagnostic script, a fix that breaks another storefront, and any change to BasePage or base-test.ts all call for advisor() before another attempt. These have burned hours before.
5
Comments get checked too
Any comment an agent writes is checked against the §16 checklist in .claude/agents/qa-code-reviewer.md. The default is no comment at all unless it explains a reason the code can't show.

Knowledge and memory (LightRAG)

Markdown notes in git, a knowledge graph for retrieval

Some things the code can't tell you: a staging quirk on Vans NZ, why a spec is Chromium-only, a decision made last week. Those go into short markdown notes in memory-vault/20-memory/. The vault is the source of truth and is committed to git. LightRAG reads it and builds a knowledge graph that the prompt hook and the agents query.

Counted on 2026-10-30. Each note has frontmatter (name, description, type, tags, last_verified) and links to related notes with [[wikilinks]], so the folder also opens as an Obsidian vault.

Write path

1
Claude, the vault-updater agent (from a Jira issue or Confluence page) or a person writes a note in the right folder.
2
The sync-memory.js hook runs scripts/sync-vault-to-lightrag.mjs for the notes that changed.
3
LightRAG (lightrag-hku 1.5.7, a local server on port 9621) pulls entities and relations out of the note into its graph.
4
At the end of the turn, lightrag-sync-status.js reports what synced. /sync-vault or npm run sync:vault pushes everything by hand. memory-vault-curator adds links and tags from time to time.

Read path

1
On every prompt, user-prompt-submit.js queries LightRAG in hybrid mode, waits up to 9 seconds, and injects up to 1,500 characters as "Relevant Memory".
2
The orchestrator, planner, research agent, vault-updater and curator call mcp__lightrag__query_document for questions that span several notes, after a health check.
3
For an exact keyword or tag, Grep over the vault is faster. It is also the fallback whenever LightRAG is down.
Ground rules. The vault is authoritative. The old ~/.claude/projects/.../memory seed is deprecated, and scripts/sync-memory-to-vault.mjs must not be run. On a new machine, node scripts/init-memory-from-vault.mjs loads Claude Code's memory from the vault (steps in memory-vault/SETUP.md). LightRAG indexes notes only, never source code; code search goes through codebase-memory-mcp or Grep.

Test anatomy

The shape of a real ecommerce smoke spec, trimmed
tests/ecommerce/smoke/homepage-smoke.spec.ts TypeScript 
// 1. UI specs import from @config/base-test, never from @playwright/test
import { test } from '@config/base-test';
import { storefronts } from '@data/ecommerce/storefronts';
import { createTestLogger } from '@utils/test-logger';

// 2. Tags go in the describe() name
test.describe('Ecommerce Homepage Smoke @ecommerce @smoke @homepage', () => {
  // 3. The staging SPAs need extra time to hydrate
  test.slow();

  // 4. One test per storefront: the ID stays fixed, the site name changes
  for (const site of storefronts) {
    test(`E2E-HOME-001 - ${site.name} homepage loads with expected title and hero`,
      async ({ ecommerceHomePage }) => {
      const logger = createTestLogger(`${site.name} - Homepage Load`);

      // 5. logger.step can wrap the step body
      await logger.step('Step 1 - Navigate to homepage', async () => {
        await ecommerceHomePage.navigate(site.url);
      });

      await logger.step('Step 2 - Assert title matches', async () => {
        await ecommerceHomePage.assertTitleMatches(site.titleRegex);
      });

      await logger.step('Step 3 - Assert hero visible', async () => {
        await ecommerceHomePage.assertHeroVisible();
      });
    });
  }
});
New ecommerce UI tests use E2E-{DOMAIN}-{NNN}, and new API tests use TC_XX. Older names (TC_01, E2E-..., PLA_OperationName) stay as they are, because renaming a test breaks CI tag filters and its monocart history.

Assertion strategy

Two modes, and how to pick one for each check
Hard assertions: expect
Fail immediately. Use them for preconditions that guard the steps after them: if the precondition is wrong, the rest of the test means nothing.

Also hard: Playwright locator assertions (expect(locator).toBeVisible()), expect.poll(), and tests with a single check.
Soft assertions: softAssert / softExpect
Keep going after a failure. Use them for several independent checks on the same page state, where you want every result.

The softAssert fixture logs each call with a [SOFT] marker through TestLogger. Don't call logger.verify() before it, or the entry is logged twice.
ScenarioUse
Several independent checks (title, count, visibility) on one page stateSoft, so every failure shows at once
Per-item checks inside a loopSoft, so every item is reported
A precondition that guards later stepsHard, because the later steps are meaningless if it fails
Playwright locator assertions (expect(locator).toHaveText())Hard; SoftAssertHelper has no locator equivalent
expect.poll()Hard; poll has its own timeout and intervals
A test with one assertionHard; soft adds nothing

Data isolation in parallel UI tests

Six separate layers that stop concurrent workers from stepping on each other's data
fullyParallel: true is safe here because six independent layers each remove a different kind of collision: separate processes, separate browser contexts, freshly generated test data, assertions that tolerate other activity, collision-free artifact paths, and no forced serial order.
1
Process isolation: one OS process per worker
Each workers slot (playwright.config.ts:34-38, default "50%") is a separate Node.js process, not a thread. A module-level let or const in a spec file exists once per process, so one worker can never read another worker's variables. None of the ecommerce spec files declares a module-level let; mutable values such as targetSize and availableSizes live inside a single test() body.
2
Browser context isolation: a fresh context per test, not per worker
The page fixture is test-scoped by default: every test() gets a new BrowserContext with its own cookies, localStorage, sessionStorage and cache. All 13 ecommerce page-object fixtures in base-test.ts wrap that same test-scoped page, and none widens the scope to the worker. The framework never reuses a saved storageState ("log in once, share everywhere"). Each test that needs a session logs in inside its own body, so no session token crosses a test boundary.
3
Fresh test data per test: the layer that prevents backend collisions
Browser isolation alone doesn't stop two workers from hitting the same backend record. A test that performs a real login first creates a throwaway account through a GraphQL createCustomer call, before the browser opens:
src/data/ecommerce/test-accounts.ts TypeScript 
export function createFreshAccountCredentials(brandCode: string): FreshAccountCredentials {
  const ts = Date.now();
  const rand = faker.string.alphanumeric(8).toLowerCase();
  return {
    email: `qa.${brandCode}.e2e${ts}${rand}@mailinator.com`, // timestamp + random suffix
    password: FRESH_ACCOUNT_PASSWORD,
    firstname: faker.person.firstName(),
    lastname: faker.person.lastName(),
    phone_number: '0412345678',
  };
}
3
Date.now() plus an 8-character random suffix gives 368 ≈ 2.8 trillion combinations per millisecond, so a collision is not a realistic concern even with heavy parallelism. The real login tests (E2E-AUTH-002, E2E-AUTH-010) and the checkout address prefill spec call createFreshAccountViaGraphQL(request, site), so each worker gets its own customer on the shared staging backend. Static shared data is used only where it can't change anything: invalidCredentials and nonExistentCredentials in the same file back only negative-path tests (wrong password, unknown email) that never open a session or change server state.
4
Assertions tolerate other activity on shared staging
Even with fresh accounts, all 8 storefronts are shared, live staging sites. Per tests/ecommerce/CLAUDE.md, cart tests assert the change (initialCartCount + 1), never the absolute count. A test doesn't care what other activity left in the cart. It checks only the change it caused, which keeps it stable when tests interleave.
5
Collision-free artifacts and reports
Screenshots, videos and traces use Playwright's default output paths, which embed the test title, project and retry number, so two workers writing failure artifacts at once never touch the same file. The HTML, JSON, JUnit and monocart reporters run in the main process and receive results from workers over IPC, so there is no race on the report files either.
6
No artificial serialization
Nothing under tests/ecommerce/ uses test.describe.configure({ mode: 'serial' }). That's deliberate. Layers 1 to 5 already keep the data correct, so the suite doesn't need a forced order to stay safe, and fullyParallel: true can run everything at once.

Design patterns applied

Named patterns underneath composition (section 01) and fixture injection (section 04)

Composition and dependency injection cover the page-object layer. The API client stack and the test lifecycle add a second set of patterns, mostly aimed at one goal: a new client, auth type or piece of teardown logic should mean writing a new implementation of an existing shape, not editing code that already works.

Strategy
The AuthType enum (NONE, BASIC, BEARER, API_KEY, CUSTOM) lets ApiClient change how a request authenticates without touching the request-building code. Pass a different AuthType in the client options and the header logic underneath follows.
ApiClientAuthType
Factory
createClient, createClientExt and createGraphQLClient each return a freshly configured client on demand instead of putting every test on one shared instance. The *DataGenerator classes in src/data/api/ do the same for test data: PlaceOrderTestDataGenerator.generateGuestEmail() returns a new, unique value on every call.
createClientExtPlaceOrderTestDataGenerator
Wrapper + fluent interface
ApiResponseWrapper and GraphQLResponseWrapper wrap the raw response and add a chainable assertion API: assertStatus(), assertJsonPath(), assertNoErrors(). A test reads response.assertStatus(200) and carries on instead of picking the body apart by hand.
ApiResponseWrapperGraphQLResponseWrapper
Adapter
extract<T>(path) on the same wrapper takes a dot-notation path like 'user.name' and turns the raw JSON into a typed value, so a test never walks a parsed response field by field.
extract<T>()
Registry
ApiClient.tokenStore is static, so a token stored in one test (ApiClient.storeToken('admin', token)) can be read by any later test in the same worker (ApiClient.getToken('admin')). It works as a small in-memory registry for the worker rather than something one client instance owns.
tokenStorewithStoredToken
Template method
global-setup.ts and global-teardown.ts plug into Playwright's fixed lifecycle: clear logs and check connectivity before the run, then generate reports and archive artifacts after it. Neither file changes the sequence. They fill in fixed steps around an order Playwright already controls, which is the textbook shape of the pattern.
global-setup.tsglobal-teardown.ts
Collector
SoftAssertHelper doesn't throw on the first failed check. It collects every failure and reports them together at teardown, so one run surfaces all the broken assertions. That is the opposite of Playwright's default hard-assertion behaviour.
SoftAssertHelpersoftAssert fixture
Facade
Every BasePage helper is a facade over Playwright's raw page API. this.elements.clickElement() hides waiting, retries and error handling behind one call, so page objects never touch Playwright primitives directly.
BasePageElementHelper
Spoken answer (interview-ready)

Beyond composition and dependency injection, I lean on a handful of named patterns in the client and lifecycle code. Authentication is a Strategy: the AuthType enum changes how a request signs itself without touching the request-building code. Anything that needs a fresh, differently configured instance is a Factory, like the createClientExt-style fixtures and the test data generators. The response wrappers combine Wrapper with a fluent interface, so assertStatus and assertJsonPath chain together, and extract<T>() on the same wrapper acts as an Adapter that turns a raw blob into a typed value by path. Cross-test token sharing runs through a static token store, which is a small Registry. Global setup and teardown follow Template Method: fixed steps run before and after the whole suite without any spec repeating them. The base-test files that extend Playwright's test are something else, the dependency-injection layer, not another Template Method. Soft assertions are a Collector that gathers every failed check and reports them together. And each BasePage helper is a Facade over Playwright's raw page API, so page objects never call page.click() or page.locator() directly.
