Component Object Model (COM)

Reusable widgets instead of one giant page object
Context
EN

Modern web apps (dashboards, SaaS, ERP) run at a large scale, spanning hundreds of different screens that all reuse the same core building blocks: a navbar, a sidebar menu, or data tables.

VI

Ứng dụng web hiện đại (dashboard, SaaS, ERP) có quy mô rất lớn, chứa hàng trăm màn hình giao diện khác nhau nhưng lại dùng chung các thành phần cốt lõi như thanh điều hướng (navbar), thanh menu bên (sidebar), hay bảng dữ liệu (table).

Why it's hard
EN

With a traditional Page Object Model, the locator and interaction code for something like a data table ends up repeated across every page file that uses it. When the interface's structure changes, that means hunting down and fixing the same logic in each file, which costs effort and lets bugs slip through.

VI

Nếu áp dụng Page Object Model truyền thống, mã định vị và tương tác của một bảng dữ liệu sẽ bị viết lặp đi lặp lại ở tất cả các file Page khác nhau có dùng đến nó. Khi giao diện đổi cấu trúc, phải lục tìm và sửa ở từng file, tốn công sức và dễ sót lỗi.

Solution
EN

Apply the Component Object Model. Break the page's interface down into independent, reusable Component classes, so the larger Page files stop locating small elements themselves and just call these Component classes in as properties.

VI

Áp dụng mô hình Component Object Model. Chia nhỏ giao diện trang web thành các thành phần tái sử dụng độc lập (Component Class). Các file Page lớn lúc này không tự định vị các phần tử nhỏ nữa, mà chỉ cần gọi lại các lớp Component này làm thuộc tính.

In practice
EN

Define a TableComponent class that takes the page and the table's own selector string. Write its action methods there, getting a row's text, clicking an action button, then in DashboardPage declare it as a property: readonly mainTable = new TableComponent(page, '#dashboard-table').

VI

Định nghĩa một lớp TableComponent nhận vào cấu trúc page và chuỗi selector đại diện của bảng. Viết các hàm chức năng xử lý như lấy text của dòng, click nút hành động ngay trong class này. Trong file DashboardPage, khai báo thuộc tính: readonly mainTable = new TableComponent(page, '#dashboard-table').

EN

Each Component owns its own locators scoped to its own container element, and exposes methods that describe what a user can do with it, not how it's built underneath. A page object then composes several components instead of redeclaring their internals, so a change to how the table renders only needs a fix in one place.

VI

Mỗi Component sở hữu locator riêng, giới hạn trong container của chính nó, và cung cấp method mô tả người dùng có thể làm gì với nó, chứ không phải nó được dựng bên trong ra sao. Một page object sau đó chỉ ghép các component lại thay vì khai báo lại chi tiết bên trong, nên khi bảng đổi cách hiển thị chỉ cần sửa một nơi.

→
EN

This repo's own BasePage already composes 11 helper classes instead of putting every method in one file. COM applies the same composition idea to on-screen widgets rather than to interaction helpers.

VI

Chính BasePage của repo này đã ghép 11 helper class thay vì dồn mọi method vào một file. COM áp dụng cùng ý tưởng ghép nối đó cho thành phần trên màn hình thay vì cho helper thao tác.

components/TableComponent.ts TypeScript 
import { Locator, Page } from '@playwright/test';

export class TableComponent {
  readonly container: Locator;
  readonly rows: Locator;

  constructor(page: Page, tableSelector: string) {
    this.container = page.locator(tableSelector);
    this.rows = this.container.locator('tbody tr');
  }

  async getRowTextByIndex(index: number): Promise<string> {
    return this.rows.nth(index).innerText();
  }

  async clickActionByName(rowName: string, actionButtonText: string) {
    const targetRow = this.container.locator('tr', { hasText: rowName });
    await targetRow.getByRole('button', { name: actionButtonText }).click();
  }
}
02

Custom fixtures for dependency injection

Stop building page objects by hand in beforeEach
Context
EN

Before running any UI test scenario, a repeated chain of setup actions has to happen: constructing page objects, navigating the browser to the right target page, or setting environment configuration cookies.

VI

Trước khi thực thi bất kỳ kịch bản kiểm thử UI nào, đều cần thực hiện một chuỗi các hành động khởi tạo lặp đi lặp lại như khởi tạo các trang đối tượng (POM), điều hướng trình duyệt đến đúng trang đích, hoặc cài đặt cookie cấu hình môi trường.

Why it's hard
EN

Cramming that setup code into a traditional beforeEach block bloats the test file, the same code repeats across many files, maintenance gets harder, and performance suffers once runs are configured for parallel execution.

VI

Việc nhồi nhét mã nguồn khởi tạo này vào các khối lệnh beforeEach truyền thống khiến file test bị phình to, mã nguồn bị lặp lại ở nhiều file khác nhau, gây khó khăn cho việc bảo trì và làm giảm hiệu suất khi cấu hình chạy song song đa luồng.

Solution
EN

Use Dependency Injection through Playwright's built-in Custom Fixtures feature. Define how each page object gets created and torn down once, in a shared base file; a test case just asks for that page by name as a parameter, and Playwright loads it and cleans it up automatically.

VI

Tận dụng cơ chế Dependency Injection thông qua tính năng Custom Fixtures tích hợp sẵn của Playwright. Định nghĩa trước cách thức khởi tạo và giải phóng cho từng trang đối tượng trong một file cấu hình nền tảng. Khi viết test case, chỉ cần gọi tên trang đó ra làm tham số, Playwright sẽ tự động nạp vào và dọn dẹp sau khi chạy xong.

In practice
EN

Use Playwright's test.extend to define a custom fixture (e.g. dashboardPage). Inside the fixture body, construct new DashboardPage(page) and call await use(dashboard). In the test file, this shortens to test('Kiểm tra', async ({ dashboardPage }) => { await dashboardPage.doSomething() }).

VI

Sử dụng phương thức mở rộng test.extend của Playwright để định nghĩa một fixture tùy biến (ví dụ dashboardPage). Bên trong thân fixture, viết logic ngầm khởi tạo new DashboardPage(page) và gọi lệnh await use(dashboard). Trong file test, viết ngắn gọn: test('Kiểm tra', async ({ dashboardPage }) => { await dashboardPage.doSomething() }).

EN

Fixtures are Playwright's own dependency injection mechanism. A fixture function receives whatever it needs, builds what it's responsible for, and hands it to the test through use(). Only the fixtures a test actually lists as parameters get initialized, so tests stay lightweight even when the fixture file defines many of them.

VI

Fixture là cơ chế dependency injection riêng của Playwright. Một hàm fixture nhận vào những gì nó cần, dựng phần nó chịu trách nhiệm, rồi truyền lại cho test qua use(). Chỉ những fixture mà test thật sự liệt kê làm tham số mới được khởi tạo, nên test vẫn nhẹ dù file fixture khai báo rất nhiều fixture khác.

→
EN

This framework already registers 14 UI page-object fixtures in base-test.ts, following exactly this pattern, one fixture function per page, composed through base.extend.

VI

Framework này đã đăng ký sẵn 14 fixture page object UI trong base-test.ts, theo đúng mô hình này: mỗi trang một hàm fixture, ghép lại qua base.extend.

fixtures/baseTest.ts TypeScript 
import { test as base } from '@playwright/test';
import { DashboardPage } from '../pages/DashboardPage';
import { SettingsPage } from '../pages/SettingsPage';

type MyPages = {
  dashboardPage: DashboardPage;
  settingsPage: SettingsPage;
};

export const test = base.extend<MyPages>({
  dashboardPage: async ({ page }, use) => {
    const dashboard = new DashboardPage(page);
    await dashboard.goto();
    await use(dashboard);
  },
  settingsPage: async ({ page }, use) => {
    await use(new SettingsPage(page));
  },
});
export { expect } from '@playwright/test';
03

Robust locator strategy

Filter by what the user sees, not where the element sits
Context
EN

Front-end developers constantly update the interface to improve the experience, regularly changing CSS classes, ids, or the wrapping HTML tags around elements.

VI

Đội ngũ lập trình viên Front-end liên tục cập nhật giao diện để tối ưu trải nghiệm. Họ thường xuyên thay đổi các thuộc tính mã nguồn như lớp giao diện (CSS class), mã định danh (id), hoặc thay đổi cấu trúc sắp xếp các thẻ HTML bọc bên ngoài.

Why it's hard
EN

Selectors based on absolute XPath or plain CSS break repeatedly whenever the DOM structure changes, the classic brittle-test problem, and QA ends up spending a lot of time just maintaining test code.

VI

Nếu sử dụng các bộ định vị (selector) dựa trên XPath tuyệt đối hoặc CSS Selector thuần, bài test sẽ bị gãy liên tục (gây ra hiện tượng brittle test) mỗi khi mã nguồn giao diện thay đổi cấu trúc DOM, khiến QA mất rất nhiều thời gian bảo trì code test.

Solution
EN

Apply the user-centric locator strategy Playwright recommends. Locate elements by their visible role, their accessible label, or the actual text shown on screen, combined with a dynamic filter.

VI

Áp dụng chiến lược định vị hướng người dùng (user-centric locators) được Playwright khuyến nghị tối đa. Định vị phần tử giao diện dựa trên vai trò hiển thị (role), nhãn văn bản hỗ trợ (aria-label) hoặc nội dung chữ (text) thật hiển thị trên màn hình, kết hợp bộ lọc động (filter).

In practice
EN

Prefer page.getByRole('button', { name: 'Xác nhận thanh toán' }) over an id or class. To find one specific element inside a dynamic list, filter it down: page.locator('tr').filter({ hasText: 'iPhone 15 Pro' }).getByRole('button', { name: 'Xóa' }).

VI

Ưu tiên dùng câu lệnh page.getByRole('button', { name: 'Xác nhận thanh toán' }) thay vì dùng id hay class. Khi cần tìm một phần tử cụ thể nằm trong một danh sách động, sử dụng bộ lọc: page.locator('tr').filter({ hasText: 'iPhone 15 Pro' }).getByRole('button', { name: 'Xóa' }).

EN

This project's own conventions already ban hierarchical structural selectors and require getByRole, getByLabel, or getByText as the default. Chaining .filter() is exactly how a selection narrows further without giving up that semantic meaning, each filter stacks on top of the last.

VI

Quy ước riêng của project này đã cấm selector cấu trúc phân cấp và yêu cầu dùng getByRole, getByLabel, hoặc getByText làm mặc định. Nối thêm .filter() chính là cách thu hẹp lựa chọn mà vẫn giữ được ý nghĩa ngữ nghĩa đó, mỗi filter chồng lên filter trước.

→
EN

.filter() chains can stack as many times as needed, useful for compound conditions like "the row named X that is also currently in stock".

VI

Chuỗi .filter() có thể nối bao nhiêu lần cũng được, hữu ích cho điều kiện kết hợp kiểu "dòng tên X mà đồng thời đang còn hàng".

dynamic-locator.spec.ts TypeScript 
import { test, expect } from './fixtures/baseTest';

test('locates one specific row inside a dynamic list', async ({ page }) => {
  const targetRow = page.locator('tr')
    .filter({ hasText: 'iPhone 15' })
    .filter({ has: page.getByRole('badge', { name: 'In Stock' }) });

  await targetRow.getByRole('button', { name: 'Edit' }).click();
});

Multi-tab, multi-window and iframe handling

Reach across a new tab, or into a third-party payment frame
Context
EN

Real end-to-end user journeys get complicated fast. A user clicks a terms-and-conditions link and the system silently opens a new browser tab, or the flow needs to interact with a payment gateway embedded through a third-party <iframe>.

VI

Kịch bản kiểm thử hành trình người dùng thực tế (E2E) rất phức tạp. Ví dụ, người dùng nhấn vào link điều khoản và hệ thống tự động bật ra một tab trình duyệt mới, hoặc tương tác với một khung nhúng cổng thanh toán độc lập (<iframe>) từ đối tác ngân hàng bên thứ ba.

Why it's hard
EN

Older-generation testing tools often can't automatically catch the event of a new tab opening, or get blocked from reaching inside the iframe at all, because of the browser's strict same-origin security policy.

VI

Các công cụ kiểm thử thế hệ cũ thường không thể tự động bắt được sự kiện của tab mới vừa bật lên, hoặc bị chặn đứng không thể can thiệp vào bên trong khung iframe do rào cản chính sách bảo mật nghiêm ngặt của trình duyệt web (same-origin policy).

Solution
EN

Use Playwright's high-level asynchronous event listener to catch a new tab the instant it appears, and use its dedicated frame locator to reach past that security boundary.

VI

Tận dụng cơ chế lắng nghe sự kiện bất đồng bộ (event listener) cấp cao của Playwright để bắt trọn tab mới ngay khi xuất hiện và sử dụng bộ định vị khung nhìn chuyên dụng (frameLocator) để đi xuyên rào cản bảo mật.

In practice
EN

Before the click, declare const pagePromise = context.waitForEvent('page'). After the click fires, take control of the new tab with const newTab = await pagePromise. For an embedded frame, use page.frameLocator('iframe[name="stripe"]').getByPlaceholder('Số thẻ').fill('4242').

VI

Trước khi click, khai báo một Promise chờ sự kiện: const pagePromise = context.waitForEvent('page'). Sau khi thực hiện hành động click, lấy quyền điều khiển tab mới bằng lệnh: const newTab = await pagePromise. Đối với khung nhúng, sử dụng: page.frameLocator('iframe[name="stripe"]').getByPlaceholder('Số thẻ').fill('4242').

EN

context.waitForEvent('page') resolves the moment Playwright detects a new page inside that same browser context. frameLocator returns a locator scoped entirely to what's inside one specific iframe, and normal locator chaining, including .filter() from the previous section, still works from there.

VI

context.waitForEvent('page') hoàn tất ngay khi Playwright phát hiện một trang mới trong cùng browser context đó. frameLocator trả về một locator giới hạn hoàn toàn trong một iframe cụ thể, và việc nối locator thông thường, kể cả .filter() ở mục trước, vẫn dùng được từ đó.

→
EN

The pagePromise has to be created before the click that opens the tab, not after. Otherwise the event can fire before the listener exists, and the promise never resolves.

VI

pagePromise phải được tạo trước lệnh click mở tab, không phải sau. Nếu không, sự kiện có thể xảy ra trước khi listener tồn tại, và promise sẽ không bao giờ hoàn tất.

multi-tab-iframe.spec.ts TypeScript 
test('handles a new tab and a third-party payment iframe', async ({ page, context }) => {
  const pagePromise = context.waitForEvent('page');
  await page.getByRole('link', { name: 'Mở điều khoản cấu hình' }).click();
  const newTabPage = await pagePromise;

  await newTabPage.waitForLoadState();
  await expect(newTabPage).toHaveTitle(/Điều khoản dịch vụ/);

  const paymentFrame = page.frameLocator('iframe[name="stripe-checkout"]');
  await paymentFrame.getByPlaceholder('Card Number').fill('4242 4242 4242');
});
05

Simulating human-like interactions

Typing key by key, with a delay, instead of setting a value
Context
EN

To defend against automated attacks, businesses often add advanced firewall layers, like Cloudflare or Akamai, right at the front-end specifically to block bot software.

VI

Để bảo vệ hệ thống khỏi các cuộc tấn công mạng, doanh nghiệp thường trang bị các lớp tường lửa bảo mật nâng cao (như Cloudflare, Akamai) ở tầng giao diện Front-end để chặn đứng các phần mềm tự động (bot).

Why it's hard
EN

Ordinary automation code moves the mouse in a straight line instantly and types out an entire string in a fraction of a second. That unrealistic speed is exactly what tips the firewall off that it's a bot, and access gets blocked right away.

VI

Các mã nguồn automation thông thường sẽ di chuyển chuột lập tức theo đường thẳng tuyệt đối và gõ toàn bộ chuỗi ký tự dài trong một phần triệu giây. Tốc độ phi thực tế này khiến tường lửa nhận diện ra ngay đây là bot và ngay lập tức khóa (block) quyền truy cập.

Solution
EN

Use Playwright's low-level input device APIs to closely mimic real mouse movement with curved acceleration and unpredictable typing speed, producing the same kind of varying delay a real person has.

VI

Sử dụng các API điều khiển thiết bị ngoại vi cấp thấp (low-level input) của Playwright nhằm mô phỏng chính xác hành vi di chuyển chuột có gia tốc cong và tốc độ gõ phím bất định, tạo độ trễ biến thiên y như người thật.

In practice
EN

page.locator('#search').pressSequentially('Bàn phím cơ', { delay: 120 }) adds a randomized 120ms delay between keystrokes. For mouse movement, page.mouse.move(x, y, { steps: 10 }) moves the cursor smoothly through 10 intermediate points instead of jumping straight there.

VI

Sử dụng hàm page.locator('#search').pressSequentially('Bàn phím cơ', { delay: 120 }) để tạo độ trễ 120ms ngẫu nhiên giữa mỗi phím gõ. Đối với tương tác chuột, sử dụng lệnh điều khiển tọa độ: page.mouse.move(x, y, { steps: 10 }) để con trỏ chuột di chuyển mượt mà qua 10 điểm trung gian thay vì nhảy cóc.

EN

This is one of the few places a test deliberately slows itself down. pressSequentially sends a real keydown and keyup pair per character, and the delay should stay proportional to what the flow actually needs, a search box tolerates 150 milliseconds fine, while a longer form might need the delay varied per field.

VI

Đây là một trong số ít trường hợp test chủ động tự làm chậm lại. pressSequentially gửi đúng một cặp keydown và keyup cho mỗi ký tự, và độ trễ nên tương ứng với luồng thực tế cần gì, một ô tìm kiếm chấp nhận 150 mili giây là ổn, còn một form dài hơn có thể cần độ trễ khác nhau ở từng field.

→
EN

pressSequentially only smooths input timing. It does nothing about mouse movement paths or other fingerprinting signals a detector might check, so treat it as one layer, not a complete bypass.

VI

pressSequentially chỉ làm mượt thời gian nhập liệu. Nó không xử lý đường đi chuột hay các tín hiệu nhận diện khác mà hệ thống phát hiện có thể kiểm tra, nên xem đây là một lớp phòng vệ, không phải cách vượt qua hoàn toàn.

human-like-typing.spec.ts TypeScript 
test('types and moves the mouse like a real user', async ({ page }) => {
  await page.goto('/search');
  await page.locator('#search-box').hover();

  await page.getByPlaceholder('Tìm kiếm sản phẩm...').pressSequentially('Bàn phím cơ', { delay: 150 });
  await page.keyboard.press('Enter');
});
06

Canvas, SVG and coordinate-based drag and drop

There's no element to grab, only pixels and coordinates
Context
EN

Modern web apps pack in a lot of highly interactive graphics: digital maps, charts drawn on a <canvas>, or Kanban-style task boards (like Trello or Jira) that need cards dragged and dropped by hand.

VI

Ứng dụng web hiện đại tích hợp rất nhiều thành phần đồ họa tương tác cao như bản đồ số, đồ thị trực quan vẽ trên thẻ <canvas>, hoặc các bảng quản lý công việc dạng Kanban (như Trello, Jira) yêu cầu hành động cầm chuột kéo thả các thẻ nhiệm vụ.

Why it's hard
EN

A <canvas> is just a flat image to the browser, there's no way to find an id or text inside it the normal way. And a drag-and-drop driven by an ordinary click-and-move sequence can easily drop the event mid-gesture because of render lag.

VI

Thẻ <canvas> chỉ là một tấm ảnh phẳng đối với trình duyệt, không thể dùng các hàm tìm id hay text thông thường để tương tác với các thành phần bên trong. Các hành động kéo thả nếu thực thi bằng lệnh click-and-move thông thường của code test cũng rất dễ bị mất sự kiện (drop event) giữa chừng do độ trễ render.

Solution
EN

Use Playwright's boundingBox measurement to pull the actual pixel coordinates of an element on screen, then drive the mouse action sequence (mouse.down, mouse.move, mouse.up) with a controlled number of intermediate steps.

VI

Sử dụng cơ chế đo lường hộp biên (boundingBox) của Playwright để trích xuất tọa độ pixel thực tế của phần tử trên màn hình, sau đó điều khiển chuỗi hành động chuột (mouse.down, mouse.move, mouse.up) có kiểm soát số lượng bước di chuyển (steps).

In practice
EN

Get the source and target coordinates with const sourceBox = await source.boundingBox(). Move to the source's center with page.mouse.move(sourceBox.x + sourceBox.width / 2, sourceBox.y + sourceBox.height / 2). Press down with page.mouse.down(), move smoothly to the target using { steps: 10 }, and release with page.mouse.up().

VI

Lấy tọa độ của thẻ nguồn và đích bằng lệnh const sourceBox = await source.boundingBox(). Di chuyển chuột đến tâm thẻ nguồn: await page.mouse.move(sourceBox.x + sourceBox.width / 2, sourceBox.y + sourceBox.height / 2). Kích hoạt lệnh nhấn giữ (page.mouse.down()), di chuyển mượt mà tới đích bằng thuộc tính { steps: 10 }, và nhả chuột (page.mouse.up()).

EN

The steps option on mouse.move matters here. Moving in one jump can fail to trigger a widget's own dragover handlers, spreading the move across several intermediate points makes it register as a real drag gesture instead of a single teleport.

VI

Tùy chọn steps trên mouse.move quan trọng ở đây. Di chuyển trong một bước nhảy có thể không kích hoạt được handler dragover riêng của widget, việc chia nhỏ di chuyển thành nhiều điểm trung gian khiến nó được ghi nhận như một thao tác kéo thật thay vì một cú nhảy đơn.

→
EN

boundingBox() can return null if the element isn't currently visible or has zero size. The if (sourceBox && targetBox) guard is there for that reason, not just as a type-narrowing habit.

VI

boundingBox() có thể trả về null nếu phần tử đang không hiển thị hoặc có kích thước bằng không. Điều kiện if (sourceBox && targetBox) tồn tại vì lý do đó, không chỉ là thói quen thu hẹp kiểu dữ liệu.

canvas-drag-drop.spec.ts TypeScript 
test('drags an element by coordinates', async ({ page }) => {
  const source = page.locator('.drag-source-item');
  const target = page.locator('.drop-zone-area');

  const sourceBox = await source.boundingBox();
  const targetBox = await target.boundingBox();

  if (sourceBox && targetBox) {
    await page.mouse.move(sourceBox.x + sourceBox.width / 2, sourceBox.y + sourceBox.height / 2);
    await page.mouse.down();
    await page.mouse.move(targetBox.x + targetBox.width / 2, targetBox.y + targetBox.height / 2, { steps: 10 });
    await page.mouse.up();
  }
});

Visual regression testing

Compare pixels against a baseline, mask what's expected to change
Context
EN

After a major front-end update, the business needs assurance that the whole interface hasn't broken visually: no display bugs, no CSS drift, no wrong font size or color straying from the approved Figma design.

VI

Sau mỗi đợt cập nhật mã nguồn Front-end lớn, doanh nghiệp cần đảm bảo toàn bộ giao diện của hệ thống không bị lỗi hiển thị, lệch CSS, sai cỡ chữ, hoặc bị thay đổi màu sắc sai lệch so với bản thiết kế chuẩn (design Figma).

Why it's hard
EN

Writing ordinary expect assertions to check the color and width of hundreds of buttons individually would balloon the test code to tens of thousands of lines, and it becomes nearly impossible to maintain once the interface shifts even slightly.

VI

Nếu viết các câu lệnh expect thông thường để kiểm tra từng thuộc tính style màu sắc, độ rộng của hàng trăm nút bấm trên màn hình, file code test sẽ phình to hàng vạn dòng và cực kỳ khó duy trì khi giao diện thay đổi nhẹ.

Solution
EN

Apply visual regression testing. Playwright captures a screenshot of the live interface during the test run and compares it pixel by pixel against a previously stored baseline image.

VI

Áp dụng giải pháp kiểm thử so sánh hình ảnh giao diện (visual regression testing). Playwright sẽ chụp ảnh màn hình giao diện lúc chạy test thật, đối chiếu sai lệch cấu trúc từng pixel với một tấm ảnh mẫu chuẩn (baseline image) được lưu từ trước.

In practice
EN

Write the assertion: await expect(page).toHaveScreenshot('homepage-master.png', { maxDiffPixels: 100 }). To avoid a false failure from a region that's always changing, pass a mask over it: mask: [page.locator('.live-clock-timestamp')].

VI

Viết câu lệnh assert: await expect(page).toHaveScreenshot('homepage-master.png', { maxDiffPixels: 100 }). Để tránh việc bài test bị fail oan do các vùng chứa dữ liệu luôn thay đổi theo thời gian, truyền thêm thuộc tính che vùng động: mask: [page.locator('.live-clock-timestamp')].

EN

The first run of a new toHaveScreenshot assertion writes the baseline image rather than comparing against one, so a newly added visual assertion needs a deliberate review pass before it can be trusted as a real regression gate.

VI

Lần chạy đầu tiên của một assertion toHaveScreenshot mới sẽ ghi ảnh chuẩn thay vì so sánh với ảnh có sẵn, nên một assertion hình ảnh vừa thêm vào cần được rà soát có chủ đích trước khi có thể tin tưởng là cổng chặn hồi quy thật sự.

→
EN

maxDiffPixels sets a small tolerance for anti-aliasing noise between machines. It isn't meant to hide a real layout regression, keep it tight and use mask for anything genuinely dynamic instead of loosening this number.

VI

maxDiffPixels chỉ nên chừa một dung sai nhỏ cho nhiễu anti-aliasing giữa các máy. Nó không dùng để che giấu một hồi quy bố cục thật sự, hãy giữ số này chặt và dùng mask cho thứ thật sự động thay vì nới lỏng con số này.

test('Dashboard layout matches the visual baseline', async ({ page }) => {
  await page.goto('/dashboard');

  await expect(page).toHaveScreenshot('dashboard-master.png', {
    maxDiffPixels: 100,
    mask: [
      page.locator('.current-time-clock'),
      page.locator('.user-profile-name')
    ]
  });

Accessibility testing (WCAG scanning)

Automated axe-core scans as a hard gate, not a manual pass
Context
EN

When a web app ships to a global market, especially Europe and the US, it has to comply strictly with accessibility law (the WCAG standard), making sure people with visual impairments can operate it through screen readers.

VI

Khi ứng dụng web phát hành ra thị trường toàn cầu (đặc biệt là thị trường Âu Mỹ), hệ thống bắt buộc phải tuân thủ nghiêm ngặt luật bảo vệ người khuyết tật (tiêu chuẩn WCAG), đảm bảo những người khiếm thị có thể sử dụng phần mềm đọc màn hình (screen readers) để thao tác bình thường.

Why it's hard
EN

A QA engineer can't visually inspect whether every HTML tag was written with the right hidden aria-* attributes, or whether the text-to-background color contrast meets the medical standard, just by looking at the screen.

VI

Kỹ sư QA không thể tự kiểm tra bằng mắt thường để phát hiện xem các thẻ HTML đã được lập trình viên khai báo đủ thuộc tính ẩn (aria-*) hay chưa, hoặc độ tương phản màu sắc giữa chữ và nền có đạt chuẩn y khoa hay không.

Solution
EN

Integrate the Axe Core automated scanning library directly into Playwright's browser run to automatically analyze the whole DOM tree and produce a violations report.

VI

Tích hợp bộ thư viện quét lỗi tự động chuyên dụng Axe Core trực tiếp vào luồng chạy trình duyệt của Playwright để tự động phân tích toàn bộ cây cấu trúc DOM và xuất báo cáo vi phạm.

In practice
EN

Install @axe-core/playwright. After navigating to the target page, run the scanner: const results = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa']).analyze(). Then assert expect(results.violations).toEqual([]).

VI

Cài đặt gói mở rộng @axe-core/playwright. Trong file kịch bản, sau khi điều hướng tới trang cần kiểm tra, khởi chạy trình quét: const results = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa']).analyze(). Viết câu lệnh kiểm tra: expect(results.violations).toEqual([]).

EN

This project already exposes a makeAxeBuilder fixture for exactly this purpose, so a new accessibility test doesn't need to construct AxeBuilder by hand, it can call the fixture and scan straight from there.

VI

Project này đã có sẵn fixture makeAxeBuilder đúng cho mục đích này, nên một test accessibility mới không cần tự dựng AxeBuilder bằng tay, chỉ cần gọi fixture rồi quét từ đó.

→
EN

An automated scanner like axe only catches what's mechanically detectable, missing labels, contrast, ARIA misuse. Whether tab order actually makes sense to a real user still needs a human pass.

VI

Một scanner tự động như axe chỉ bắt được những gì có thể kiểm tra máy móc, thiếu nhãn, tương phản, dùng sai ARIA. Việc thứ tự tab có thật sự hợp lý với người dùng thật hay không vẫn cần con người rà soát.

accessibility-scan.spec.ts TypeScript 
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

  await page.goto('https://yourcompany.com');

  const accessibilityScanResults = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa'])
    .analyze();

  expect(accessibilityScanResults.violations).toEqual([]);
});

Network mocking and data manipulation

Answer the request yourself, force the empty state to show
Context
EN

Some scenarios need testing the front-end's edge cases or error handling, for example verifying what the UI shows for an empty product list, or whether a friendly warning banner appears when the server goes down (a 500 error).

VI

Cần thực hiện kiểm thử các kịch bản biên hoặc xử lý lỗi của giao diện Front-end, ví dụ xác thực xem UI hiển thị hình minh họa thế nào khi danh sách sản phẩm trống (empty state), hoặc UI có hiện banner cảnh báo thân thiện không khi server sập (lỗi 500).

Why it's hard
EN

There's no practical way to keep wiping the real test database clean for one scenario, and no way to deliberately take down the company's real backend server just to check how one screen's UI reacts.

VI

Không thể liên tục can thiệp vào database thật của môi trường test để xóa sạch dữ liệu, cũng như không thể chủ động đánh sập server backend thật của công ty chỉ để phục vụ cho việc kiểm tra giao diện của một kịch bản duy nhất.

Solution
EN

Use network mocking at the browser layer. Playwright acts as an internal proxy, intercepting the API request the UI sends out and fulfilling it with a fake JSON response matching whatever scenario is needed.

VI

Sử dụng giải pháp network mocking ở tầng trình duyệt. Playwright đóng vai trò như một proxy nội bộ, nó chặn đứng request API phát đi từ giao diện UI và tự động nạp trả về (fulfill) một nội dung phản hồi JSON giả lập theo đúng kịch bản mong muốn.

In practice
EN

Set up the intercept before the page loads: await page.route('**/api/products', async route => { await route.fulfill({ status: 500, contentType: 'application/json', body: JSON.stringify({ error: 'Server sập' }) }) }). Then call page.goto() and check whether the error banner actually shows.

VI

Khai báo cấu hình chặn mạng trước khi load trang: await page.route('**/api/products', async route => { await route.fulfill({ status: 500, contentType: 'application/json', body: JSON.stringify({ error: 'Server sập' }) }) }). Sau đó gọi page.goto() và viết lệnh kiểm tra xem banner lỗi có hiển thị lên màn hình UI hay không.

EN

route.fulfill fully replaces the response, so this technique also covers other hard-to-reproduce shapes: a single item, a malformed payload, or a specific error code, not only an empty list.

VI

route.fulfill thay thế hoàn toàn response, nên kỹ thuật này cũng phủ được các trường hợp khó tái hiện khác: một phần tử duy nhất, payload sai định dạng, hay một mã lỗi cụ thể, không chỉ mỗi danh sách rỗng.

→
EN

page.route only intercepts requests that go through the browser context. It has no effect on calls made through a standalone request fixture or client.

VI

page.route chỉ chặn được request đi qua browser context. Nó không có tác dụng với các lệnh gọi qua fixture hay client request độc lập.

test('shows the empty-state illustration when the product list API returns nothing', async ({ page }) => {

    await route.fulfill({

      contentType: 'application/json',
      body: JSON.stringify([])
    });
  });

  await page.goto('/inventory');
  await expect(page.locator('.empty-state-illustration')).toBeVisible();

See the app the way a phone on a weak connection sees it
Context
EN

An app serving users across multiple countries needs a UI that responds correctly on every mobile screen size, switches language automatically based on the visitor's country, and still works when someone is in an area with weak, spotty 3G coverage.

VI

Ứng dụng web phục vụ người dùng đa quốc gia yêu cầu giao diện phải tự động responsive chuẩn trên mọi kích thước thiết bị di động, tự động chuyển đổi ngôn ngữ dựa theo vị trí quốc gia truy cập, và hoạt động tốt ngay cả khi người dùng đi vào vùng sóng yếu (mạng 3G chập chờn).

Why it's hard
EN

QA can't physically travel to different countries to test location, can't stock every real phone model on the market, and can't unplug the office network to simulate lag while automation is running.

VI

QA không thể di chuyển sang các nước khác nhau để test vị trí, không thể trang bị đầy đủ tất cả các loại điện thoại thật trên thị trường, và không thể tự rút phích cắm mạng của công ty để làm mạng lag khi đang chạy automation.

Solution
EN

Use the hardware emulation feature and the Chrome DevTools Protocol session Playwright's core already provides to fully control the browser environment.

VI

Tận dụng tính năng giả lập cấu hình phần cứng (emulation) và kết nối phiên nâng cao (Chrome DevTools Protocol, CDP) có sẵn trong nhân của Playwright để kiểm soát hoàn toàn môi trường trình duyệt.

In practice
EN

test.use({ ...devices['iPhone 14 Pro'], geolocation: { latitude: 35.67, longitude: 139.65 }, permissions: ['geolocation'] }). To throttle bandwidth, open a CDP session with const session = await context.newCDPSession(page) and send Network.emulateNetworkConditions with the desired latency parameters.

VI

Khai báo cấu hình giả lập trong file test: test.use({ ...devices['iPhone 14 Pro'], geolocation: { latitude: 35.67, longitude: 139.65 }, permissions: ['geolocation'] }). Để bóp băng thông mạng, khởi tạo một CDP session ngầm bằng lệnh const session = await context.newCDPSession(page) và gửi sự kiện cấu hình tốc độ mạng Network.emulateNetworkConditions kèm các thông số độ trễ (latency) mong muốn.

EN

The CDP session approach only works in Chromium, since Firefox and WebKit don't expose the same protocol, so a suite that needs network throttling across browsers has to treat this check as Chromium-only.

VI

Cách dùng CDP session chỉ hoạt động trên Chromium, vì Firefox và WebKit không cung cấp cùng protocol đó, nên một suite cần bóp mạng trên nhiều trình duyệt phải xem đây là kiểm tra riêng cho Chromium.

→
EN

permissions: ['geolocation'] has to be granted explicitly, otherwise the browser blocks the geolocation API outright, and code depending on the emulated coordinates just sees a permission error instead.

VI

permissions: ['geolocation'] phải được cấp rõ ràng, nếu không trình duyệt sẽ chặn hẳn geolocation API, và đoạn mã phụ thuộc vào tọa độ giả lập chỉ nhận được lỗi permission thay vì dữ liệu.

  permissions: ['geolocation'],
});

test('renders correctly on a throttled mobile connection', async ({ page, context }) => {
  const session = await context.newCDPSession(page);
  await session.send('Network.emulateNetworkConditions', {
    offline: false,
    latency: 400,
    downloadThroughput: 500 * 1024 / 8, // 500 kbps (Slow 3G)
    uploadThroughput: 500 * 1024 / 8,
  });

  await page.goto('/stores-near-me');
  await expect(page.locator('.store-location-card').first()).toContainText('Tokyo Branch');
});

Centralized login session management (storage state)

Log in once in setup, reuse the session everywhere else
Context
EN

Almost every deep business feature in a UI requires a user to have already logged in successfully before they're allowed to reach the working screen.

VI

Hầu hết các tính năng nghiệp vụ sâu của ứng dụng UI đều yêu cầu người dùng phải thực hiện đăng nhập tài khoản thành công thì mới có quyền truy cập vào màn hình thao tác.

Why it's hard
EN

If every UI spec file makes the browser repeat opening the login page, typing username and password, and waiting for the dashboard to load, the whole suite's runtime balloons dramatically (sometimes to several hours), and it becomes prone to random flaky failures from interface network delay.

VI

Nếu cứ mỗi file kịch bản test UI đều bắt trình duyệt lặp lại các bước mở trang login, gõ username/password, rồi bấm nút đợi trang dashboard tải xong, thời gian thực thi của bộ test suite sẽ bị phình to khủng khiếp (lên đến nhiều tiếng đồng hồ) và rất dễ bị lỗi ngẫu nhiên (flaky) do trễ mạng giao diện.

Solution
EN

Roll out a storage-state bypass. Have Playwright run exactly one login setup file at the start of the run, capture the full cookies and local storage into a compressed JSON file, then automatically inject that file into every subsequent test's browser so it lands directly on the target page without going through the login screen.

VI

Triển khai cơ chế Storage State Bypass. Cấu hình cho Playwright khởi chạy duy nhất một file setup đăng nhập ở đầu phiên chạy, chụp lại toàn bộ cookie và local storage lưu vào một file JSON nén, sau đó tự động "tiêm" (inject) file này vào trình duyệt của tất cả các kịch bản test sau để vào thẳng trang đích mà không cần qua màn hình login.

In practice
EN

In playwright.config.ts, declare a project that runs the dedicated login setup file. In the main project running the E2E scenarios, load that state automatically with use: { storageState: '.auth/user-session.json' } and set dependencies: ['auth-setup'] to bind the run order.

VI

Trong file cấu hình playwright.config.ts, khai báo một dự án chạy file setup đăng nhập riêng. Handling flaky tests without hard waits

Web-first assertions instead of a fixed sleep
Context
EN

When running UI automation, test scenarios fail randomly fairly often, simply because the interface loads a few milliseconds slower due to CI network congestion or an unstable server response.

VI

Khi chạy automation trên giao diện UI, kịch bản test rất thường xuyên bị lỗi ngẫu nhiên (flaky test) do giao diện tải chậm hơn một vài mili giây vì nghẽn mạng CI hoặc server phản hồi không ổn định.

Why it's hard
EN

The usual workaround is sprinkling fixed sleep calls like page.waitForTimeout(5000) everywhere. That wastes suite runtime for no reason, and it still doesn't fix anything if the network lags for more than five seconds the next time.

VI

Lập trình viên thường giải quyết bằng cách chèn các câu lệnh ngủ cố định (hard wait) dạng page.waitForTimeout(5000) vào khắp mọi nơi. Việc này làm lãng phí thời gian chạy test suite một cách vô ích và không giải quyết dứt điểm được lỗi nếu lần sau mạng lag quá 5 giây.

Solution
EN

Rely fully on Playwright's smart auto-waiting combined with web-first assertions. The system polls an element's state in the background until the condition is met or the timeout is hit. Hard waits are off the table entirely.

VI

Áp dụng triệt để cơ chế Auto-waiting thông minh kết hợp bộ kiểm tra hướng giao diện (web-first assertions) của Playwright. Hệ thống sẽ tự động thực hiện lặp vòng kiểm tra (polling) trạng thái phần tử ngầm cho đến khi thỏa mãn điều kiện hoặc đạt giới hạn tối đa (timeout). Tuyệt đối cấm dùng hard wait.

In practice
EN

Configure automatic retries for randomly failing scenarios with retries: 2 in the config file. When writing checks, always use assertions that wait on their own, like await expect(page.locator('.success-toast')).toBeVisible({ timeout: 7000 }); Playwright stops waiting and passes the moment the element shows up, whether that's the first second or the second.

VI

Cấu hình tự động chạy lại kịch bản lỗi ngẫu nhiên trong file config bằng lệnh retries: 2. Khi viết code kiểm tra, luôn dùng các hàm async tự động chờ đợi dạng: await expect(page.locator('.success-toast')).toBeVisible({ timeout: 7000 }). Playwright sẽ tự động dừng chờ và pass ngay tại giây thứ nhất hoặc thứ hai nếu phần tử hiển thị sớm.

EN

This project's own CLAUDE.md states the same rule for timeouts in general: named constants from src/constants/timeouts.ts replace magic numbers, and every one of those constants is CI-aware rather than a single guessed value.

VI

CLAUDE.md của chính project này nêu đúng quy tắc đó cho timeout nói chung: hằng số có tên từ src/constants/timeouts.ts thay cho số ma thuật, và mỗi hằng số đó đều nhận biết môi trường CI thay vì chỉ là một con số đoán chừng duy nhất.

→
EN

Web-first assertions only retry the specific check they wrap. A plain variable read followed by a manual if isn't covered by that retry logic, the assertion itself has to be the thing doing the waiting.

VI

Web-first assertion chỉ tự thử lại đúng phép kiểm tra mà nó bọc. Việc đọc một biến thường rồi tự viết if không nằm trong cơ chế thử lại đó, bản thân assertion phải là thứ đảm nhận việc chờ.

Extracting page-load metrics (Core Web Vitals & Performance API)

Turn window.performance timing into a hard CI gate
Context
EN

A business needs to closely monitor page-load performance to make sure new front-end code doesn't slow the interface down and violate Google's Core Web Vitals standards for SEO and user experience.

VI

Doanh nghiệp cần giám sát chặt chẽ hiệu năng tải trang web để đảm bảo code mới của lập trình viên Front-end không làm giảm tốc độ hiển thị giao diện, vi phạm các tiêu chuẩn tối ưu SEO và trải nghiệm người dùng của Google (Core Web Vitals).

Why it's hard
EN

Ordinary functional tests only check whether elements render with the right data, not how long that took, so a page can degrade badly (a real UI performance regression) while the test suite still shows green on CI/CD.

VI

Các bài test chức năng thông thường chỉ kiểm tra xem các phần tử có hiển thị đúng cấu trúc dữ liệu hay không chứ không đo lường thời gian tải, dẫn đến việc trang web bị chậm nghiêm trọng (UI performance regression) nhưng bài test vẫn báo xanh (pass) trên hệ thống CI/CD.

Solution
EN

Reach directly into the browser's window.performance object during the automation run to pull real timing numbers and set quality-gate thresholds (an SLA).

VI

Truy cập trực tiếp vào đối tượng quản lý hiệu năng hệ thống window.performance của trình duyệt web ngay trong quá trình chạy automation để trích xuất các chỉ số thời gian thực tế và thiết lập các chốt chặn chất lượng (SLA).

In practice
EN

After the page finishes loading, run code in the browser context: const timingJson = await page.evaluate(() => JSON.stringify(window.performance.timing)). Extract and compute: const loadTime = timing.loadEventEnd - timing.navigationStart. Assert expect(loadTime).toBeLessThan(2500) to fail the CI build if the page takes longer than 2.5 seconds to load.

VI

Sau khi load xong trang, gọi lệnh thực thi mã nguồn trong trình duyệt: const timingJson = await page.evaluate(() => JSON.stringify(window.performance.timing)). Trích xuất và tính toán dữ liệu: const loadTime = timing.loadEventEnd - timing.navigationStart. Sử dụng câu lệnh assert: expect(loadTime).toBeLessThan(2500) để đánh trượt bài test trên CI nếu trang web tải lâu quá 2.5 giây.

EN

page.waitForLoadState('networkidle') needs to run before reading the timing object, otherwise loadEventEnd may not be populated yet and the calculated total comes out wrong.

VI

page.waitForLoadState('networkidle') cần chạy trước khi đọc object timing, nếu không loadEventEnd có thể chưa được điền và tổng tính ra sẽ sai.

→
EN

window.performance.timing is the older Navigation Timing API. It still works for straightforward SLA-style thresholds like this, but newer Core Web Vitals metrics (LCP, CLS, INP) live under a different, more detailed API if a suite needs those specifically.

VI

window.performance.timing là Navigation Timing API đời cũ hơn. Nó vẫn đủ dùng cho các ngưỡng kiểu SLA đơn giản như thế này, nhưng các chỉ số Core Web Vitals mới hơn (LCP, CLS, INP) nằm trong một API khác chi tiết hơn nếu suite cần riêng chúng.

performance-timing.spec.ts TypeScript 
test('monitors page-load performance metrics', async ({ page }) => {
  await page.goto('/landing-page');
  await page.waitForLoadState('networkidle');

  const performanceTimingJson = await page.evaluate(() => JSON.stringify(window.performance.timing));
  const timing = JSON.parse(performanceTimingJson);

  const timeToFirstByte = timing.responseStart - timing.navigationStart;
  const domContentLoadedTime = timing.domContentLoadedEventEnd - timing.navigationStart;
  const totalPageLoadTime = timing.loadEventEnd - timing.navigationStart;

  console.log(`⏱️ TTFB: ${timeToFirstByte}ms`);
  console.log(`⏱️ DOM Content Loaded: ${domContentLoadedTime}ms`);
  console.log(`⏱️ Total Page Load Time: ${totalPageLoadTime}ms`);

  expect(timeToFirstByte).toBeLessThan(400);
  expect(totalPageLoadTime).toBeLessThan(2500); // UI must load in under 2.5 seconds
});

Automatic flaky test detection and isolation

Catch the failed-then-passed-on-retry pattern automatically
Context
EN

In large projects running thousands of UI test cases a day on CI/CD, random flaky failures caused by temporary network congestion or hardware resource lag come up fairly often, and that noise erodes trust in the automation system.

VI

Trong các dự án lớn chạy hàng nghìn test case UI mỗi ngày trên CI/CD, hiện tượng test bị fail ngẫu nhiên (flaky test) do nghẽn mạng tạm thời hoặc lag tài nguyên phần cứng xảy ra rất phổ biến, làm nhiễu kết quả và gây mất lòng tin vào hệ thống automation.

Why it's hard
EN

A QA engineer can't manually comb through hundreds of run logs a day to work out which failures are real product bugs and which are false failures from a laggy environment.

VI

Kỹ sư QA không thể ngồi dò thủ công hàng trăm bản ghi log chạy mỗi ngày để phân tích xem test case nào bị fail thật do bug của sản phẩm, test case nào bị fail giả do môi trường lag để tìm cách sửa code.

Solution
EN

Build a custom reporter that connects to a centralized data management system. It automatically analyzes test run history, calculates each scenario's failure frequency, and automatically quarantines unstable scenarios out of the main deployment pipeline.

VI

Xây dựng một Custom Reporter tùy biến kết nối với hệ thống quản lý dữ liệu tập trung. Trình báo cáo này sẽ tự động phân tích lịch sử chạy test (test run history), tính toán tần suất lỗi của từng kịch bản, và tự động gắn nhãn cách ly (quarantine) các kịch bản không ổn định ra khỏi bộ test chính của luồng deploy.

In practice
EN

Create a class that implements Playwright's Reporter interface. Write the logic inside the test-end event handler, async onTestEnd(test, result). Check if result.status === 'failed' but the retry then passed, if so, automatically fire an HTTP POST with that test's identifying details to a health-tracking dashboard (e.g. Currents or an ELK Stack).

VI

Tạo một file class kế thừa cấu trúc Reporter của Playwright. Viết logic bên trong hàm sự kiện kết thúc test async onTestEnd(test, result). Kiểm tra nếu result.status === 'failed' nhưng ở lượt retry lại thành công, hệ thống sẽ tự động thực hiện một request HTTP POST đẩy thông tin định danh của test case đó về dashboard theo dõi chỉ số sức khỏe (ví dụ Currents/ELK Stack).

EN

This pattern reads from data Playwright already tracks internally, test.results holds one entry per attempt, so it doesn't need any extra instrumentation added to the tests themselves, only a reporter that inspects what's already there.

VI

Kỹ thuật này đọc từ dữ liệu Playwright đã tự theo dõi sẵn, test.results chứa một mục cho mỗi lần thử, nên không cần thêm bất kỳ instrumentation nào vào bản thân test, chỉ cần một reporter kiểm tra những gì đã có sẵn.

→
EN

This check only fires on the failed-then-retried-and-passed case. A test that fails on every retry is a real failure, not a flaky one, and doesn't belong in this bucket.

VI

Điều kiện này chỉ kích hoạt ở trường hợp fail rồi retry lại pass. Một test fail ở mọi lần thử là lỗi thật, không phải flaky, và không thuộc nhóm này.

Running UI automation on serverless infrastructure

Hundreds of headless browsers, paid for by the second
Context
EN

Sometimes a suite of over 2000 UI test cases needs to run in the shortest possible time every time a developer opens a pull request, to check the code right away.

VI

Cần chạy một bộ test suite khổng lồ gồm hơn 2000 test case UI trong thời gian ngắn nhất mỗi khi lập trình viên tạo Pull Request để kiểm tra code lập tức.

Why it's hard
EN

Sharding across traditional fixed CI virtual machines (Jenkins agents, GitHub runners) means paying a large ongoing cost to keep dozens of powerful machines running 24/7, and the maximum speed is still capped by however many of those fixed machines were rented.

VI

Nếu chạy phân mảnh (sharding) trên các máy ảo CI truyền thống cố định (như Jenkins Agent, GitHub Runner), doanh nghiệp sẽ phải chi trả một khoản chi phí cực kỳ lớn để thuê hàng chục máy cấu hình mạnh bật 24/7, nhưng tốc độ tối đa cũng bị giới hạn bởi số lượng máy ảo thuê cố định đó.

Solution
EN

Move the automation system onto serverless architecture. Package Playwright and a compressed Chromium core to run on cloud functions like AWS Lambda or Google Cloud Functions. On trigger, CI fires up 500 Lambda functions in parallel, each one running exactly one test case in a few seconds before shutting itself down.

VI

Chuyển dịch toàn bộ hệ thống automation lên kiến trúc không máy chủ (serverless architecture). Đóng gói mã nguồn Playwright và lõi trình duyệt Chromium siêu nén chạy trên các hàm đám mây như AWS Lambda hoặc Google Cloud Functions. Khi có lệnh kích hoạt, hệ thống CI sẽ kích hoạt đồng thời 500 hàm Lambda chạy song song, mỗi hàm thực thi duy nhất 1 test case trong vòng vài giây rồi tự hủy.

In practice
EN

Use a Lambda-optimized browser build library like @sparticuz/chromium alongside playwright-core. Write a handler file that receives the CI event carrying the target URL (event.targetUrl), launches a headless browser, runs the test case, closes the browser, and returns the result to the CI server to aggregate the report, all in under a minute.

VI

Sử dụng bộ thư viện build trình duyệt tối ưu cho Serverless dạng @sparticuz/chromium kết hợp với playwright-core. Viết một file handler nhận sự kiện truyền vào từ CI chứa đường link URL cần test (event.targetUrl), khởi chạy trình duyệt headless, thực thi test case, đóng browser và trả kết quả về cho máy chủ CI tổng hợp báo cáo chỉ trong vòng chưa đầy 1 phút.

EN

@sparticuz/chromium exists specifically because Lambda's deployment package size and read-only filesystem rule out a normal full Chromium install, it ships a build compressed and configured for that constrained environment.

VI

@sparticuz/chromium tồn tại chính vì giới hạn kích thước gói triển khai và hệ thống file chỉ đọc của Lambda loại bỏ khả năng cài Chromium đầy đủ thông thường, nó cung cấp một bản build đã nén và cấu hình riêng cho môi trường bị giới hạn đó.

→
EN

The drop from hours to seconds comes from running instances in parallel across many Lambda invocations, not from any single browser session running faster than usual.

VI

Việc giảm từ vài tiếng xuống vài giây đến từ chạy song song nhiều lần gọi Lambda, không phải vì một phiên trình duyệt đơn lẻ nào chạy nhanh hơn bình thường.

lambda/handler.ts TypeScript 
import playwright from 'playwright-core';
import chromium from '@sparticuz/chromium'; // Compressed Chromium build for Lambda

export const handler = async (event: any) => {
  const browser = await playwright.chromium.launch({
    args: chromium.args,
    executablePath: await chromium.executablePath(),
    headless: true,

One locator chain, automatically crossing shadow boundaries
Context
EN

Large enterprise web systems apply a micro-frontend architecture, splitting the interface across multiple independent teams, and package UI code with Shadow DOM to fully isolate CSS and components between pieces.

VI

Các hệ thống ứng dụng web doanh nghiệp quy mô lớn áp dụng mô hình kiến trúc Micro-Frontends (chia nhỏ giao diện cho nhiều đội phát triển độc lập) và đóng gói mã nguồn UI bằng công nghệ Shadow DOM nhằm cô lập hoàn toàn mã định dạng CSS và Component giữa các phần mềm.

Why it's hard
EN

Shadow DOM creates an isolated security wall (a shadow root). Older-generation testing tools like Selenium go completely blind against this structure and keep reporting that they can't find an element that's clearly visible on screen.

VI

Cơ chế Shadow DOM tạo ra một bức tường bảo mật cô lập (shadow-root). Các công cụ kiểm thử thế hệ cũ (như Selenium) sẽ hoàn toàn "mù" khi gặp cấu trúc này và liên tục báo lỗi không thể tìm thấy phần tử giao diện hiển thị trên màn hình.

Solution
EN

Rely on Playwright's newer selector engine design. Its selector filter is built to automatically pierce through every layer of Shadow DOM isolation by default, with no extra JavaScript workaround needed.

VI

Tận dụng cơ chế thiết kế công cụ định vị (selector engine) thế hệ mới tân tiến của Playwright. Nhân bộ lọc của Playwright được lập trình để có khả năng tự động đi xuyên qua tất cả các lớp ranh giới cô lập của Shadow DOM theo mặc định mà không cần viết thêm mã nguồn JavaScript bổ trợ phức tạp.

In practice
EN

Write the locator exactly as if it were a normal DOM: page.locator('fancy-button >> custom-input >> input.text-field'). The >> separator lets Playwright automatically peel back each nested shadow-root layer to interact directly with the target element buried inside.

VI

Bạn viết câu lệnh định vị phần tử một cách hoàn toàn bình thường giống như DOM truyền thống: page.locator('fancy-button >> custom-input >> input.text-field'). VI

Toán tử >> ở đây làm hai việc cùng lúc, băng từ một custom element sang custom element con của nó, và từ mỗi cái đó vào shadow root riêng, tất cả qua cùng một cú pháp locator mà test không cần biết ranh giới shadow thật sự nằm ở đâu.

→

VI

Vì hành vi xuyên thấu này là tự động, người viết test không cần biết trước phần tử lồng nào có shadow root và phần tử nào không, cùng một chuỗi locator vẫn hoạt động trong cả hai trường hợp.

Context
EN

A front-end team constantly ships interface updates. Every time they rename a class or change a button's id (say, from id="btn-login" to id="submit-auth-form"), the whole existing test codebase immediately breaks with broken locators.

VI

Đội ngũ phát triển Front-end liên tục thực hiện cập nhật cải tiến giao diện. Mỗi khi họ thay đổi tên class, đổi thuộc tính định danh nút bấm (ví dụ đổi id="btn-login" thành id="submit-auth-form"), toàn bộ bộ mã nguồn test cũ sẽ lập tức bị lỗi gãy bộ định vị (broken locators).

EN

VI

Hệ thống automation sẽ bị đánh sượt hàng loạt bài test trên CI, buộc kỹ sư automation QA phải dừng công việc lại để đi dò tìm thủ công cấu trúc HTML mới và sửa lại từng dòng selector trong code test, tạo ra một gánh nặng bảo trì (maintenance overhead) rất lớn.

Solution
EN

When Playwright can't find an element after the timeout, instead of failing the test immediately, the system captures the page's full current HTML and sends it to an AI API (an LLM like OpenAI or Claude) to analyze and find an equivalent new element that lets the test keep running.
