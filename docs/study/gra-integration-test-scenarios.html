What Makes a Test "Integration" on GRA

Integration tests verify that two or more system layers communicate correctly. On GRA, there are five boundaries worth testing.

Boundary A

Frontend → GraphQL → Magento

User action fires a GraphQL mutation or query. The backend processes it, returns structured data. The frontend re-renders from that data. Verifying the full round-trip catches serialization bugs, missing fields, and schema drift.

Boundary B

GraphQL Response → UI State

After a mutation (e.g. addProductsToCart), the mini-cart badge, overlay total, and item list must all reflect the server response — not a locally cached guess. Tests here catch React state hydration bugs.

Boundary C

UI Action → Analytics (dataLayer)

Every key action must fire the correct window.adobeDataLayer event with the right product/page data. Tests here catch GTM tag breaks that silently kill revenue reporting.

Boundary D

Cross-Storefront Localization

The same page object must render AUD on AU sites and NZD on NZ sites. Qantas Points must appear only on AU. Tests here catch config drift when GRA deploys to a new region.

Boundary E

Storefront → Third-Party Vendors

Payments, search, reviews, address lookup, loyalty, chat, analytics and ad tags all run on hosts GRA doesn't control. Tests on this boundary check that staging only talks to each vendor's sandbox or staging endpoint, and that the UI shows what the vendor returned. A separate group checks that the purchase path still works when a vendor is down. Per-brand vendor switches live in getStoreConfigData, so that response is the precondition for most of these tests.

ℹ
Not integration: clicking a nav link and asserting URL change (smoke). Integration requires verifying that two separate layers agreed on the same data — browser state matched server state, or UI event matched analytics payload.

P1 Critical Scenarios

These 6 scenarios must pass on every staging deploy. They protect the primary revenue path.

INT-001
Add to Cart — GraphQL Mutation ↔ UI ↔ Analytics
P1 Critical All 8 sites 3 Boundaries ★★★★★ ROI

The highest-value integration test. It checks that the add-to-cart mutation fires and Magento processes it, then that the mini-cart badge goes up by one, the overlay total matches the PDP price, and a cart_add event lands in adobeDataLayer.

✓
Implemented as E2E-INT-001-001..008 in tests/ecommerce/integration/add-to-cart-integration.spec.ts, with helpers in integration-helpers.ts. Mutations on these storefronts are a bare POST /graphql with operationName only in the JSON body, so URL patterns like **/graphql?**operationName=… match GET queries but never a mutation. The client operation is addConfigurableProductToCart and the field it calls is addConfigurableProductsToCart, so the spec matches the ProductsToCart substring in the body. The ACDL event is cart_add, with the product name at cart_items[0].name.
Boundary A: GraphQL mutation → Magento cart
Boundary B: Magento response → UI state
Boundary C: ATC action → Analytics event

Test Steps

  • 1
    Block noise routes (TrueFit, FullStory, Facebook, Taboola)
  • 2
    Capture the POST /graphql whose body contains ProductsToCart
  • 3
    Navigate → PLP → PDP (preferMens where required)
  • 4
    Capture productPrice BEFORE selectSize()
  • 5
    Dismiss Vans popup if present (#popup-close)
  • 6
    Select first available size → addToCart()

Assertions

  • ✓ Intercepted mutation response has cart.items.length > 0
  • ✓ Cart badge = initialCount + 1
  • ✓ Mini-cart overlay total ≈ PDP price (±0.01)
  • ✓ cart_add event in adobeDataLayer
  • ✓ cart_items[0].name on the event matches the PDP product name
// Mutations are bare POST /graphql; match on the body, pass everything else through
const state: { payload: AddToCartMutationResponse | null } = { payload: null };
await page.route('**/graphql*', async route => {
  const req = route.request();
  const body = req.method() === 'POST' ? req.postDataJSON() : undefined;
  if (!body?.query?.includes('ProductsToCart')) return route.continue();
  const response = await route.fetch();
  state.payload = await response.json();
  await route.fulfill({ response });
});

// The response field name varies by product type, so read it positionally
const result = Object.values(state.payload?.data ?? {})[0];
softAssert.toBeTruthy((result?.cart?.items?.length ?? 0) > 0, 'GraphQL cart has items');

const newCount = await pdpPage.getMiniCartCount();
softAssert.toBe(newCount, initialCount + 1, 'Cart badge incremented');

// Array scan, not getState(): getState() always returns an object, so a ?? fallback never runs
const atcEvent = await page.evaluate(() => {
  const isAtc = (e: any) => ['cart_add', 'add_to_cart'].includes(e?.event);
  return (window as any).adobeDataLayer?.find(isAtc) ?? (window as any).dataLayer?.find(isAtc);
});
softAssert.toBeTruthy(!!atcEvent, 'cart_add event in adobeDataLayer');
⚠
Vans AU: Bloomreach popup (#popup.popup.visible, z-index 200) blocks cart icon click. Dismiss via #popup-close before any Vans interaction.
Capture price BEFORE selectSize() — Vans AU drops the ATC button on size selection (race condition).
INT-002
Full Revenue Path — Search → Attraqt → PDP → Add to Cart
P1 Critical All 8 sites 2 Boundaries ★★★★★ ROI

Tests the complete top-of-funnel revenue path. Verifies that Attraqt-powered search returns relevant results, clicking a search result lands on the correct PDP (URL/product name match), and the ATC button is enabled and functional — all in a single session.

Boundary A: Search term → same-origin /fredhopper/query proxy → product cards (no Magento products query is involved)
Boundary B: Search result click → correct PDP loaded (URL + title consistent)

Test Steps

  • 1
    Navigate to storefront homepage
  • 2
    Enter site.searchTerm in search box
  • 3
    Wait for the GET /fredhopper/query response (the result data; ResolveURL only resolves the route)
  • 4
    Assert search results URL matches site.searchResultUrlPattern
  • 5
    Click first product card → wait for PDP
  • 6
    Assert product name on PDP is non-empty
  • 7
    Select size → add to cart

Assertions

  • ✓ Search URL matches /(search|\/shop\/)/i
  • ✓ At least 1 product card visible in results
  • ✓ PDP product name is non-empty string
  • ✓ PDP price matches /[A-Z]{0,3}\$[\d,]+\.\d{2}/
  • ✓ ATC button enabled after size selection
  • ✓ Cart count increments by 1
⚠
Platypus AU: Search for "Nike" sometimes redirects to /shop/nike (brand page) not /search?q=nike. The searchResultUrlPattern for Platypus already accepts both: /(search|\/shop\/)/i. Do not tighten to exact path.
Platypus NZ: on 2026-10-16 the same search redirected to the production host www.platypusshoes.co.nz/shop/nike, and the pattern above still matched. Assert the host stays stag-platypus-nz.accentgra.com as well as the path, or the rest of the test runs against production (see INT-011).

INT-004
Checkout Entry — Shipping Address → Method → Order Total Recalculation
P1 Critical All 8 sites 2 Boundaries ★★★★☆ ROI

Tests the critical checkout data path: shipping address submission fires a setShippingAddressesOnCart mutation, the available shipping methods update, and selecting a method fires setShippingMethodsOnCart, which makes the order total recalculate and display the shipping cost. This scenario stops at the payment step. Placing an order is covered separately: E2E-PLAORD-001/002 place Braintree sandbox PayPal orders and E2E-PLAORD-003 places sandbox card orders (opt-in via RUN_CARD_CHECKOUT). On the live storefront the operation names are setShippingAddress and setShippingMethods, both sent as body-only POST /graphql.

Boundary A: Address form → GraphQL mutation → shipping methods returned
Boundary B: Shipping method selection → total recalculation → UI update
⚠
Prerequisite: Cart must have items. Seed via Magento REST API before this test — navigating to checkout with empty cart redirects to homepage on all GRA sites. Use POST /rest/V1/guest-carts/{id}/items with a confirmed in-stock SKU per storefront.

Test Steps

  • 1
    API: seed cart with 1 in-stock product
  • 2
    Navigate to storefront → open mini cart → click checkout
  • 3
    Intercept setShippingAddressesOnCart mutation
  • 4
    Fill guest email + shipping address form
  • 5
    Submit address → wait for shipping methods to render
  • 6
    Select first available shipping method

Assertions

  • ✓ Shipping address mutation succeeded (no errors in response)
  • ✓ At least 1 shipping method rendered
  • ✓ Order total updates after method selection
  • ✓ Total includes shipping cost (total > item subtotal)
  • ✓ Currency symbol correct per region (AUD vs NZD)

INT-006
GraphQL Error Fallback — Network Failure Handling
P1 Critical AU sites × 4 1 Boundary ★★★★☆ ROI

Deliberately fails specific GraphQL operations using Playwright route mocking to verify the storefront degrades gracefully — showing an error state or fallback UI rather than a blank page or JS crash. This catches missing error boundaries in the PWA Studio React app.

Boundary A: GraphQL 500 error → UI error state (not blank/crashed page)

Scenarios to Fail

  • A
    GetCmsPage → 500 → homepage still renders header/nav
  • B
    GET /fredhopper/query → 500 or empty body → "No results" or error state shown (search has no productSearch GraphQL operation)
  • C
    addProductsToCart → GraphQL error → toast or inline error shown
  • D
    generateCustomerToken → invalid credentials error → login error shown in modal

Assertions

  • ✓ Page does not show a blank white screen
  • ✓ Header and navigation remain functional
  • ✓ Error message or fallback UI visible to user
  • ✓ No uncaught React "Cannot read properties of undefined" in console
// Mutations are body-only POST /graphql, so match on the body, not the URL
await page.route('**/graphql*', async route => {
  const req = route.request();
  const body = req.method() === 'POST' ? req.postDataJSON() : undefined;
  if (!body?.query?.includes('ProductsToCart')) return route.continue();
  await route.fulfill({
    status: 200,   // GraphQL returns 200 even for errors
    contentType: 'application/json',
    body: JSON.stringify({
      errors: [{ message: 'Cart not found', extensions: { category: 'graphql-no-such-entity' } }],
      data: { addProductsToCart: null }
    })
  });
});

// Expect an error toast or inline message — not a crash
const errorVisible = await page.locator('[class*="toast" i], [class*="error" i], [role="alert"]')
  .isVisible({ timeout: 5000 }).catch(() => false);
expect(errorVisible).toBe(true);

INT-007
Promo Code → applyCouponToCart Mutation → Cart Total Recalculation
P2 High All 8 sites 2 Boundaries ★★★★☆ ROI

Applies a staging promo code and verifies the applyCouponToCart GraphQL mutation returns a discounted cart, the UI updates the total, and the discount line item appears. Also covers the invalid code path — removeCouponFromCart on error.

Boundary A: Promo code → applyCouponToCart → discount applied in cart response
Boundary B: Discount in response → UI total updates + discount line visible
// Coupon mutation is a body-only POST; match the field name in the body
await page.route('**/graphql*', async route => {
  const req = route.request();
  const body = req.method() === 'POST' ? req.postDataJSON() : undefined;
  if (!body?.query?.includes('applyCouponToCart')) return route.continue();
  const response = await route.fetch();
  couponResponse = await response.json();
  await route.fulfill({ response });
});

// Assert discount is reflected in GraphQL response AND UI
const discount = couponResponse?.data?.applyCouponToCart?.cart?.prices?.discounts?.[0];
softAssert.toBeTruthy(discount?.amount?.value > 0, 'Discount amount in GraphQL response');
softAssert.toBeTruthy(await cartOverlay.isDiscountLineVisible(), 'Discount line visible in cart UI');
⚠
Data requirement: Promo codes must be stored in .env.staging and loaded via test data module — never hardcoded in spec files. Request codes from the merchandising team. Codes may expire — add a validity-check guard that skips the test if the code is rejected with a "code expired" error.
INT-008
PLP Category Filter → Fredhopper Query → Count Reduces
P2 High ×6 + △DRM 2 Boundaries ★★★☆☆ ROI

Applies a category filter on the PLP and captures the GET /fredhopper/query request it triggers. PLPs on all 8 storefronts are served by this same-origin Fredhopper proxy, with GraphQL helpers (fredhopperSeoConvertToFRH, fredhopperFRHConvertToPretty) translating between the SEO URL and the Fredhopper location. The test checks that the new fh_location carries the filter, the result count in the response drops below the pre-filter count, and the grid matches the response.

Boundary A: Filter click → /fredhopper/query with the filter in fh_location → smaller result count
Boundary B: Result count in the response → UI product count matches
ℹ
The Fredhopper response shape (field names for the result count and items) hasn't been captured yet. Log one response per brand before writing assertions against it.
⚠
DRM AU known issue: getTotalProductCount() returns 0 on Dr. Martens AU — the <p> regex /^(\d+)\s+Products$/i does not match DRM AU's format. Use soft assertions for DRM AU and track this as an open investigation. Do not fail the suite on DRM AU count assertion.

Boundary A: Swatch href → page.goto() → React router resolves variant URL
Boundary B: URL change → Swiper gallery updates (.swiper-slide-active changes)

const swatchAnchor = page.locator('[class*="swatch"] a, [class*="colour"] a, [class*="color"] a').nth(1);

expect(afterSrc).not.toBe(beforeSrc);  // gallery updated

INT-010
Spend & Save — Cart Threshold → Discount Ladder (Skechers NZ)
P2 High Skechers NZ only 2 Boundaries ★★★☆☆ ROI

Skechers NZ has a tiered "Spend & Save" promotion: $110 unlocks 15% off, $170 unlocks 20% off, $200 unlocks 25% off. This integration test seeds carts at each threshold via REST API, then verifies the correct discount tier is applied in the GraphQL cart response and displayed in the mini-cart UI.

Boundary A: Cart total at threshold → Magento rule engine → discount applied in customerCart response
Boundary B: GraphQL cart discount → UI shows correct discount tier and % off message
// Parameterised over 3 thresholds
const tiers = [
  { minCart: 110, expectedDiscount: 15, label: 'Spend $110, Save 15%' },
  { minCart: 170, expectedDiscount: 20, label: 'Spend $170, Save 20%' },
  { minCart: 200, expectedDiscount: 25, label: 'Spend $200, Save 25%' },
];

for (const tier of tiers) {
  // Seed cart via REST to exactly meet threshold
  await apiClient.seedCartToAmount(guestCartId, tier.minCart);

  // Open mini cart and verify discount is shown
  await cartOverlay.waitForOverlayVisible();
  const discountText = await cartOverlay.getDiscountMessage();
  softAssert.toContain(discountText, `${tier.expectedDiscount}%`, tier.label);
}

Third-Party Vendor Map

Built from a passive Playwright run on all 8 staging storefronts on 2026-10-16. It visited home, search suggest, search results, a PDP, add to cart, the cart page, checkout shipping, and the payment step with every payment radio selected in turn. It placed no order and submitted no form. It ran in headless Chromium at 1920×1080 from a Vietnam IP, so geo-gated vendors may behave differently for AU and NZ shoppers or on US-hosted CI runners. Two stores never reached checkout, so their checkout column comes from storeConfig only. On Platypus NZ the add to cart ran but the cart badge stayed at 0. On Skechers NZ none of the first 10 MENS products had a purchasable size.

GraphQL Mutation Interceptor

Queries are GET with operationName in the URL; mutations are a bare POST /graphql with it only in the body. Match mutations on a substring of the body's query, pass everything else through. The working version is createAddToCartCapture() in tests/ecommerce/integration/integration-helpers.ts.

async function captureMutation(page: Page, bodyMatch: string) {
  const state: { payload: unknown } = { payload: null };
  await page.route('**/graphql*', async route => {
    const req = route.request();
    const body = req.method() === 'POST' ? req.postDataJSON() : undefined;
    if (!body?.query?.includes(bodyMatch)) return route.continue();
    const res = await route.fetch();
    state.payload = await res.json();
    await route.fulfill({ response: res });
  });
  return state;
}

// Usage: field name varies, so read data positionally

REST API Cart Seeding

Seed cart before checkout/promo tests — faster than UI ATC flow.

Unverified on GRA staging: the existing suites seed carts through GraphQL (createCart, add-to-cart mutation), not these REST endpoints. Prefer the GraphQL route until the REST one is confirmed.

// POST /rest/V1/guest-carts → cartId
// POST /rest/V1/guest-carts/{cartId}/items
async function seedGuestCart(
  apiClient: ApiClient,
  baseUrl: string,
  sku: string,
  qty = 1
): Promise<string> {
  const { data: cartId } = await apiClient
    .post(`${baseUrl}/rest/V1/guest-carts`, {});
  await apiClient.post(
    `${baseUrl}/rest/V1/guest-carts/${cartId}/items`,
    { cartItem: { sku, qty, quote_id: cartId } }
  );
  return cartId;
}
