E2E-PLAORD-001 (Place order via PayPal, guest user) implemented 2026-07-27, initially scoped to Platypus AU only, then extended to all 8 storefronts (see recent.md "Week of 2026-07-27": "approved PayPal guest popup extension"). **Correction (2026-09-11):** this note previously said "scoped to Platypus AU only (not all 8 storefronts)" — that was stale. `tests/ecommerce/regression/paypal-checkout.spec.ts` loops `storefronts.entries()` and its describe-block comment explicitly reasons about "All 8 tests... the SAME PayPal sandbox buyer" sharing one file in `mode: 'default'` (not `serial`) specifically so they don't cascade-skip. Trust the code over this note per the vault's own grounding rule.

**Why single-storefront-first (historical):** Discovery report (`Guideline/E2E_DISCOVERY_REPORT.md` §7.28) lists this P1 across "All" sites; single-site scope was the deliberate *first-pass* judgment call given the real per-run cost of a live PayPal sandbox round-trip vs. the existing fast DOM-scan smoke tests — extended to all 8 once the pattern was proven.

**How to apply:** When building E2E-PLAORD-002/003/004 (PayPal logged-in, Credit Card guest/logged-in — same discovery-report section) or extending PayPal coverage to other storefronts, reuse these confirmed findings instead of re-deriving them:

- **Integration shape:** Braintree + PayPal Smart Payment Buttons, popup-based (zoid dispatch-frame → separate popup window) — NOT an inline iframe login form, NOT a same-tab redirect. `TabHelper` (now has `switchToPage()` for popup/opener restoration) is the right tool, not `FrameHelper`.
- **Sandbox vs. live verification method:** don't trust credential format alone — this account's plain `@gmail.com` address looked unusual for a generated sandbox account but was legitimate. Confirm via network instead: the functional PayPal SDK calls carrying the client-id resolve to `www.sandbox.paypal.com` with `env=sandbox`, and Braintree gateway calls go to `payments.sandbox.braintree-api.com`. Some loader/telemetry scripts legitimately load from the bare `www.paypal.com` host in both sandbox and live — that alone is not evidence of anything. Cross-check against `src/data/api/gra-test-data.ts`'s `braintree_paypal` expected-payment-methods entry as corroboration.
- **Payment-method radio value:** `braintree_paypal_gra` on the standard checkout flow. The two unlabeled "PAY WITH" buttons visible on `/cart` (class names `afterpay-button` / `paypal-button`, no accessible-name markup) are a separate cart-level express-checkout shortcut, not the main flow — the test uses the checkout radio, not the shortcut.
- **CONTINUE TO PAYMENT button gotcha:** its disabled→enabled state lags behind the shipping-method radio's own `checked` state — a genuine UI timing race, not a missing field. Poll it directly (`waitForContinueToPaymentEnabled()`) rather than assuming a checked radio means the button is ready.
- **Guest email on shipping form:** persists from the auth-modal step; the shipping form has no separate email field to re-fill.

**Files:** `src/pages/ecommerce/checkout-page.ts` (payment-step methods added to the single `EcommerceCheckoutPage`/`ecommerceCheckoutPage` fixture — no second page object), `src/pages/helpers/tab-helper.ts` (`switchToPage()`), `src/data/ecommerce/payment-accounts.ts` (`PayPalSandboxAccount`, password via `PAYPAL_SANDBOX_PASSWORD` env var, empty-string fallback → `test.skip()`), `tests/ecommerce/regression/paypal-checkout.spec.ts` + `checkout-helpers.ts` (extracted `addToCartAndReachCheckoutCta()`/`parsePriceToken()` out of `checkout.spec.ts` so the new spec doesn't import a spec file into a spec file).

**Login-mechanism discriminator for PLAORD-002 (logged-in user) — resolved 2026-09-11:** `createFreshAccountViaGraphQL` (used by E2E-CHKOUT-009) cannot log in on Platypus AU/NZ — `createCustomer` GraphQL mutation returns "Internal server error" there (see `checkout-address-prefill.spec.ts:17-20`), which would collide with this flow's all-8-storefront scope. Use the persistent per-site `testAccounts` map in `src/data/ecommerce/test-accounts.ts` instead (password via `GRA_TEST_PASSWORD` env var, same guard pattern) — it covers all 8 storefronts and is already the account auth.spec.ts logs in with. Also `fillGuestDetailsAndCommitAddress()` (checkout-helpers.ts) is NOT reusable for a logged-in session as a whole — it bundles the guest-auth-modal email submit (which a logged-in session never sees) with the address fill. **Skechers AU FAILED deterministically — dirty shared QA account, not a code defect. RESOLVED 2026-09-11.** `qa.skechers.au.t1@mailinator.com` (also used by `auth.spec.ts`) never completed checkout in this test, so its cart never emptied; mini-cart count climbed 3→4→5 across three consecutive runs while the pre-ATC read stayed 0. `checkout-helpers.ts:120`'s pre-ATC `getMiniCartCount()` read is unpolled (unlike the post-ATC read) — a contributing factor, but shared code used by 3 other passing specs, out of scope for a targeted fix here.

**Resolution mechanism:** `clearCustomerCartViaGraphQL()` in `tests/ecommerce/smoke/smoke-helpers.ts` is called as a precondition step (Step 2b) in the PLAORD-002 loop for all 8 storefronts, immediately after login and before `addToCartAndReachCheckoutCta()`. Schema: query `customerCart { id items { id quantity } }`, then mutation `updateCartItems(input: UpdateCartItemsInput!)` with `cart_items: [{ cart_item_id: Int!, quantity: 0 }]` — the field is `id` (not `uid`) on this Magento version, matching the existing precedent in `src/data/api/gra-graphql-operations.ts` / `tests/api/gra-cart-minicart.spec.ts` TC_07's `UPDATE_CART_ITEMS_MUTATION`. The helper retries up to 3 times (`MAX_CLEAR_ATTEMPTS`) because one live-observed leftover item (SKU `200054.BLK`) reappeared under a regenerated `cart_item_id` after the first mutation pass. Step 2b is precondition hygiene only (`logger.verify(...)`, no assertion) — a clear failure logs and the test continues rather than failing.

**Independent re-verification (2026-09-11, playwright-test-healer, separate from the architect's initial Skechers-only check):** ran `E2E-PLAORD-002-003` (Skechers AU) + `E2E-PLAORD-002-005` (Vans AU, regression check on a previously-passing storefront), together, 1 worker, chromium. Both PASSED with real sandbox orders placed: Skechers AU → `SKXAUST001564966`, Vans AU → `VANAUST000009917`. No fixes were required. Step 2b logged `cleared=true, itemsRemoved=0` on **both** runs — both accounts' carts were already empty going in (Skechers AU presumably emptied by the architect's own prior run, order `SKXAUST001564960`, completing checkout; Vans AU was never a dirty account to begin with, so its `itemsRemoved=0` needs no such explanation). This confirms the precondition step is wired correctly and non-fatal against an already-clean cart, but it does **not** exercise the leftover-item-removal path end-to-end — that path is still validated only by the architect's live recon note above (the `200054.BLK` / regenerated-`cart_item_id` retry case), not by an automated run with items actually present. Treat the retry-on-leftover-item logic as code-reviewed and recon-verified, not test-verified, until a future run happens to land on a genuinely dirty cart.
